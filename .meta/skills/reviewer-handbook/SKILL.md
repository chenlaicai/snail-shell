# 检视者操作手册

## Purpose

本 skill 承载检视者详细的阶段操作流程、检查要点和自检清单，与 S-04 系统提示词中的行为原则和决策规则互补。S-04 定义"什么是好的检视行为"，本手册定义"每个阶段具体怎么做"。

## When To Use

- 进入 review stage 需要逐阶段执行检视流程时
- 需要查阅 GATE 检查清单时
- 需要复检流程参考时
- 需要 PR 评论签名模板时

## 检视工作流程

按以下四个阶段顺序执行。每个阶段有明确的输入和产出，不要跳过或合并阶段。

### 阶段一：准备与上下文加载

**GATE-1: 进入 feature 的 worktree**
- 检视者必须进入当前 feature 的 worktree 目录才能读取代码进行检视
- 从 Stage 上下文注入的 `stage_output_artifacts` 中 `worktree_path` 字段获取 worktree 路径
- 如果 `worktree_path` 字段不存在，向研发者确认 worktree 路径

**GATE-2: 确认 PR 基于最新 `origin/main`**
- 比对 commit 历史，确认 PR 分支没有落后于目标分支

**GATE-3: 确认 PR 分支属于当前 feature**
- 分支名/worktree/feature 文档一致

**GATE-4: 确认 feature 文档编号合规**
- `FYYYYMMDDNN` 格式正确，在对应日期目录下不冲突

1. 加载完整上下文：PR diff、提交记录、PR 说明、当前 Feature 文档、Stage 输入、conversation 上下文和已记录验证结果
2. 当前摘要不足以判断时，使用可用的历史查询能力补足事实
3. 仍存在真实事实缺口或业务取舍时，在检视结论中说明不确定性或提出需要研发者回应的问题

### 阶段二：判断检视重点

4. 判断 PR 的语义类型和本质目标，对齐成功标准和可接受证据，再选择检视重点
5. 文档、提示词、流程治理、UI、运行时和数据模型类 PR 需分别按对应成功标准检视（不能默认套用代码缺陷清单，不能把测试通过等同于语义成立）

### 阶段三：对抗性检查

6. 采取对抗性代码检视心态，主动寻找 bug、回归风险、边界条件、缺失验证、可维护性问题和设计问题
7. 代码结构：重点关注文件、类、方法过长，职责混杂、重复逻辑、类型边界不清
8. why 注释：非显而易见的分支、兼容性处理、边界条件、防御性校验、顺序依赖或看似可简化但实际有业务/系统原因的实现，必须使用 `/** ... */` 注释说明设计意图和保护场景
9. why 注释：如果改动完全没有新增或调整必要注释，或关键不变量、外部协议边界、安全/权限边界、顺序依赖、兼容性处理、防御性校验仍只存在于 feature 文档或 PR 评论中，必须主动判断是因为逻辑确实自解释，还是遗漏了长期维护所需的 why 说明
10. 重构建议必须以不改变业务语义为前提
11. 只要问题属于当前 PR 的正确性、回归风险、可维护性、流程合规或交付产物一致性范围，就必须暴露给 PR
12. Feature 文档：确认新增或移动的 feature 文档位于 `docs/features/YYYYMMDD/` 日期目录；如果 diff 二次修改已合入 feature 文档，必须作为文档治理问题提出
13. commit/PR 模板：检查标题是否使用 `[FYYYYMMDDNN][Feature Update|BugFix|New Feature][Incompatible] 中文标题` 模板；如 diff 包含删除旧入口、改变持久化 schema 或协议字段、移除兼容层、改变用户可见流程或要求迁移，必须确认标题带 `[Incompatible]` 且 PR 正文包含 `## 不兼容更新` 段落
14. 模块边界：检查新代码是否遵守模块依赖方向（ESLint 规则自动检查，但检视者需确认例外情况是否合理）
15. 测试质量：检查测试是否为源码字符串匹配反模式（`fs.readFileSync` 读取 `.js`/`.css`/`.html`/`.sh` 源文件匹配特定字符串如 CSS class 名、HTML 结构、shell 命令、JS 标识符）——这类测试绑定在实现细节上，UI 微调或脚本重构即可导致崩溃但业务逻辑未变。测试应该验证运行时行为：函数调用、API 交互、状态转移、事件流程。断言对象的行为级属性（`hidden`、函数返回值），不受 CSS class 名称或 DOM 属性名变化影响。

### 阶段四：问题报告与对话回传

15. 所有真实存在且有修复价值的问题必须在 PR 上完整评论
16. 结论必须具体到文件和代码段；如果问题来自文档、提示词或流程语义，必须指明对应段落
17. 检视评论使用普通 PR 评论；多条意见合并到同一条评论中；评论按签名模板收尾
18. PR 评论必须使用真实 Markdown 换行
19. 检视结论、问题已提交、复检通过或仍需研发者响应时，通过 message-out 通知研发者：
    ```
    node .meta/skills/message-out/message-out.js text --text '检视结论内容' --mentions '研发者'
    ```

## 复检流程

研发者修复或回应后，必须基于最终状态重新判断：

1. **重新进入 feature 的 worktree**（研发者可能在不同 worktree 中修复）
2. **完整重新检视 PR diff**（不能只确认单个评论是否已处理，需覆盖完整 PR diff、相关上下文和可能回归风险）
3. 按 `docs/README.md` 中当前 feature 模板确认 feature 文档与最终 diff 一致
4. 如果复检期间同步、合并或发现 `origin/main` 已前进，必须在同步后重新执行准备阶段的 GATE-2 与 GATE-4
5. 没有待处理问题时，在 PR 上明确回复最终复核通过、可等待用户合入的结论

## PR 评论签名模板

具体模板见 `.meta/templates/pr-comment-signature.md`。

规则摘要：
- 检视者 PR 评论最后一行：`by 检视者（<Snail 名称>）`
- 签名与正文之间保留一个真实 Markdown 空行
- 签名不得与正文挤在同一行或非末行位置
- `<Snail 名称>` 使用当前响应 Snail 的可展示名称

## 自检清单

| 阶段 | 自检项 |
|---|---|
| 准备 | **GATE-1** 已进入 feature worktree · **GATE-2** PR 基于最新 main · **GATE-3** 分支属于当前 feature · **GATE-4** feature 文档编号合规 · 完整上下文已加载 · 事实缺口已说明 |
| 判断 | 语义类型和成功标准已对齐 · 按对应类型检视 |
| 检查 | 对抗性心态 · 结构问题已检查 · why 注释已检查 · 重构不改语义 · 问题全部暴露 · feature 文档已检查 · commit/PR 模板已检查 · 模块边界已检查 · 测试质量已检查 |
| 报告与回传 | 问题在 PR 上评论 · 具体到文件和代码段 · 评论格式正确 · Markdown 换行正确 · 已 mention 研发者 |

## Output

本 skill 不产生直接输出，而是提供流程参考。具体产出（检视评论、mentions 等）由当前 Stage 的系统提示词和 message-out skill 规范定义。
