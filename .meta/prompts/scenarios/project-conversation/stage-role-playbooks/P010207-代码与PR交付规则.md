## 代码与 PR 交付规则

### 目标

- 这组规则保护 Implementation Snail 对代码修改、commit、PR 信息和长期代码注释的交付质量。
- 代码与 PR 交付规则独立于 Development 阶段流程和 Review 阶段检视意见处理流程；只要 Implementation Snail 在项目推进中交付或更新代码与 PR，就必须遵守。

### Commit 与 PR

[0230] [commit收拢] [development, review, Implementation Snail] 所有代码修改最终必须通过 commit 收拢。
[0231] [commit拆分] [development, review, Implementation Snail] 改动范围较大时，拆分为多个主题清晰的 commit。
[0232] [commit中文] [development, review, Implementation Snail] commit 标题必须使用中文。
[0233] [PR中文] [development, review, Implementation Snail] PR 标题和正文必须使用中文。

### 代码注释

[0234] [正式注释优先] [development, review, Implementation Snail] 新增或调整代码注释时，必须优先使用 `/** ... */` 形式的正式注释。
[0235] [注释解释why] [development, review, Implementation Snail] 注释应解释 why 与设计意图，避免用随意的 `//` 注释复述代码正在做什么。
[0236] [why注释触发条件] [development, review, Implementation Snail] 当代码包含非显而易见的分支、兼容性处理、边界条件、防御性校验、顺序依赖或看似可简化但实际有业务/系统原因的实现时，必须写清楚 why 注释。
[0237] [why注释内容] [development, review, Implementation Snail] why 注释必须说明该逻辑保护的场景和不能随意改动的约束。
[0238] [保留逻辑注释] [development, review, Implementation Snail] 修改已有逻辑时，如果保留了某段看似多余或反直觉的处理，必须补充或更新 why 注释。
[0239] [删除逻辑说明] [development, review, Implementation Snail] 如果删除了原有保护逻辑，必须在 PR 中说明原保护场景为什么不再成立，以及用什么测试或验证覆盖替代风险。

### 代码注释与 PR 信息边界

[0240] [why注释长期价值] [development, review, Implementation Snail] 代码仓内的 why 注释用于支撑后续长期演进。
[0241] [代码级注释必要性] [development, review, Implementation Snail] 未来维护者仅凭代码仓也需要知道的约束、设计意图和保护场景，必须写入代码级注释。
[0242] [PR信息边界] [development, review, Implementation Snail] PR 信息只服务本次修改的评审、沟通和决策追溯，不能替代代码仓中的长期注释。
[0243] [提交前自检] [development, review, Implementation Snail] 提交 PR 前必须自检本次代码改动是否包含关键不变量、外部协议边界、安全/权限边界、顺序依赖、兼容性处理、防御性校验或容易被误删的设计取舍。
[0244] [补充why注释] [development, review, Implementation Snail] 命中上述场景时，必须补充代码级 why 注释。
[0245] [无需注释说明] [development, review, Implementation Snail] 判断无需新增注释时，应在 PR 说明或交付记录中说明理由。
