# 检视 — 参考约束

## 变更完整性证据验证

[STD] 检视者独立执行变更完整性验证，不依赖开发者的自验证据。验证命令模板和 evidence 要求见 `shared.handbook.md` 的"证据规则"章节。检视者按 task_anchor 的 change_type 执行对应命令，将实际输出写入 rev-02 的 gate_evidence。禁止以"看了 diff""开发者说验证过了"作为唯一 evidence。

## 代码结构检查

[STD] 代码结构检视重点：
- 文件/类/方法是否过长、职责是否混杂
- 是否存在重复逻辑、类型边界不清
- 先看可维护性和结构问题，再看纯格式问题

## Issue 文档检查

[STD] Issue 文档检视要点：
- 确认新增或移动的 issue 文档位于 `docs/issues/YYYY/MM/DD/` 日期目录
- 如果 diff 二次修改已合入 issue 文档追写新结论，必须作为文档治理问题提出

## commit/PR 模板检查

[STD] 确认 PR 标题模板 `[IYYYYMMDDNN][module][Issue Update|BugFix|New Issue] 中文标题` 格式正确。如包含不兼容变更，确认带 `[Incompatible]` 标记且 PR 正文有 `## 不兼容更新` 段落。

## 模块边界检查

[STD] 检查新代码是否遵守模块依赖方向（ESLint 规则自动检查，检视者确认例外情况是否合理）。

## 测试质量审查

[STD] 检查测试是否验证业务行为/设计契约而非源码文本匹配：
- 源码字符串匹配反模式（`fs.readFileSync` + `str.includes` 匹配 CSS class/shell 命令/HTML 结构/JS 标识符）必须在检视中指出
- 测试应通过运行时行为验证（函数调用、API 交互、状态转移、事件流程）
- 不以源码字符串匹配方式断言 CSS class 或 aria 属性，但通过运行时 DOM 行为验证无障碍语义等可访问性契约是合理的

## 复检详细步骤

[STD] 研发者修复或回应后，复检步骤：
1. 重新进入 issue 的 worktree
2. 完整重新检视 PR diff（不能只确认单个评论是否已处理）
3. 确认 issue 文档与最终 diff 一致
4. 如果 origin/main 已前进，重新执行 GATE-2 和 GATE-4
5. 没有待处理问题时，在 PR 上明确回复最终复核通过、可等待用户合入的结论

## 重构建议边界

[STD] 重构建议必须以不改变业务语义为前提。
