# 测试 — 参考约束

## 测试质量

[STD] 测试验证业务行为/核心设计契约，不是源码文本匹配：
- 不允许通过 `fs.readFileSync` + `str.includes` 匹配源码字符串（CSS class、shell 命令、HTML 结构、JS 标识符）
- 测试应通过运行时行为验证（函数调用、API 交互、状态转移、事件流程）
- 不要求 100% 覆盖率；优先覆盖核心契约、边界条件和已知风险点

## 行为契约测试范式

[STD] AI 时代测试编写范式：测试场景来源于 feature spec 的核心业务行为列表，而非 AI 从代码中推导。

**行为契约测试**：断言外部可观测行为（输入/输出/状态变化/错误），场景来源于 feature spec 的核心业务行为列表。代码重构时只要行为不变，测试就不该挂。

**实现绑定测试**（禁止）：断言内部实现（函数调用次数/参数/调用顺序/内部状态），场景来源于 AI 扫描代码结构。代码重构即挂，无法区分"行为变了"还是"实现变了"。

**"业务场景"判定标准**（适用于行为契约测试；其他测试类型如设计契约、性能测试不受此约束，但仍须避免禁止层）：断言的是外部可观测行为，还是内部实现？前者是业务场景，后者不是。
- 是：Issue 创建时未指定 SOP → 报错
- 不是：validateSOP() 被调用了 1 次
- 不是：createIssue 应先调用 validateSOP 再调用 saveToDB（断言调用顺序）

**测试场景来源**：feature spec 的"核心业务行为"章节。如果章节不存在或列表为空，不得自行推导，必须升级给用户要求补充。

**测试分层**：
1. 行为契约测试（最高优先级）：核心业务流程的行为正确性
2. 回归测试（只出可退）：已发现的真实 bug 不再复现；被测功能移除时可删除
3. 可访问性契约测试：面向辅助技术的运行时 API 契约

**mock 边界**：
- 允许 mock：数据库、文件系统、网络请求、第三方 API、时间/随机数
- 禁止作为断言依据：mock 的调用次数（N 次）、调用参数、调用顺序
- 允许作为行为否定断言：断言某个函数未被调用（`expect(fn).not.toHaveBeenCalled()`）
- 允许作为隔离手段：mock 被测模块的内部函数，但测试必须断言外部可观测行为

## 自检覆盖

[STD] 自检修复必须覆盖触发场景和既有路径，不得仅验证新代码片段。修复 bug 时必须验证原始 bug 触发场景 + 相关既有路径未被影响。

## Diff 范围校验

[STD] 实际 diff 超出 feature 文档范围时先更新文档，再提交 PR。文档必须准确反映本次变更的实际范围和设计取舍。

## 测试失败决策

[STD] 当测试因你的代码变更而失败时，按以下决策路径处理：

1. **代码变更是否是有意的*行为*变更？**（注意区分：有意的代码变更 ≠ 有意的行为变更）
   - 有意的行为变更（用户明确要求改变系统行为）→ 更新测试以匹配新行为
   - 有意的代码变更但非有意的行为变更（重构、优化、可读性改进）→ 测试不该挂；如果挂了，说明引入了无意的行为变更 → 进入步骤 2
   - 无意的代码变更 → 进入步骤 2

2. **测试是否断言的是外部可观测行为？**（行为契约测试）
   - 是 → 这是无意的回归 → 修复主代码
   - 否 → 进入步骤 3

3. **测试断言的是内部实现**（函数调用、内部状态、源码结构）
   - → 删除测试，不要改主代码来让它通过

**补充：设计意图判断**（SOP 场景）：
- 有 Feature 文档 → 对照 [design-time] 章节的设计声明，逐条检查
- 无 Feature 文档 → 对照对话中的需求声明、commit 描述、任务锚

禁止：为了让测试通过而回退符合设计的业务代码变更（测试是仆，代码是主，详见 B-01 硬约束）
