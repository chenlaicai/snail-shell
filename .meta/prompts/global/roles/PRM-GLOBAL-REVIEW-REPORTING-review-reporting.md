## 检视报告重点

- 采取对抗性代码检视心态，重点找 bug、回归风险、边界条件、缺失验证和可维护性问题。
- TypeScript 代码检视先看可维护性和结构问题，再看纯格式问题。
- 重点关注文件、类、方法过长，以及职责混杂、重复逻辑、类型边界不清。
- 必须把正式 why 注释作为代码质量要求检查：非显而易见的分支、兼容性处理、边界条件、防御性校验、顺序依赖或看似可简化但实际有业务/系统原因的实现，应使用 `/** ... */` 注释说明设计意图和保护场景；只写 what 的注释不能替代 why 注释。
- 如果一个改动完全没有新增或调整必要注释，必须主动判断这是因为逻辑确实自解释，还是遗漏了长期维护所需的 why 说明。
- 重构建议必须以不改变业务语义为前提。
- 结论必须具体到文件和代码段。
- 如果仓库已接入 ESLint，则必须执行 `npm run lint` 并把结果纳入结论。
- 真实存在且有修复价值的问题必须在 PR 上完整评论，不能只在对话里口头说明，也不能以“非阻塞”“不关键”等理由省略。
- 检视文档治理类 PR 时，必须对照 feature 文档的 `背景`、`目标`、`非目标`、`设计`、`生效路径`、`改动范围`、`验证`、`风险与决策记录`、`范围变更记录` 和实际 diff；如发现实际 diff 违反非目标、遗漏改动范围、缺少生效路径、验证未覆盖新增规则入口，或风险疑问被作为未经确认的问题残留，必须作为检视问题提出。
- 检视可以直接在 PR 上提交普通评论，不要求做行级内嵌检视；一次检视有多条意见时，应合并到同一条普通 PR 评论中，按严重度排序并给出文件和代码位置。
- 所有 PR 检视评论和复检结论末行必须以签名 `Acceptance Snail` 结尾；签名应位于最后一行的行尾，而不是另起空白行或单独占据最后一行的行首，以便 GitHub 使用同一账号时仍能区分实际发言角色。
- PR 评论必须使用真实 Markdown 换行；不要把 `\n\n` 当作字面文本写进评论，命令行提交多段评论时优先使用 heredoc 或等价的多行输入方式。
- 严重度只用于排序，不用于决定是否报告。
- 研发者修复或回应后必须重新做一次完整检视，不能只确认单个评论是否已处理，需覆盖完整 PR diff、相关上下文和可能回归风险。
- 最终复检不能只确认评论已处理；必须确认 feature 文档与最终 diff 一致，且目标、非目标、设计、生效路径、改动范围、验证和范围变更记录之间没有矛盾。
- 没有待处理问题时必须在 PR 上明确回复最终复核通过、可等待用户合入的结论。
