## 研发执行重点

- 先和用户收敛需求、设计和问题边界，再动手实现。
- 严禁默认采用“最小修复”或打补丁式处理；不得只围绕单点症状堆条件分支，必须先完成全链路影响分析，再基于已确认的问题边界完成完整修复，覆盖必要的代码、测试、文档或流程调整。
- 如果完整修复会显著扩大改动范围、影响架构或改变用户可见行为，应先向用户说明取舍并确认边界；不能以未经确认的“最小改动”替代完整修复。
- 修改既有逻辑前，必须先理解原逻辑服务的场景、约束和历史取舍；不能只针对新发现的问题做单点修补。
- 设计修复方案时，必须同时列出新场景和受影响的原有场景，确认修复不会让原本支持的合理行为退化。
- 面向 Snail Shell 本仓库的 feature 开发，必须先检查 `docs/features/` 是否已有对应 feature 文档；如没有，应先按 `docs/README.md` 的编号和模板规则创建 feature 文档，再进入实现。feature 文档必须随需求收敛、设计取舍、检视反馈和验证结果同步更新，不能只作为事后记录。
- feature 文档不应残留未经确认的问题；研发者发现风险、疑问或待决策事项时，必须向用户或相关参与者提出并收敛，文档记录沟通后的决策、接受遗留的原因、后续处理条件或跟进方式，而不是把“待确认”作为未处理问题池。
- 每次因用户补充、实现发现或检视意见导致实际 diff 超出 feature 文档原先范围时，必须先按 `docs/README.md` 中当前 feature 模板更新 feature 文档的受影响部分，并记录范围变化，再继续实现或回复检视。
- 梳理或调整提示词时，必须消除重复、冲突和边界不清的规则；同一约束只应放在最稳定、最贴近责任边界的位置。
- 完成实现后必须自检、运行必要验证，并提交 PR。
- 提交 PR 前、处理检视意见后或回复 PR 前，必须检查需求讨论、设计取舍、实现教训和验证结果中是否出现可复用知识；命中用户长期偏好、项目规则、流程约束、设计决策、失败教训或开放治理问题时，使用 `knowledge-candidate` skill 创建待审批候选，不能因为主开发任务繁忙而跳过明确触发点。
- 所有代码修改最终必须通过 commit 收拢；改动范围较大时，拆分为多个主题清晰的 commit。
- commit 标题必须使用中文；PR 标题和正文必须使用中文。
- 新增或调整代码注释时，必须优先使用 `/** ... */` 形式的正式注释；注释应解释 why 与设计意图，避免用随意的 `//` 注释复述代码正在做什么。
- 当代码包含非显而易见的分支、兼容性处理、边界条件、防御性校验、顺序依赖或看似可简化但实际有业务/系统原因的实现时，必须写清楚 why 注释，说明该逻辑保护的场景和不能随意改动的约束。
- 修改已有逻辑时，如果保留了某段看似多余或反直觉的处理，必须补充或更新 why 注释；如果删除了原有保护逻辑，必须在 PR 中说明原保护场景为什么不再成立，以及用什么测试或验证覆盖替代风险。
- 必须区分代码注释和 PR 信息的边界：代码仓内的 why 注释用于支撑后续长期演进，必须记录未来维护者仅凭代码仓也需要知道的约束、设计意图和保护场景；PR 信息只服务本次修改的评审、沟通和决策追溯，不能替代代码仓中的长期注释。
- 修复 bug 时，测试或手动验证不能只覆盖触发 bug 的新场景，还必须覆盖与被修改逻辑相关的既有成功路径、边界路径和失败路径；无法自动化覆盖时，必须在 PR 中说明人工验证范围。
- 代码修改必须可追溯到当前 stage 与 conversation 的目标。
- 在研发阶段不要 @Acceptance Snail；当前阶段没有检视者存在，提及也不会产生有效检视。
- 进入检视阶段后，再主动 @Acceptance Snail 检视 PR。
- 对检视意见逐条判断：合理则修复并回复，不合理则说明理由。
- 回复 PR 检视意见时使用普通 PR 评论即可；多条回复应合并到一条普通评论中，避免无必要的行级内嵌回复。
- 回复 PR 检视意见或补充 PR 说明时，评论末行必须以签名 `Implementation Snail` 结尾；签名应位于最后一行的行尾，而不是另起空白行或单独占据最后一行的行首，以便 GitHub 使用同一账号时仍能区分实际发言角色。
- 在 PR 评论或回复中必须使用真实 Markdown 换行；不要把 `\n\n` 当作字面文本写进评论，命令行提交多段内容时优先使用 heredoc 或等价的多行输入方式。
- 检视未清零前不要宣称本轮完成。
