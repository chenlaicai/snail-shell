# Code Style Review

## Purpose

这个 skill 用于在 TypeScript 代码检视中，优先识别可维护性退化问题，尤其是文件、类、方法过长，以及职责混杂、重复逻辑、类型边界不清的问题。

## When To Use

当用户要求“代码规范检视”“代码规范化”“重构但不改业务语义”“按规范 review”时使用。

它适用于全仓扫描，也适用于针对单个文件或单次变更的检视。

## Rules

1. 检视重点先看可维护性和结构问题，再看纯格式问题，不要把注意力主要放在空格、换行一类低价值样式差异上。
2. 优先参考主流 TypeScript/JavaScript 实践，尤其是 `typescript-eslint` 推荐规则、Google TypeScript Style Guide、Airbnb JavaScript Style Guide 中与可读性和可维护性相关的部分。
3. 如果单个文件明显过长，应优先判断是否存在多个职责混在一起；通常应按职责拆分为更内聚的模块，而不是只在原文件中继续堆辅助函数。
4. 如果单个类明显过长，应检查是否同时承担了编排、格式化、校验、持久化、协议转换等多种职责；应建议把纯函数逻辑、格式转换逻辑、工具辅助逻辑提取出去。
5. 如果单个方法明显过长，应检查是否可以拆成命名清晰的私有方法或纯函数；拆分后必须保持调用路径清晰，避免过度抽象。
6. 重构建议必须以“不改变业务语义”为前提，优先最小正确改动，避免为了形式上的短小而引入额外层级、过多新类型或不必要的抽象。
7. 对重复逻辑，优先提取单一辅助函数；如果重复逻辑跨模块复用，再考虑提取共享模块。
8. 对公共接口、导出函数、类的公开方法，要求类型边界清晰；避免 `any`、隐式不明确返回值、过宽的输入输出类型。
9. 对条件分支和状态分支，优先要求显式、可读、可验证；发现容易漏分支的逻辑时，应建议增加穷尽性检查或更清晰的分支结构。
10. 如果发现模块同时包含核心业务逻辑和展示/协议拼装逻辑，应建议分层，至少把纯格式化、序列化、描述生成之类逻辑从核心编排中移出。
11. 评论结论必须具体到文件和代码段，说明问题是什么、为什么影响维护、建议如何最小化处理，避免空泛口号。
12. 如果某处当前实现虽长但高度内聚、改动风险明显高于收益，应明确说明“暂不建议改”，而不是机械要求拆分。
13. 规范检视不能停留在口头建议；如果仓库已接入 ESLint，则必须执行 `npm run lint`，并把命中的规则与文件位置纳入结论。
14. 如果用户要求建立质量门禁，应将 lint 接入 `build`、`test` 或统一 `check` 流程，并确保本地提交流程会阻止不符合规则的变更。
15. 文件长度和函数长度主要作为“需要审查”的信号，不应凌驾于设计判断之上；如果代码已经高内聚、低耦合、抽象层级清晰，则应优先调整阈值以匹配项目现实，而不是为了压行数继续拆分。

## Expected Outputs

1. 一份按严重度排序的代码规范检视结果
2. 对超长文件、超长类、超长方法的具体定位与原因说明
3. 可执行的最小重构建议，明确哪些建议属于纯规范化且不改变业务语义
4. 对剩余风险、未覆盖区域和后续可继续优化点的简短说明
5. 如果仓库已有质量门禁，还应说明当前 `lint/build/test` 是否全部通过
