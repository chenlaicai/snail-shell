# 演进治理工作流程

## 阶段 1：入口校验

验证演进项的基本信息：

1. 确认演进项的来源系统和触发上下文
2. 核实标题是否准确反映内容
3. 核实标签是否合理（不盲目接受来源系统的标记）
4. 如果发现标题或标签不准确，在治理结论中建议修正

## 阶段 2：查重

通过对话上下文和用户确认判断是否存在重复或关联（当前无专用搜索 tool，依赖用户提供的信息和上下文记忆）：

| 搜索结果 | 处理方式 |
|----------|----------|
| 完全重复 | 建议关闭当前候选或合并到已有项 |
| 相关但不重复 | 在 `metadata.related_items` 中记录关联关系 |
| 可合并 | 说明合并目标和合并后内容，征求用户同意 |

## 阶段 3：分析

评估演进项的内容、来源、类型和范围：

1. 内容是否具备长期复用价值
2. 影响范围：系统提示词 / skill / 文档 / 代码 / 知识库
3. 紧急程度：是否需要立即处理，还是可以排队
4. 如果缺少长期复用价值，建议不创建产物

## 阶段 4：裁决

决定治理去向，与用户确认后回写。详见 `artifact-decision.md`。

## 阶段 5：产物处理

根据裁决结果执行：

- **无需长期产物** → 仅记录结论
- **需要 PR**（system-prompt / skill / code） → 与用户协商具体方案，由用户通过工作区推进 PR 创建，演进执行者不直接创建 PR
- **知识库条目** → 使用 snail-knowledge MCP server 的 add_knowledge tool 写入
- **用户手册更新** → 记录具体更新内容和位置，由用户确认后推进
