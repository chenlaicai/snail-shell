# 审查者工作流程详细流程

## 阶段一：准备与上下文加载

### GATE-1: 进入 issue 的 worktree
- 从 Issue.context 中通过 `design.worktree_path` 获取 worktree 路径
- 如果字段不存在，向开发者确认 worktree 路径

### GATE-2: 确认 PR 基于最新 `origin/main`
- 比对 commit 历史，确认 PR 分支没有落后于目标分支

### GATE-3: 确认 PR 分支属于当前 issue
- 分支名/worktree/feature 文档一致

### GATE-4: 确认 feature 文档编号合规
- 严格按照特性编号规则（见 `cd-shared/references/feature-numbering.md`）验证格式合法且不与已有编号碰撞

加载完整上下文：PR diff、提交记录、PR 说明、当前 Feature 文档、Stage 输入、conversation 上下文和已记录验证结果。

## 阶段二：判断检视重点

1. 判断 PR 的语义类型和本质目标，对齐成功标准和可接受证据，再选择检视重点
2. 文档、提示词、流程治理、UI、运行时和数据模型类 PR 需分别按对应成功标准检视（不能默认套用代码缺陷清单）

## 阶段三：对抗性检查

详见 `adversarial-check.md`。

## 阶段四：交叉审视

详见 `cross-review.md`。

## 阶段五：问题报告与对话回传

1. 所有真实存在且有修复价值的问题必须在 PR 上完整评论
2. 结论必须具体到文件和代码段
3. 检视结论必须逐条列出每个问题的处置状态：
   - `[已修复] 问题描述` — 开发者已在当前 PR 修复
   - `[开发者回应] 问题描述` — 开发者有合理理由不修改，审查者必须判断理由是否合理
   - `[待处理] 问题描述` — 开发者尚未处理或回应
4. 只有全部问题为"已修复"或"开发者回应（审查者认可）"时，才能给出"可等待用户合入"结论
5. 存在任何"待处理"项时，结论必须是"需要开发者继续处理"

## 复检流程

开发者修复或回应后，必须基于最终状态重新判断：

1. 重新进入 issue 的 worktree（开发者可能在不同 worktree 中修复）
2. 完整重新检视 PR diff（不能只确认单条评论是否已处理）
3. 重点关注修复是否引入新的回归风险
4. 按 feature 模板确认 feature 文档与最终 diff 一致
5. 没有待处理问题时，在 PR 上明确回复最终复核通过
6. 复检时发现开发者跳过了之前提出的任何问题，必须打回

## 阶段五补充：检视后系统内呼叫

PR 评论完成后，必须通过 `set_final_body` 的 `to_speakers` 声明路由目标。消息内容包含：
- PR 链接
- 检视结论摘要
- 待处理问题列表
