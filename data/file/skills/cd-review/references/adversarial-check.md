# 对抗性检查规则

## 核心心态

采取对抗性代码检视心态，主动寻找 bug、回归风险、边界条件、缺失验证、可维护性问题和设计问题。

## 检查维度

1. **代码结构**：重点关注文件、类、方法过长，职责混杂、重复逻辑、类型边界不清
2. **why 注释**：非显而易见的分支、兼容性处理、边界条件、防御性校验、顺序依赖等实现必须使用 `/** ... */` 注释说明设计意图和保护场景
3. **重构建议**必须以不改变业务语义为前提
4. **问题暴露**：只要问题属于当前 PR 的正确性、回归风险、可维护性、流程合规或交付产物一致性范围，就必须暴露给 PR
5. **质量改进**：措辞不精确、结构可优化、边界可收紧等不构成阻塞但能提升质量的问题，不得以"不阻塞"为由不提

## 提出的问题必须在当前 PR 中修复

审查者提出的所有问题（无论严重度）都是检视意见，开发者必须在当前 PR 中处理，不得以"不阻塞"或"可后续优化"为由推到后续 feature。

唯一合理的例外：开发者证明修复会引入更大风险（需具体说明风险），且审查者认可该理由。复检时逐条确认：未修复的问题就是待处理问题，检视不能清零。

## MUST NOT

- 审查者不得使用"低风险"、"可忽略"、"不重要"等标签跳过问题
- 审查者不得换一种说法（比如"这个问题不重要"、"这个问题可以后续再处理"）来实质跳过问题
- 复检时，如果发现审查者跳过了问题，必须打回，要求审查者重新检视

## "实质是跳过问题"的判断标准

- 审查者没有提供具体的修复方案，且没有说明为什么不修复
- 审查者以"不重要"、"可后续处理"、"不影响功能"等模糊理由拒绝修复
- 审查者以"风险很低"、"概率很小"等理由拒绝修复

## 变更完整性证据验证（rev-02 核心动作）

从 task_anchor 读取 `change_type`（和可选的 `verification_commands`），**独立执行**同一组验证命令。将实际输出写入 rev-02 的 gate_evidence；如果输出与开发者的不一致，必须作为问题提出。

禁止以"看了 diff，都改了""开发者说验证过了"作为 rev-02 的 evidence。必须是自己执行命令的输出。

## 测试质量检查

- 测试是否对应 feature spec 中的核心业务行为？（无对应行为的测试可能是填充式的）
- 断言的是外部可观测行为，还是内部实现？
- 如果删除测试中的 mock，断言是否仍然成立？
- mock 仅作为隔离手段，不作为断言依据

## Feature 文档检查

- 确认新增或移动的 feature 文档位于 `docs/features/YYYY/MM/DD/` 日期目录
- 如果 diff 二次修改已合入 feature 文档，必须作为文档治理问题提出

## 测试验证失败时的判断

独立对照 Feature 文档 [design-time] 章节判断开发者的代码变更：测试失败是因为测试未适配新设计，还是因为实现偏离了设计。不得仅因测试失败就要求开发者回退业务代码。
