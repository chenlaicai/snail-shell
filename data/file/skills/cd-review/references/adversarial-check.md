# 对抗性检查规则

## 核心心态

采取对抗性代码检视心态，主动寻找 bug、回归风险、边界条件、缺失验证、可维护性问题和设计问题。

## 检查维度

1. **代码结构**：重点关注文件、类、方法过长，职责混杂、重复逻辑、类型边界不清
2. **why 注释**：非显而易见的分支、兼容性处理、边界条件、防御性校验、顺序依赖等实现必须使用 `/** ... */` 注释说明设计意图和保护场景
3. **重构建议**必须以不改变业务语义为前提
4. **问题暴露**：只要问题属于当前 PR 的正确性、回归风险、可维护性、流程合规或交付产物一致性范围，就必须暴露给 PR
5. **质量改进**：措辞不精确、结构可优化、边界可收紧等不构成阻塞但能提升质量的问题，不得以"不阻塞"为由不提
6. **事实性声明验证**：如设计文档或 PR 描述中包含关于现状的事实性声明，审查者必须验证该声明。验证格式：`声明：{声明} | 代码证据：{代码+位置} | 结论：verified/contradicted/unverifiable`

### 通用战术适配（review 阶段）

以下检查点基于对抗性审视通用战术，详见 `cd-shared/references/adversarial-review-tactics.md`。

- **事实性声明验证**（战术 2）：review 阶段可使用，验证实现是否符合设计
- **术语一致性检查**（战术 3）：如发现术语不一致，按分级标准处置（L1 修正文档 / L2 决策记录 / L3 CONTEXT.md）
- **场景压力测试不适用于 review 阶段**：review 阶段通过完整文件覆盖检查承接实现完整性

## 提出的问题必须在当前 PR 中修复

审查者提出的所有问题（无论严重度）都是检视意见，开发者必须在当前 PR 中处理，不得以"不阻塞"或"可后续优化"为由推到后续 feature。

唯一合理的例外：开发者证明修复会引入更大风险（需具体说明风险），且审查者认可该理由。复检时逐条确认：未修复的问题就是待处理问题，检视不能清零。

## 结构化审查报告模板

审查报告中每个问题必须包含以下字段：

| 字段 | 说明 |
|------|------|
| 问题描述 | 具体到文件和代码段 |
| 风险等级 | 高/中/低 |
| 处置方式 | **只允许填"在当前 PR 修复"** |

审查报告格式示例：

```
### 问题 1
- **问题描述**：`path/to/file.ts:42` 中缺少空值校验，可能导致运行时异常
- **风险等级**：高
- **处置方式**：在当前 PR 修复
```

## MUST NOT

- 审查者不得使用"低风险"、"可忽略"、"不重要"等标签跳过问题
- 审查者不得换一种说法（比如"这个问题不重要"、"这个问题可以后续再处理"）来实质跳过问题
- 复检时，如果发现审查者跳过了问题，必须打回，要求审查者重新检视
- **禁用话术清单**（审查报告中禁止出现以下表述）：
  - "不堵塞"
  - "可遗留"
  - "建议合入"
  - "后续优化"
  - "不影响功能"
  - "不影响，建议合入"
  - 任何实质表达"可以不在当前 PR 修复"的变体话术
- **禁止用代码反驳用户**：审查者不得以"当前代码逻辑是这样做的"作为反驳用户的论据，必须分析用户意图和新逻辑的合理性

### 反破窗规则（Anti-Broken-Windows）

> 本规则是"禁止用代码反驳用户"在架构合规审查场景的具体化。前者保护用户意图不被代码现状压制；本规则保护架构原则不被已有违规压制。

审查者引用已有代码作为质量辩护时，必须遵守以下规则：

1. **验证被引用代码的合规性**：引用已有代码作为"已有模式"辩护前，必须先验证被引用代码本身是否符合架构规则（ESLint 通过、类型检查通过、无已知违规标记）。引用已知违规或未验证的代码作为辩护 = 审查缺陷。
2. **区分"一致性论据"和"合规论据"**：引用已有代码证明"新代码与已有代码风格一致"是合理的（一致性论据）；但不能以此证明"新代码的架构违规是可接受的"（合规论据）。一致性不等于合规性。
3. **warn 不等于可接受**：当 linter 输出 warning 时，审查者不得将其自动视为"已建立的可接受模式"。必须确认 warn 是有意保留（有明确注释说明原因）还是遗漏升级（如本案"待 F-1 修复后升级为 error"）。

## 审查结论自检

审查者在提交审查报告前，必须检查：
1. 报告中是否有任何禁用话术清单中的表述
2. 每个问题是否都有"处置方式"字段且填写为"在当前 PR 修复"
3. 是否有遗漏的问题未被报告

## "实质是跳过问题"的判断标准

- 审查者没有提供具体的修复方案，且没有说明为什么不修复
- 审查者以"不重要"、"可后续处理"、"不影响功能"等模糊理由拒绝修复
- 审查者以"风险很低"、"概率很小"等理由拒绝修复

## 变更完整性证据验证（rev-02 核心动作）

从 issue context 读取 `sop.change_type`（和可选的 `sop.verification_commands`），**独立执行**同一组验证命令。将实际输出在消息中呈现；如果输出与开发者的不一致，必须作为问题提出。

禁止以"看了 diff，都改了""开发者说验证过了"作为 rev-02 的 evidence。必须是自己执行命令的输出。

## 完成度审视

与代码质量审视并列，检查实现是否完整而非留了尾巴：

- 是否存在 TODO/FIXME/HACK 注释？
- 是否存在功能开关（feature flag）但未说明何时移除？
- 是否存在"临时"方案但未标记为 [Incompatible]？
- 是否存在兼容性桥接代码（if oldFormat）？
- 测试是否覆盖了新行为的正向和边界场景？

## 测试质量检查

- 测试是否对应 feature spec 中的核心业务行为？（无对应行为的测试可能是填充式的）
- 断言的是外部可观测行为，还是内部实现？
- 是否使用了 `toHaveBeenCalledWith` / `toBeCalledTimes` 等断言调用参数/次数的方法？（禁止——绑定实现细节，使用返回值/状态/副作用断言替代）
- 测试文件是否有 spec 引用注释？（建议有，非阻塞）
- 如果删除测试中的 mock，断言是否仍然成立？
- mock 仅作为隔离手段，不作为断言依据

## Feature 文档检查

- 确认新增或移动的 feature 文档位于 `docs/features/YYYY/MM/DD/` 日期目录
- 如果 diff 二次修改已合入 feature 文档，必须作为文档治理问题提出

## 测试验证失败时的判断

独立对照 Feature 文档 [design-time] 章节判断开发者的代码变更：测试失败是因为测试未适配新设计，还是因为实现偏离了设计。不得仅因测试失败就要求开发者回退业务代码。
