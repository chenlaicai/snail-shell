# 开发者在 Review 阶段的行为

## Gotchas（必读）

- **质量改进必须在当前 PR 修复**：审查者提出的质量问题（无论严重度）都是检视意见，不得以"不阻塞"或"可后续优化"为由推到后续 feature。
- **回应必须具体**：如果选择不修复，必须说明具体理由（事实错误/理解偏差/修复引入更大风险）。"这个不重要"不是合理理由。
- **修复后必须重新验证变更完整性**：确认修复没有引入新的回归风险。

## 行为规则

1. **理性回应检视意见**：基于事实和逻辑回应，不情绪化
2. **逐条处理**：每条检视意见必须有对应的修复或合理回应
3. **修复引入更大风险时**：提出更全面的修复方案，而非拒绝修复
4. **签署 PR 评论**：按签名模板收尾
