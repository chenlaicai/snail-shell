# 交叉审视与设计收敛

## 核心机制

两位架构师在同一 conversation 中通过 @mention 交互，交替提出方案和审视。

## 流程

1. 一方提出设计方案（或对需求的理解），包括"核心业务行为"列表的初稿（每条行为是"当 X 时，应该 Y"的形式，断言外部可观测行为）
2. 另一方从「这个方案会出什么问题」的角度审视
3. 审视必须产生价值：指出具体风险、遗漏场景或替代方案，不能为了反对而反对
4. 对关键设计取舍，必须在 Feature 文档中记录正反两面论述
5. 交替进行，直到双方达成共识
6. 共识不等于妥协——如果双方对某取舍无法达成一致，必须升级到用户决策

## 对抗性审视要点

- 方案是否覆盖了所有已知场景？
- "核心业务行为"列表是否完整？是否遗漏了关键行为？
- 非目标是否合理？是否有遗漏的必要范围？
- 设计取舍是否有替代方案？当前选择的理由是否充分？
- 设计复杂度是否合理？是否有更简单的等价方案？
- 是否会引入回归风险或破坏已有行为？

## 决策记录要求

每次对抗性审视后，必须将讨论的关键点记录到 Feature 文档的"关键决策记录"章节：

1. **决策点**：讨论的核心问题是什么
2. **正方论点**：支持当前方案的理由（必须具体）
3. **反方论点**：反对当前方案的理由（必须具体）
4. **最终决策**：选择的方案是什么
5. **决策依据**：为什么选择这个方案
6. **参与者**：实际参与讨论的人员

禁止只记录结论而不记录过程。

## 遗漏检查

阶段结束时，必须检查是否有遗漏的关键决策未被记录：
1. 回顾本阶段的所有对抗性审视
2. 列出所有讨论过的决策点
3. 检查每个决策点是否已记录到 Feature 文档
4. 如果发现遗漏，立即补充记录
