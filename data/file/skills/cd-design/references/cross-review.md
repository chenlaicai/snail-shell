# 交叉审视与设计收敛

## 核心机制

两位架构师在同一 conversation 中通过 @mention 交互，采用"背靠背独立分析 → 交换对抗 → 合并收敛"三阶段流程。

## 对抗产物协议

设计阶段的 `consensus: true` 信号必须携带 `adversarial_artifact`（通用字段 + Design 特有字段）。详见 `cd-shared/references/adversarial-artifact-protocol.md`。

Design 特有字段：
- `critique_obligation`：质疑义务量化产出（risk >= 2, gap >= 1, alternative >= 1）
- `independent_analysis`：独立分析过程（禁止直接同意）
- `scenario_coverage`：场景覆盖（coverage_ratio = 1.0）

## 角度分工

两位架构师分析角度不同，保障结构性独立：

| 架构师 | 聚焦维度 |
|--------|---------|
| 架构师-1 | 业务流程、用户视角、功能完整性、前端交互 |
| 架构师-2 | 技术架构、系统边界、变更影响、风险点、后端约束 |

## 三阶段流程

### Phase 1：独立分析

1. 两位架构师各自在对话中独立完成分析（通过 `set_final_body` 路由给对方）
2. 架构师-1 聚焦业务/用户/前端视角，架构师-2 聚焦技术/架构/风险视角
3. 各自的分析必须包括"核心业务行为"列表的初稿（每条行为是"当 X 时，应该 Y"的形式，断言外部可观测行为）

### Phase 2：交换对抗

1. 双方交换各自的独立分析内容
2. 架构师-1 审视架构师-2 的方案，架构师-2 审视架构师-1 的方案
3. **审视者必须展示独立分析过程**：在同意任何一点之前，必须先说明自己分析了什么、得出什么结论、与对方对比。禁止"分析全面，同意方案""没有补充意见"作为审视的唯一输出
4. 审视必须产生具体价值，不能为了反对而反对

#### @mention 交互协议

**触发条件**：
- 架构师完成独立分析后，产出的是**草稿方案**，必须路由给对方架构师进行对抗审视
- **您的草稿方案必须经过对方审视才能成为最终方案**——这是设计阶段的核心协作机制
- 对话即证据——分析内容通过 `set_final_body` 路由给对方，对话历史天然记录审视过程

**响应格式**：
- 审视者必须展示独立分析过程
- 禁止"分析全面，同意方案"作为唯一输出
- 必须满足质疑义务最低要求（risk >= 2, gap >= 1, alternative >= 1）

**交互轮次约束**：
- 最少一轮审视 + 一轮回应
- 最多 3 轮（审视 → 回应 → 再审视 → 再回应 → 最终审视）
- 超过 3 轮仍未达成共识，触发升级流程（见下方"升级流程"）
- 禁止单方确认

#### 升级流程

**触发条件**：
- 3 轮交互后仍未达成共识
- 或任一架构师明确表示无法接受对方方案

**触发方式**：
- 系统自动检测：当交互轮次达到 3 轮且无共识信号时，自动要求架构师发起升级
- 架构师手动发起：任一架构师在审视回应中明确表示无法接受对方方案时，主动 @用户

**升级方式**：
- @用户，附带分歧摘要

**分歧摘要格式**：
- 双方各自的核心论点（各 1-2 句话）
- 无法达成共识的具体点

### Phase 3：合并收敛

1. 合并讨论，解决分歧
2. 对关键设计取舍，必须在 Feature 文档中记录正反两面论述
3. 共识不等于妥协——如果双方对某取舍无法达成一致，必须升级到用户决策

## 质疑义务

审视者必须产出具体价值——风险点、遗漏场景、替代方案。审视报告有最低数量要求：

- 风险点 ≥ 2
- 遗漏场景 ≥ 1
- 替代方案 ≥ 1

审视意见少于上述最低要求时，视为审视不充分，必须补充。

### 处置约束

审视产出的每条发现，必须在当前阶段有明确处置——写入 Feature 文档或经纠错机制撤回。不得以"建议后续阶段处理"作为处置方式。

### 禁用话术清单

审视报告中禁止出现以下表述：

- "不阻塞" / "不堵塞"
- "建议 development 阶段处理"
- "属于实现细节"
- "后续迭代" / "后续优化"
- "不影响设计"
- 任何实质表达"可以不在当前阶段处理"的变体话术

**例外**：当架构师按 Gotchas #25 的分类标准将发现归类为"实现建议"并写入实现指引时，可以使用上述短语解释分类理由（如"属于实现细节，写入实现指引"），但必须伴随明确的处置动作（写入实现指引），不得单独使用这些短语作为处置结论。

## 禁止无条件同意

- 禁止"分析全面，同意方案"作为审视的唯一输出
- 禁止"没有补充意见"作为审视的唯一输出
- 审视者在同意任何一点之前，必须先展示自己的独立分析过程

## 对抗性审视检查点

- 方案是否覆盖了所有已知场景？
- "核心业务行为"列表是否完整？是否遗漏了关键行为？
- **每条行为条目是否满足质量标准？**（参照 `references/behavior-item-guide.md`：S1 触发条件具体、S2 预期行为可观测、S3 值得守护、S4 粒度适中、S5 不绑定实现）
- 非目标是否合理？是否有遗漏的必要范围？
- 设计取舍是否有替代方案？当前选择的理由是否充分？
- 设计复杂度是否合理？是否有更简单的等价方案？
- 是否会引入回归风险或破坏已有行为？
- 是否有未经用户确认的假设被当作确定决策？
- **前端影响是否被遗漏？**
- **变更影响分析是否覆盖后端/前端/提示词三个维度？**
- **禁止用代码反驳用户**：不得以"当前代码是这样做的"作为反驳，必须分析用户意图和新逻辑的合理性

## 变更影响分析强制维度

变更影响分析必须覆盖以下三个维度：

- **后端**：API、数据模型、业务逻辑、配置
- **前端**：UI 组件、交互流程、状态管理、路由
- **提示词/SOP**：相关 skill 和 SOP 的变更

## 决策记录要求

每次对抗性审视后，必须将讨论的关键点记录到 Feature 文档的"关键决策记录"章节：

1. **决策点**：讨论的核心问题是什么
2. **正方论点**：支持当前方案的理由（必须具体）
3. **反方论点**：反对当前方案的理由（必须具体）
4. **最终决策**：选择的方案是什么
5. **决策依据**：为什么选择这个方案
6. **参与者**：实际参与讨论的人员

禁止只记录结论而不记录过程。

## 遗漏检查

阶段结束时，必须检查是否有遗漏的关键决策未被记录：
1. 回顾本阶段的所有对抗性审视
2. 列出所有讨论过的决策点
3. 检查每个决策点是否已记录到 Feature 文档
4. 如果发现遗漏，立即补充记录

## Stage Gate（design-04）

产出锁定前必须满足以下条件：

- **design-04**：存在至少一轮交叉审视记录（双方各自的审视 + 对方的回应）

**Gate 检查方式**：
- 对话历史中必须存在双方架构师的审视记录（通过 `set_final_body` 路由的对话即证据）
- Feature 文档的"关键决策记录"章节中必须有至少两条参与者不同的决策记录
- 每条决策记录的"正方论点"和"反方论点"字段不得为空，且不得是同一论点的复述（防止形式主义绕过）
- Phase 2 完成前不得向用户呈现方案（禁止单方确认）
