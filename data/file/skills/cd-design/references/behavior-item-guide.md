# 核心业务行为条目质量标准

## 定位

核心业务行为条目是 Feature 文档中"核心业务行为"章节的每一行。它是整个测试链条的**源头**：架构师写条目 → 开发者翻译为测试 → 测试守护业务行为。

源头质量决定链条质量。一条好的行为条目能让开发者写出有意义的测试；一条坏的行为条目（trivially true、无法断言、绑定实现）会让测试变成形式合规但零价值的代码。

## 质量标准

每条行为条目必须同时满足以下 5 条标准：

### S1：触发条件必须具体

**规则**：场景列必须包含一个可识别的触发条件，不能是"当系统运行时"或"当调用 X 时"。

```
❌ 当调用 createIssue 时，应该创建 issue
   → "调用 createIssue" 是实现描述，不是业务触发条件

✅ 当用户提交 issue 创建表单且必填字段完整时，应返回 201，后续查询时应能看到一条新 issue
   → 触发条件是用户操作 + 前置状态，预期行为从外部可观测
```

### S2：预期行为必须可观测

**规则**：预期行为列必须描述外部可观测的结果（返回值、状态变化、副作用、错误），不能是"正确处理"、"正常工作"等模糊表述。

```
❌ 当用户关闭 issue 时，应该正确处理
   → "正确处理"无法断言

✅ 当用户关闭一个 open 状态的 issue 时，issue 状态应变为 closed，closed_at 应被设置为当前时间
   → 状态变化和字段值可观测、可断言
```

### S3：必须值得守护

**规则**：行为必须是"如果这个行为被破坏，用户会受影响"的业务逻辑。不能是 trivially true 的描述（函数做了它名字说的事）或实现细节。

**定位**：S3 是思考框架而非机械规则——它迫使架构师自问"如果这条被删掉，谁会发现？"。灰色地带由对抗审视兜底。

**不适用场景**：非确定性行为（AI 输出质量、LLM 响应内容）即使满足 S1-S2-S4-S5，也无法被翻译为可靠的行为契约测试。这类行为条目不应出现在核心业务行为列表中。

```
❌ 当调用 getMessage 时，应该返回消息对象
   → trivially true，函数名已经保证了这一点

✅ 当查询 issue 的消息列表时，应按时间倒序返回，且包含系统消息和用户消息
   → 排序规则和包含规则是值得守护的业务逻辑
```

**判断方法**：问自己"如果这个行为被悄悄破坏了（重构时意外改变），用户会不会受影响？" 如果答案是"不会"或"无所谓"，这条不值得守护。

### S4：粒度必须适中

**规则**：一条行为 = 一个可测试的断言。不能把多个独立行为合并为一条，也不能把一个行为拆得过细。

```
❌ 当 issue 状态变化时，应正确更新状态、发送通知、记录日志
   → 三条独立行为合并为一条，测试时无法单独验证

✅ B3: 当 issue 被关闭时，状态应变为 closed
   B4: 当 issue 被关闭时，应向所有参与者发送通知
   B5: 当 issue 被关闭时，应在 audit_log 中记录一条 closed 事件
   → 每条独立可测试
```

**粒度参考**：每条行为应能用一个不超过 20 行的测试覆盖。如果需要 50+ 行测试，可能需要拆分。

### S5：不能绑定实现

**规则**：行为描述的是"做什么"（what），不是"怎么做"（how）。不能提及具体的函数名、数据库表、API 路径或内部状态。

```
❌ 当调用 repository.update() 时，应执行 UPDATE SQL 语句
   → 绑定了 repository 层和 SQL 实现

✅ 当 issue 的标题被修改后，重新查询该 issue 时标题应为新值
   → 从外部可观测角度描述，不涉及存储层实现
```

## 好坏示例对照

### 示例 1：Issue 创建

```
❌ 坏：
B1: 当调用 createIssue 时，应该创建 issue
   违反：S1（触发条件是实现描述）、S3（trivially true）

✅ 好：
B1: 当用户提交 issue 创建表单且必填字段（title）完整时，
    应返回 201，后续查询时应能看到一条 status=open 的新 issue
    满足：S1（用户操作+前置状态）、S2（返回值+可观测状态）、S3（值得守护）、S5（不绑定实现）
```

### 示例 2：Stage 流转

```
❌ 坏：
B2: 当 advanceStage 被调用时，应该推进到下一个 stage
   违反：S1（函数调用不是业务触发）、S3（trivially true）

✅ 好：
B2: 当 design stage 的所有 Gate 自检通过且架构师达成共识时，
    应自动推进到 development stage
    满足：S1（具体触发条件）、S2（stage 变化可观测）、S3（值得守护）
```

### 示例 3：消息排序

```
❌ 坏：
B3: 当获取消息列表时，应该正确排序
   违反：S2（"正确排序"无法断言）

✅ 好：
B3: 当查询 issue 的消息列表时，应按 created_at 倒序返回，
    且同一时间戳内系统消息排在用户消息之后
    满足：S2（排序规则具体可断言）、S3（排序错误用户会注意到）
```

### 示例 4：错误处理

```
❌ 坏：
B4: 当发生错误时，应该返回错误信息
   违反：S2（"错误信息"无具体标准）、S4（粒度过粗）

✅ 好：
B4: 当创建 issue 时 title 字段为空，应返回 400 错误，
    body 中包含 `{ "error": "title is required" }`
    满足：S1（具体触发条件）、S2（返回值+body 内容具体）、S4（粒度适中）
```

### 示例 5：副作用

```
❌ 坏：
B5: 当 issue 关闭时，应该发送通知
   违反：S2（"发送通知"不够具体——发给谁？什么渠道？）

✅ 好：
B5: 当 issue 被关闭时，所有已参与过消息交互的用户
    应收到包含 issue_id 和新状态的实时推送
    满足：S2（推送对象、内容可观测）、S3（通知遗漏用户会投诉）、S5（不指定 WebSocket 实现）
```

## 对抗性审视检查点

交叉审视时，对每条行为条目执行以下检查：

| 检查项 | 标准 | 不通过的处理 |
|--------|------|-------------|
| 触发条件具体？ | S1 | 要求架构师补充触发条件的具体上下文 |
| 预期行为可观测？ | S2 | 要求架构师替换为可断言的表述 |
| 值得守护？ | S3 | 要求架构师说明"如果被破坏，用户受什么影响" |
| 粒度适中？ | S4 | 要求拆分或合并 |
| 不绑定实现？ | S5 | 要求移除实现细节 |
| 是否遗漏关键行为？ | 完整性 | 要求补充遗漏的行为 |
