# docs/meta

## 目录含义

`docs/meta/` 用于存放 Snail Shell 自身的稳定设计内容。

这里的文档不是过程记录，不是执行计划，不是阶段性讨论纪要，而是当前已经拍板、应当长期成立、可作为后续设计与实现依据的系统设计说明。

可以把这个目录理解为：

Snail Shell 自身的设计主入口。

## 这里放什么

本目录只放稳定设计类文档，例如：

1. 系统模型
2. 工作流模型
3. 知识模型
4. UI 模型
5. 存储模型
6. snail 执行单元模型

## 当前总览

当前 `docs/meta/` 下的稳定设计文档如下。

建议阅读顺序：

1. `snail-shell-system-model.md`
   说明 Snail Shell 当前拍板后的整体系统模型。

2. `snail-shell-workflow-model.md`
   说明 project 如何沿 stage chain 推进，以及为什么采用多轮迭代的阶段链模型。

3. `snail-shell-knowledge-model.md`
   说明 Snail Shell 如何组织自身的知识与痕迹，而不是退化成文档中心模型。

4. `snail-shell-ui-model.md`
   说明为什么 UI 采用左 project/conversation、中间对话、右侧上下文的结构。

5. `snail-shell-storage-model.md`
   说明数据库与文件系统的职责边界，以及为什么数据库是主结构化层。

6. `snail-shell-snail-model.md`
   说明 `snail` 作为工作室执行单元的定位、要求体系和上下文约束模型。

如果要快速理解 Snail Shell 当前设计，可以先看前 3 篇；
如果要进入实现与交互层，再继续看后 3 篇。

## 与 .meta 的关系

`docs/meta/` 和根目录 `.meta/` 并不是同一类内容。

### `docs/meta/`

存放的是稳定设计说明。

重点是：

- 为什么这样设计
- 当前模型是什么
- 当前边界是什么

### `/.meta/`

存放的是系统规范文件。

重点是：

- 固定阶段类型定义
- 阶段与 snail 的固定对应关系
- 其他需要由系统直接读取的稳定规范

简单理解：

1. `docs/meta/` 解释设计
2. `/.meta/` 提供系统规范源

这些文档应该回答的是：

- 系统是什么
- 为什么要这样设计
- 核心对象如何组织
- 重要边界在哪里
- 明确放弃了哪些方案

## 这里不放什么

本目录不放以下内容：

1. 讨论过程记录
2. 某一次对话的纪要
3. 阶段性实施计划
4. 编码 checklist
5. 某次临时问题分析
6. 演进历史记录

这些内容分别应放在其他位置，例如：

1. `docs/evolution/`
   存放 Snail Shell 的演进记录与历史痕迹文档

2. 其他 `docs/` 文档
   存放蓝图、实施计划、schema 设计、重建计划等过程性或阶段性设计内容

## 与 docs/evolution 的区别

`docs/meta/` 和 `docs/evolution/` 的职责不同。

### `docs/meta/`

保存当前已经稳定下来的系统设计结论。

重点是：

- 当前模型是什么
- 当前原则是什么
- 当前边界是什么

### `docs/evolution/`

保存 Snail Shell 是如何一步步演进到当前状态的。

重点是：

- 发生过什么变化
- 为什么变
- 哪些讨论促成了这些变化

简单理解：

1. `meta` 看“现在定下来的是什么”
2. `evolution` 看“这些东西是怎么长出来的”

## 文档写作要求

本目录下文档默认使用中文编写。

文档应尽量满足以下要求：

1. 只写稳定设计结论
2. 明确写出设计初衷
3. 明确写出边界与约束
4. 必要时写出被放弃的替代方案
5. 不混入“下一步要做什么”这类阶段性内容

## 维护规则

当 Snail Shell 某一部分设计已经形成稳定结论，并且会反复作为后续设计与实现依据时，应将其整理并沉淀到本目录。

如果某个内容仍处于讨论期、试验期、变化期，则不应直接进入本目录，而应先保留在过程性文档或演进记录中。

## 一句话总结

`docs/meta/` 存放的是：

`Snail Shell 当前已经拍板、可作为长期设计依据的稳定系统设计内容。`
