# ADR-001: 特性编号从顺序递增改为随机码

## 状态

已接受

## 背景

特性编号格式为 `FYYYYMMDDNN`，其中 `NN` 是同日从 01 开始的顺序递增编号。这带来一个严重问题：当多个 PR 并行开发时，编号冲突频繁，合入时必须「顺延」——重新编号、移动文件目录、更新 frontmatter、更新 commit message 和 PR title。

AI 执行顺延操作的出错率很高，且顺序号在代码中无任何逻辑依赖（`repository.ts` 只提取日期前缀）。

## 决策

将编号格式改为 `FYYYYMMDDxxxx`，其中 `xxxx` 为 4 位随机码（字符集 `2-9a-kmnp-z`，排除易混淆字符 0/o/1/l）。

编号在创建时一次性分配，**永不变更**。删除顺延机制。

## 理由

### 为什么不迁移已有 `FYYYYMMDDNN` 文档

- **成本**：需要重命名 ~100+ 个文件、更新每个文件的 frontmatter `id` 和 H1 标题、更新所有 `from_ids` 引用链、更新已合入 commit message（不可能）
- **收益**：仅为格式统一，无功能收益
- **结论**：成本远大于收益。代码层面已兼容两种格式（正则分组 `\d{2}|[2-9a-kmnp-z]{4}`），共存无维护负担

### 为什么不用纯数字

- 纯数字 4 位碰撞空间 10^4 = 10,000，不够
- 纯数字 6 位碰撞空间 10^6 = 1,000,000，足够但长度增加
- 混合编码 4 位碰撞空间 32^4 = 1,048,576，足够且长度最短

### 为什么排除 0/o/1/l

开发者在聊天、邮件、文档中引用 feature ID 时需要手动输入或复制。排除易混淆字符降低肉眼区分成本。碰撞空间从 36^4 降到 32^4，仍然足够。

## 混合格式的长期维护策略

- 代码中的正则使用分组 `\d{2}|[2-9a-kmnp-z]{4}` 同时匹配两种格式
- 校验脚本 `check-issue-doc-numbering.ts` 对旧格式检测重复 ID，对新格式检测同日碰撞
- `feature-numbering.md` 中标注「遗留格式」，说明无需迁移

## 未来迁移的触发条件

如果出现以下情况，可重新评估迁移必要性：

- 旧格式文档数量增长到影响代码复杂度（当前正则分组是 O(1) 操作，不构成瓶颈）
- 需要对所有 feature ID 做统一的批量操作（如全局重索引）
- 出现新格式的工具链不兼容问题（当前已排查确认无此风险）

以上情况均未出现，短期内无迁移计划。
