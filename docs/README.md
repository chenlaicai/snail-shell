# Snail Shell 文档目录准则

## 目录定位

`docs` 只存放需要随仓库长期维护的用户手册和 feature 设计文档。

文档读者是 Snail Shell 的使用者和协作 agent。文档必须真实、准确、可执行，避免主观评价、宣传式表述和无法检验的描述。

## 目录结构

```text
docs/
  README.md
  user-manual/
  features/
    YYYY/
      MM/
        DD/
```

## 长期规则入口

长期规则、核心原则、事实基线和模型不变量不再通过 `docs/core` 设计文档生效。

这类内容必须进入最贴近执行边界的长期入口：

1. AI 运行时行为规则进入 `.meta/prompts/`。
2. 独立能力协议、命令和操作步骤进入 `.meta/skills/`。
3. 代码模型、数据协议、runtime 映射和安全边界进入 `src/` 类型、实现、测试和必要 why 注释。
4. 提示词效果评估规则进入 `.meta/prompt-evaluations/`、评估 runner 和相关测试。
5. 已确认的架构取舍进入设计决策库，而不是新增长期设计文档。

feature 文档可以记录本次设计取舍和迁移过程，但不能替代上述长期入口。

## user-manual

`docs/user-manual` 存放面向使用者的长期操作手册。

进入 `user-manual` 的文档必须同时满足：

1. 面向 Snail Shell 的使用者，而不是只面向单次 feature 的实现或检视。
2. 描述可以按步骤执行的安装、配置、接入、日常使用或排障流程。
3. 内容需要随仓库长期维护，并且应与实际代码、配置示例和系统边界保持一致。
4. 不记录单次阶段结论、PR 摘要、临时决策过程或仅对某个 feature 生命周期有效的验收信息。

用户手册可以引用 feature 文档中的设计背景，但不能替代 feature 文档记录需求收敛、设计取舍、改动范围和验证结果。

## features

`docs/features` 按创建日期分目录存放单个 feature 的设计文档，也是该 feature 合入前的需求、设计、验证和范围变化记录。

后续每个 feature 开发前，应先创建一份 feature 文档，再按文档推进实现、验证和 PR。feature 文档可以随该 feature 的需求收敛、设计取舍和检视反馈更新。

feature 文档在对应 PR 合入后即视为历史交付记录，后续 feature 不得二次修改已合入 feature 文档来追写新结论、更新旧范围或让历史记录适配当前实现状态。后续行为、规则或实现发生变化时，必须创建新的 feature 文档记录本次变化；需要长期维护的事实、规则或操作说明，应沉淀到 `user-manual/`、`AGENTS.md`、`.meta/prompts/`、`.meta/skills/`、代码、测试或脚本等长期入口，而不是改写已完成 feature 的历史记录。

feature 文档编号规则：

1. 格式为 `FYYYYMMDDxxxx`。
2. `YYYYMMDD` 使用创建文档当天日期。
3. `xxxx` 为 4 位随机码（字符集 `2-9a-kmnp-z`，排除 0/o/1/l），创建时一次性分配，终身不变。
4. 日期目录格式为 `docs/features/YYYY/MM/DD/`。
5. 文件名格式为 `FYYYYMMDDxxxx-kebab-case-title.md`。
6. 生成随机码后，扫描对应日期目录确认不与已有编号碰撞；碰撞则重新生成。

示例：

```text
docs/features/2026/06/23/F202606238vkw-random-feature-id.md
```

已有的 `FYYYYMMDDNN`（两位顺序递增编号）格式保持不变，无需迁移。

feature 文档应使用以下结构（新建 feature 时复制此模板到 `docs/features/YYYY/MM/DD/FYYYYMMDDxxxx-slug.md`）。各章节按阶段归属分为两类：`[design-time]` 标注的章节在需求收敛与设计阶段（代码前）完成并锁定，进入实现阶段后不得单方面修改；其余章节可在实现和验证阶段填写或更新。`## 核心业务行为` 章节由 AI 在设计阶段根据业务需求起草、人认可后进入实现阶段；实现阶段可修改（新增、修正、删除），须在范围变更记录中说明。

```markdown
---
id: FYYYYMMDDxxxx
title: kebab-case-title
from_ids: []
tags: []
modules: []
doc_kind: spec
---

# FYYYYMMDDxxxx [module] 标题

<!-- [design-time] 以下章节在需求收敛与设计阶段（代码前）完成并锁定 -->
<!-- 进入实现阶段后不得单方面修改，如需变更须通过问题卡片向用户提出并确认 -->

## 背景 [required]

说明为什么需要做这个 feature，以及它解决的真实问题。

## 用户意图锚 [required]

> 以下内容直接引用用户原始表达，架构师不得改写或概括。后续所有阶段以本节为语义保真基准。

| # | 来源 | 用户原话（逐字引用） | 关键修饰语 | 架构师解读 |
|---|------|---------------------|-----------|-----------|
| UA-1 | msg-{id} | 用户原话 | 空间/时序/数量/条件等修饰词 | 架构师的理解，必须覆盖所有修饰语 |

**适用范围**：不是所有需求都需要意图锚。判断标准：用户表达中是否包含可被降维的修饰语（空间、时序、数量、条件、视觉属性）。纯逻辑需求（"当 X 时做 Y"）的行为条目 S1-S5 已足够覆盖。

- **适用**：填写意图锚表，逐字引用用户原话，提取关键修饰语
- **不适用**：标注"不适用"并附客观原因说明（如"本需求为纯重构，无用户表达"），空白 ≠ "不适用"

**关键规则**：
- 用户原话必须逐字引用，不做书面化改写；口语化表达原文照录
- `来源`列记录消息 ID，支持快速定位原始对话
- 架构师解读必须覆盖用户原话中的所有修饰语（空间、时序、数量、条件、视觉属性）
- 意图锚必须在需求对齐结束后、向用户呈现方案前记录
- 用户修改需求时，必须更新意图锚表并在解读列标注修改历史
- 意图锚与 Task Anchor 冲突时，以意图锚为准（用户原话 > 架构师理解）

## 目标 [required]

总导览：回应背景中的问题。多阶段 feature 用 `### P1 —` / `### P2 —` 拆分，每个 Phase 说清楚要达成什么。

**多阶段实施约束**：

如果采用多阶段实施，必须说明：
- 每个阶段的交付物和验证方式
- 阶段之间的依赖关系
- 每个阶段都是可独立验证的完整状态

禁止将一个完整特性拆分为多个独立特性，除非各特性之间有明确的独立边界。

## 非目标 [required]

列出本 feature 明确不处理的范围。

## 核心业务行为 [required]

本 feature 涉及的核心业务行为列表。每条行为是"当 X 时，应该 Y"的形式，描述的是外部可观测行为（输入/输出/状态变化/错误），不是内部实现。

此章节是业务行为的文档化，与测试编写独立。修改系统功能语义的 PR 必须填写此章节（见 developer handbook GATE-3）。

| # | 场景 | 预期行为 | 测试覆盖 |
|---|------|----------|----------|
| B1 | 当 X 时（触发条件和上下文） | 系统应该 Y（具体可观测结果：返回值/状态变化/错误） ← UA-1 | tests/xxx-test.ts::testFunctionName |

列说明：
- **#**：行为编号（B1, B2, ...）
- **场景**：触发条件和上下文，必须包含"当……时"的条件描述，不能只写动作（如"创建 issue"）
- **预期行为**：系统的具体可观测结果，不能只写"成功"或"正确"（如"返回 201 并创建 issue 记录"）。对来源于用户意图锚的行为，在末尾标注 `← UA-n` 追溯关系
- **测试覆盖**：编写测试时填写，格式为"测试文件路径::测试函数名"；不写测试时留空

**追溯规则**：仅对直接来源于用户明确表达的行为标注 `← UA-n`，架构师自行推导的行为不标注，避免虚假追溯。一个 UA 可派生多个 B，一个 B 可追溯多个 UA。

## 设计 [required]

按 Phase 展开详细设计取舍（`### P1 详设` / `### P2 详设`）。

**决策内嵌标记**：当设计中出现关键决策时，在正文决策产生处使用内联标记：

```markdown
> **[Dn]** {结论}。正方：{理由}。反方：{理由}。依据：{依据}
```

`[Dn]` 标记的触发条件（满足以下任一条件即必须标记）：

1. **有正反论点**：存在被否决的替代方案
2. **改变行为语义**：该决策改变了系统的外部可观测行为
3. **限制下游选择**：该决策限制了开发者或审查者的后续选择空间

## 生效路径 [required]

说明本 feature 的规则、约束或工作方式通过哪些长期入口生效，例如代码、配置、`AGENTS.md`、`.meta/prompts`、脚本、CI 或工作流产物要求。

## 设计约束摘要 [required]

从上述设计章节中提取研发阶段必须遵守的关键约束。此节为研发者快速参考入口，避免全文阅读遗漏边界。

### 硬约束（违反即 bug）
- {不得越过的范围限制}

### 设计取舍（不得自行推翻）
- {已确认的设计决策及理由}

### 语义不变量（实现中必须保持为真）
- {持续为真的条件}

### 非目标（不得扩展）
- {明确不处理的范围}

<!-- [design-time] 章节结束 -->

## 改动范围 [required]

列出预计修改或新增的文件、模块或文档。

## 验证 [required]

按 Phase 列出验证方式与标准：`### P1` / `### P2` / `### 通用`，每项用 checkbox `- [ ]`。

当意图锚中包含视觉/空间/动画类修饰语时，验证项必须包含视觉证据（截图/录屏）比对。

## 关联 [required]

类型化的跨 feature 引用：`- **前置/阻塞/相关**: {FYYYYMMDDxxxx}（{说明}）`。

## 未实现说明 [optional]

本 feature 设计范围内但未在本次实现中完成的内容，在 review 阶段如实填写。不可将"未实现"伪装为"约束"或"非目标"。

| 原始设计要求 | 未实现原因 | 用户确认状态 | 后续处理 |
|---|---|---|---|
| ... | ... | 已确认 | 创建新 feature/记录待办/永久放弃 |

> 未实现项必须先经用户确认才能填入此表。未确认的未实现项属于待处理问题，在确认前不得标记为已完成。

## 关键决策记录 [required]

设计章节中 `[Dn]` 内联标记的纯索引。正反论点、决策依据只存在于设计正文的内联标记中，此处仅提供编号、决策点、最终决策和状态的快速查阅。

| # | 决策点 | 最终决策 | 状态 |
|---|--------|----------|------|
| D1 | 决策点描述 | 最终选择的方案 | 设计阶段确认 |

**状态列定义**：
- `设计阶段确认`：架构师在设计阶段做出的初始决策
- `审查阶段修正`：审查者发现设计缺陷后修正的决策（需关联范围变更记录）
- `用户确认`：经用户确认的决策（覆盖前两种状态）

feature 文档不应残留未经确认的问题；如最终决定暂时遗留，必须记录参与决策者、接受该遗留的原因、后续处理条件或跟进方式。

## 风险与缓解 [required]

| # | 风险 | 严重程度 | 影响 | 缓解策略 | 负责方 |
|---|------|----------|------|----------|--------|
| R1 | 风险描述 | 高/中/低 | 影响范围 | 缓解措施 | 角色名 |

## 范围变更记录 [optional]

记录本 feature 在实现或检视过程中发生的目标、非目标、设计、改动范围或验证范围变化，以及变化原因。如涉及 design-time 章节的变更，必须注明已获用户确认。
```

## 根目录规则

`docs` 根目录只允许保留：

1. `README.md`
2. `user-manual/`
3. `features/`

其他文档必须进入 `user-manual` 或 `features`；如果无法判断归属，应先作为 feature 文档沉淀，不应直接放在根目录。
