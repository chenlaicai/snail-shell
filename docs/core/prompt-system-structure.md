# 系统提示词结构规范

## 定位

本文档定义 Snail Shell 系统提示词的组织结构、规则格式和编写规范。它用于判断一条规则应归属到哪个模块、进入提示词文件后应如何表达、如何避免重复和冲突。

本文档是 `.meta/prompts/` 的权威规范。`.meta/README.md` 只描述文件格式和入口边界，两者均以本文档为准。

## 两层模型

系统提示词由两层组成，区别在于生效模式：

| 层 | 前缀 | 生效模式 | 说明 |
|---|---|---|---|
| **Base 层** | `B-` | 始终注入 | AI 身份、不可变契约、系统边界。所有场景都会注入，内容极少变动。 |
| **Scenario 层** | `S-` | 条件注入 | 根据上下文（角色、阶段、任务类型等）按需注入。内部模块平级。 |

两层不是上下级关系，而是"不变"与"可变"的区分。Scenario 层内部的模块之间是平级的，只是触发条件不同。

提示词文件只声明内容（id、title、skill_references），不声明生效条件。生效条件由架子（Frame）统一管理。

## 归属规则

### Base 层

只要一条规则对所有 Snail 底层 AI 都成立，且不依赖 Project、Feature、Stage、Conversation 或 Task，就归入 Base 层。

属于：
1. 用户决策边界。
2. 事实与上下文使用边界。
3. 结构化消息协议。
4. skill reference 的基础使用边界。
5. 知识治理的基础边界。
6. 底层 AI 与宿主运行时交互时的可信边界。

不属于：
1. 当前 Project、Feature、Stage 或 Conversation 的实例事实。
2. 某角色在某 Stage 的行动手册。
3. 后台任务的输入输出格式。
4. 只服务项目推进场景的代码仓、PR、测试或文档规则。

### Scenario 层

只要一组提示词描述某类 AI 调用的上下文结构、任务边界或行为模型，就归入 Scenario 层。场景提示词共享 Base 层，但不重复基础契约。

#### Work Context

只要内容是项目推进当前调用的上下文事实、上下文装配槽位或上下文边界说明，就归入该分类。Work Context 负责让 AI 知道"当前工作处在什么场景、有哪些事实"，但不承载角色行动策略。

#### Stage Role Playbook

只要内容描述某角色在某 Stage 应该如何判断、行动和收口，就归入该分类。角色行为必须绑定 Stage，不维护脱离 Stage 的大段角色行为清单。

#### Task Runtime

只要提示词服务后台任务或专用运行时，而不是面向 Snail 参与的项目推进会话，就归入该分类。

## 文件格式

`.meta/prompts/` 下有两种文件类型：提示词文件（`prompts/` 目录）和架子文件（`frames/` 目录）。

### 提示词文件

每个提示词文件以 YAML frontmatter 开头，后接 Markdown 正文：

```yaml
---
id: S-03
title: 研发者手册
skill_references:
  - id: message-out
    mode: required
    reason: "需要结构化呈现时使用"
---

## 研发者手册

### 职责原则
- R01 规则内容...
```

#### 提示词字段说明

**id**（必填）

模块的稳定唯一标识。格式为 `{layer_prefix}-{module_number}`：
- `B-01` ~ `B-99`：Base 层模块
- `S-01` ~ `S-99`：Scenario 层模块

文件名必须以 `{id}-` 开头并包含简短标题，例如 `S-03-研发者手册.md`。

**title**（必填）

人类可读标题，用于调试、日志和展示。

**skill_references**（可选）

声明需要引用的 skill。只引用能力边界，不复制 skill 正文。

### 架子文件

架子文件是系统提示词的模板，存放在 `frames/` 目录下。架子正文即最终系统提示词的骨架，通过模板标记嵌入提示词内容和条件段落：

```markdown
---
id: F-01
title: 项目推进会话
type: frame
---

## 身份与责任契约

{{prompt:B-01}}

## 知识治理

{{prompt:B-02}}

{{#when:runtimes=claude-code-cli,claude-code-stateful-cli}}
## 运行时边界

{{prompt:B-03}}
{{/when}}

## 项目上下文

{{prompt:S-01}}

{{#when:stage_types=development,review;snails=Implementation Snail}}
## 研发者手册

{{prompt:S-03}}
{{/when}}
```

#### 架子字段说明

**id**（必填）

架子的稳定唯一标识，格式为 `F-{两位数字}`。

**title**（必填）

人类可读标题。

**type**（必填）

固定值 `frame`，用于区分架子文件和提示词文件。

**when**（可选）

架子级别的命中条件，用于架子选择（哪个架子匹配当前上下文）。省略表示无条件命中（默认兜底架子）。支持字段：
- `runtimes`：限定运行时
- `stage_types`：限定阶段类型
- `snails`：限定角色
- `conversation_kinds`：限定会话类型
- `owner_types`：限定会话所有者类型
- `requires_repo`：是否要求代码仓上下文

#### 模板标记语法

**提示词嵌入**：`{{prompt:ID}}`

在架子正文中引用提示词内容。渲染时查找对应提示词文件，将其正文展开到当前位置，skill_references 自动追加。

**条件段落**：`{{#when:field=value1,value2;field2=value3}}...{{/when}}`

当条件满足时渲染该段落，否则整段移除。
- `;` 分隔多个条件字段（AND 关系）
- `,` 分隔同一字段的多个值（OR 关系）
- 支持的字段：`runtimes`, `stage_types`, `snails`, `conversation_kinds`, `owner_types`, `requires_repo`

**变量条件**：`{{#if:variable_name}}...{{/if}}`

当变量非空时渲染该段落。用于运行时动态内容。

**变量替换**：`{{variable_name}}`

与提示词文件中的变量替换一致，架子正文和提示词正文均支持。

### 正文结构

正文使用 Markdown，按以下结构组织：

```markdown
## 模块标题

### 职责原则
- R01 规则内容...

### Development 工作流程
- R02 规则内容...
```

- `##` 为模块主题

Stage Role Playbook 应优先按以下顺序组织 `###` 分组：职责原则、工作流程（可按阶段拆分 Development/Review 等）、专项规则、输出要求。分组顺序服务于运行时判断流程，不要把所有要求堆成一个长行动清单。
- `###` 为模块内的主题分组
- 每条规则以 `- R{number}` 开头，后接规则内容

## 规则格式

### 编号

每条规则有模块内唯一的编号，格式为 `R{两位数字}`：R01, R02, R03, ...

编号在模块内递增，稳定不变。规则被引用时使用 `模块ID-R编号` 格式，例如 `B-01-R03`、`S-03-R15`。

### 规则条目

一条规则的完整格式：

```markdown
- R03 需要用户明确决策时，不得擅自替用户做决定。
- 提问必须指向真实待决策项，选项覆盖可行分支。
```

规则条目的组成：
1. **编号**：`R{number}`，必填
2. **规则内容**：一条或多条 bullet，每条表达一个约束

### 规则粒度

- 一条规则对应一个稳定的约束边界
- 一条规则可以包含多条 bullet，但这些 bullet 必须属于同一约束主题
- 如果两条 bullet 的触发条件、受众或职责不同，应拆成两条规则

### Checklist 编号

Stage Role Playbook 中的 checklist 使用永久编号机制：

- **编号 = 唯一标识**，不表达执行顺序。执行顺序在编号规范说明文本中以 section 名称序列明确写出
- **编号规范说明**使用 `- ` 格式（非 blockquote）
- **新增条目**使用该 checklist 内下一个可用编号，永不重排已有编号
- **删除条目**后编号留空，不复用
- **引用格式**：`模块ID-checklist #编号`，如 `S-03-checklist #3`
- **粗体条目**（如 `**1. ...**`）标记关键检查点

## 内容密度原则

### 只写行为指令

提示词正文只包含 AI 必须执行的行为规则。以下内容不应出现在提示词正文中：
- 理念阐述（"为什么要这样做"）→ 移入知识库或文档
- 设计背景 → 移入 feature 文档或 `docs/core/`
- PR 说明或验收记录 → 移入 PR 或 feature 文档
- 说服性论述 → 不属于提示词

### 消除重复

一条规则只能有一个主归属。其他位置如需提及，只能引用（`→ B-01-R03`），不复制完整规则。

### 一条 bullet 一个约束

```markdown
# 避免：一条 bullet 承载多个约束
- 收到检视意见后，先理解问题本质，再判断修复方式，然后更新 PR 并在 PR 上回复评论。

# 推荐：拆成多条
- 收到检视意见后，先理解问题指向的层级（表层症状、业务语义、系统模型）。
- 判断修复方式时，必须考虑对既有场景的回归影响。
- 修复完成后，在 PR 上回复评论说明处理结果。
```

### 写可执行判断，不写抽象口号

```markdown
# 避免
- 要认真负责。
- 要充分考虑各种情况。

# 推荐
- 事实不足时，先查证或提出真实待决策问题。
- 修改既有逻辑前，先理解原逻辑服务的场景和约束。
```

## 渲染与装配

### 架子选择

运行时通过 `selectFrame(context)` 选择架子。选择规则：

1. 按架子 frontmatter `when` 条件的具体度降序排列（条件越多越靠前）
2. 无 `when` 的架子作为默认兜底，排在最后
3. 选择第一个 `when` 条件全部匹配当前上下文的架子

### 模板渲染

选中架子后，按以下顺序渲染架子正文：

1. **展开 prompt 引用**：扫描 `{{prompt:ID}}`，查找提示词文档，将其内容展开到当前位置
2. **条件段落过滤**：评估 `{{#when:...}}...{{/when}}` 块，移除不满足条件的段落
3. **变量条件过滤**：评估 `{{#if:var}}...{{/if}}` 块，移除变量为空的段落
4. **变量替换**：替换所有 `{{variable}}` 占位符
5. **清理**：移除多余空行

Task 提示词通过独立的架子（如 F-03、F-04）组装，不与项目推进会话混合。

## 文档编写规范

### 编写目标

系统提示词不是给人阅读的普通制度文档，也不是把完整设计文档直接塞进模型上下文。提示词文档必须优先服务运行时执行效果。

编写系统提示词时应同时满足：
1. 模型能快速识别这段提示词的作用。
2. 模型能知道什么时候触发规则。
3. 模型能区分必须遵守的不变量、可选择的判断流程和禁止行为。
4. 后续维护者能判断规则为什么放在这里，以及什么时候应拆分、合并或删除。

### 表达方式

规则应写成模型可以执行的判断或行动，而不是抽象价值判断。

一条 bullet 应只表达一个稳定约束。若一句话同时包含背景、条件、例外、行动和原因，应拆成多条或改成小节。

推荐：
1. 先写触发条件。
2. 再写必须行动。
3. 必要时单独写例外或原因。

系统提示词正文应以规则为主。背景说明只保留理解规则所需的最短内容。

提示词文件中不应出现：
1. 单次 feature 的讨论过程。
2. PR 解释或验收记录。
3. 为了说服人类评审而写的大段论证。
4. 与运行时无关的历史原因。

### 规则类型

**不变量**：任何命中该提示词的调用都必须保护的边界。使用明确强制语气。

**触发式流程**：模型在某类输入出现时应如何判断和行动。以条件开头。

**禁止项**：压制模型常见错误。每个禁止项对应明确的误行为。

**输出契约**：外部协议、格式或可追溯要求。不要把内部思考过程写成输出契约。

### 文件粒度

一个提示词文件应有单一职责。出现以下情况时应拆分：
1. 同一文件同时描述基础可信边界、场景上下文和角色行动。
2. 同一文件中既有事实注入模板，又有行为要求。

出现以下情况时应合并：
1. 多个文件只是重复强调同一规则。
2. 文件标题不同，但触发条件和行动结果相同。
3. 拆分后需要模型跨多个短文件才能理解一个完整判断流程。

### 边界

`docs/core/prompt-system-structure.md` 同时定义提示词规则放在哪里，以及规则进入提示词文件后如何写。不要为系统提示词规范再新增平行 core 文档。

`.meta/README.md` 只描述 `.meta/prompts/` 的文件格式、编号和入口边界；不要在 README 中复制本文档完整规范。

## 检查清单

新增或调整提示词模块前，必须检查：

1. **归属**：这条规则是否已有主归属？是否会造成重复或漂移？
2. **层**：这条规则是否对所有场景成立？是 → Base 层；否 → Scenario 层。
3. **模块**：这条规则的受众、触发条件和职责边界是否与现有模块一致？一致 → 合入；不一致 → 新建模块。
4. **架子**：提示词是否已被正确的架子引用？生效条件是否在架子中正确配置？
5. **密度**：正文是否只包含行为规则？是否混入了理念、背景或论述？
6. **粒度**：一条 bullet 是否只表达一个约束？是否存在过长的复合 bullet？
7. **重复**：是否与其他模块的规则重复？重复 → 合并到主归属，其他位置引用。
8. **可执行性**：规则是否写成了可执行的判断或行动？还是抽象口号？
