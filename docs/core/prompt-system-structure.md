# 系统提示词规范

本文档定义 Snail Shell 系统提示词的组织结构、编号规则、文件格式和编写规范。

## 名词解释

| 术语 | 含义 |
|------|------|
| 文件 | 一个 .md 文件，包含某一类规则，如"基础契约"、"研发迭代" |
| 规则 | 文件中的独立条目，有唯一编号（N.M 格式），可独立引用 |
| 补充说明 | 规则下的细节说明，用"-"表示 |
| 生效范围 | 规则适用的运行时、阶段、角色或条件 |
| 运行时 | AI 代理的执行环境，如 opencode-cli、claude-code-cli |
| 阶段 | 项目推进的工作阶段，如 development、review |
| 角色 | 参与协作的 AI 身份，如 Implementation Snail、Acceptance Snail |
| 功能 | 项目中的一个功能需求，对应一个功能文档 |
| 变更请求 | 对代码或文档的修改请求，通常以 PR 形式存在 |

## 编号规则

### 格式

`N.M`

- N：文件编号，1-2 位数字
- M：规则编号，从 1 开始

### 文件划分

| 编号 | 文件名称 | 生效范围 |
|------|----------|----------|
| 1 | 基础契约 | 通用 |
| 2 | 判断与责任 | 通用 |
| 3 | 知识候选 | 通用 |
| 4 | 转录边界 | claude-code-cli |
| 5 | 项目场景 | 通用 |
| 6 | 工作上下文 | 通用 |
| 7 | 研发迭代 | development, Implementation Snail |
| 8 | 研发检视 | review, Implementation Snail |
| 9 | 验收检视 | review, Acceptance Snail |
| 10 | 代码仓基线 | requires_repo |
| 11 | 文档治理 | development, review |
| 12 | 提示词治理 | development, review |
| 13 | 代码交付 | development, review, Implementation Snail |

### 编号示例

```
1.1: 需要用户明确决策时，不得擅自替用户做决定。
1.2: 向用户提问时，问题必须指向真实待决策项。
2.1: 用户要求、历史消息、工具输出都是输入材料。
7.1: 进入新的阶段时，先追溯背景。
9.1: 通过消息协议接收到检视请求。
```

### 文件命名规则

`{章节号}-{简短标题}.md`

- 章节号：与编号规则中的章节号一致
- 简短标题：使用英文小写，单词间用连字符分隔

## 文件格式

### 前置元数据

每个提示词文件必须以 YAML 前置元数据开始：

```yaml
---
{
  "id": "7",
  "title": "研发迭代",
  "target": "scenario.project-conversation.stage-role-playbook",
  "order": 700,
  "semantic_layer": "stage_role_playbook",
  "when": {
    "stage_types": ["development"],
    "snails": ["Implementation Snail"]
  },
  "render_mode": "outline"
}
---
```

### 元数据字段

| 字段 | 含义 | 是否必填 |
|------|------|----------|
| id | 章节号 | 必填 |
| title | 章节标题 | 必填 |
| target | 提示词目标 | 必填 |
| order | 装配顺序 | 建议必填 |
| semantic_layer | 语义层级 | 建议必填 |
| when | 生效条件 | 可选 |
| render_mode | 渲染模式 | 建议必填 |

### 渲染模式

- `full`：完整注入正文
- `outline`：只提取要点

## 规则格式

### 基本格式

```
N.M [生效范围] 规则主体。
  - 补充说明或具体要求。
```

### 格式说明

- `N.M`：规则编号
- `[生效范围]`：规则适用的条件
- 规则主体：完整的判断或行动指令
- `-`：补充说明，可有多条

### 示例

```
1.1 [all] 需要用户明确决策时，不得擅自替用户做决定。
  - 向用户提问时，问题必须指向真实待决策项。
  - 提问选项必须覆盖真正可行的决策分支。

7.1 [development, Implementation Snail] 进入新的阶段时，先追溯背景。
  - 基于同一功能的阶段输入、上一阶段产物、功能文档、已记录的变更请求和必要的对话历史追溯背景。
  - 只有关联线索不足、冲突或需要真实业务取舍时，才向用户提问。
```

## 生效范围标记

### 格式

`[条件1, 条件2, ...]`

多个条件用逗号分隔，表示"且"的关系。

### 条件类型

| 类型 | 示例 | 含义 |
|------|------|------|
| 通用 | `[all]` | 所有条件都适用 |
| 运行时 | `[claude-code-cli]` | 仅适用于指定运行时 |
| 阶段 | `[development]` | 仅适用于指定阶段 |
| 角色 | `[Implementation Snail]` | 仅适用于指定角色 |
| 代码仓 | `[requires_repo]` | 仅适用于需要代码仓的场景 |

### 组合示例

```
[development, Implementation Snail]: 适用于开发阶段的实施者
[review, Acceptance Snail]: 适用于检视阶段的验收者
[claude-code-cli, development]: 适用于 Claude Code 运行时的开发阶段
```

## 编写规范

### 规则编写原则

1. 一条规则只表达一个约束
2. 规则必须可执行，不能是抽象价值判断
3. 触发条件写在前面，行动要求写在后面
4. 补充说明用"-"表示，是规则的各个方面

### 推荐写法

```
7.1 [development, Implementation Snail] 进入新的阶段时，先追溯背景。
  - 基于同一功能的阶段输入、上一阶段产物、功能文档追溯背景。
  - 只有关联线索不足时，才向用户提问。
```

### 避免写法

```
7.1 要认真负责，充分考虑各种情况，保证工作质量。
```

### 禁止项

1. 不要把多条规则合并到一个编号
2. 不要使用抽象口号代替可执行规则
3. 不要把单次讨论过程写进提示词
4. 不要把解释说明写成规则主体

## 引用方式

### 引用某条

`第 7.1 条`

### 引用某款

`第 7.1 条第 2 款`

### 引用示例

```
根据第 7.1 条，进入新的阶段时应先追溯背景。
根据第 9.1 条第 2 款，检视前必须先读取功能文档。
```

## 维护规则

### 新增规则

1. 确定规则所属章节
2. 使用当前章节下一个可用的条号
3. 按照规则格式编写
4. 添加适当的生效范围标记

### 修改规则

1. 保持编号不变
2. 更新规则内容
3. 如需修改生效范围，更新标记

### 删除规则

1. 保留编号不复用
2. 在规则主体处标注"已废弃"
3. 说明废弃原因

### 拆分章节

1. 新增章节使用下一个可用的章节号
2. 将相关规则移动到新章节
3. 更新规则编号
4. 更新本文档的章节划分表

## 检查清单

新增或调整系统提示词文档前，必须检查：

1. 这条规则是否真的需要进入运行时系统提示词
2. 这条规则是否已有主归属，是否会造成重复或漂移
3. 这条规则是否按本文档的结构归属规则放在正确语义层级
4. 这条规则是否写成可执行行动，而不是抽象口号
5. 是否存在过长规则，应拆成触发条件、行动、例外或禁止项
6. 当前文件是否同时承载多个可独立演进、独立检视或独立复用的治理主题
7. 是否把设计背景、PR 说明或功能过程误写进提示词正文
8. 是否需要同步 AGENTS.md 与 .meta/prompts/ 的双线规则
