# 知识生效生命周期

## 定位

知识系统负责把对话、实现、检视和验证中出现的可复用结论转化为可治理、可追溯、可更新的系统能力。知识不是阶段产物的替代品，也不是未经审批即可影响 agent 行为的旁路配置。

## 生命周期

1. 提取为候选：agent 识别到长期规则、偏好、决策、失败教训、术语、流程或开放治理问题后，创建 `candidate` 知识并保留来源。
2. 人工审批：候选知识经人工确认后才能进入 `active`，审批时可以调整范围、类型、治理等级和正文。
3. 选择生效途径：审批后的知识必须明确是动态生效、静态生效，还是仅保留为可搜索参考。
4. 记录使用反馈：每次通过 prompt、manual reference、search、skill、tool 或 checker 使用知识时，应尽量保留使用记录、结果和反馈。
5. 更新或退出：知识失效、被替代或造成错误反馈时，应通过新候选、更新 PR、废弃、归档或 supersede 路径处理，不能静默改写历史来源。

## 生效途径

### 动态生效

动态生效发生在运行时，典型方式包括：

1. 系统提示词注入：按 project、feature、stage、snail 范围匹配已审批知识，并记录 `prompt_injection` 使用。
2. 手动引用：agent 搜索或读取知识后，在当前任务中作为参考使用，并记录 `manual_reference` 或 `search_result`。

动态生效适合偏好、规则提示、阶段上下文提醒和仍需要快速调整的工作方式。动态生效不得绕过范围、治理等级和使用策略，也不得把候选、拒绝、废弃或跨范围知识注入上下文。

### 静态生效

静态生效发生在仓库长期入口或外部运行能力中，典型方式包括：

1. Skill：把可复用操作协议、工作流或领域能力沉淀到 `.meta/skills/<skill-name>/SKILL.md`。
2. Prompt：把稳定身份、场景边界或角色职责沉淀到 `.meta/prompts/`。
3. MCP 或 tool：把需要外部能力、自动化操作或稳定接口调用的知识沉淀到工具配置、脚本或服务接入中。
4. Checker：把必须自动验证的规则沉淀到测试、lint、CI、脚本或专用检查器中。
5. 文档和代码：把长期模型、用户操作、系统不变量或业务规则沉淀到 `docs/core`、`user-manual`、`AGENTS.md`、代码和脚本中。

静态生效通常需要代码审查和 PR 合入。知识审批只能确认“这条知识值得生效”，不能替代修改长期入口所需的设计、实现、验证和检视。

## 使用策略

`knowledge_usage_policy` 描述已审批知识的反哺策略：

1. `allow_prompt_injection` 与 `prompt_mode` 控制动态系统提示词注入。
2. `skill_visibility` 记录该知识应被哪些 skill 关注或引用。
3. `tool_visibility` 记录该知识与哪些 MCP/tool 能力相关。
4. `checker_binding` 记录该知识是否已绑定到自动验证入口。
5. `stage_types`、`snail_names`、`priority` 和 `token_budget` 约束动态注入和推荐顺序。

这些字段是治理策略，不等同于静态入口已经落地。静态入口是否已落地，应以仓库 diff、PR、测试、脚本或配置为准。

## 反馈与更新

知识使用记录应服务于后续治理：

1. 如果知识经常被动态注入且稳定有效，应评估是否转为 skill、prompt、checker、文档或代码。
2. 如果知识只在少量任务中偶发使用，可以保持为可搜索参考或手动引用。
3. 如果知识导致错误行为，应废弃、归档或创建替代知识，并在来源或 PR 中说明原因。
4. 如果静态入口已经承载某条规则，后续不应再用重复候选制造审批噪音；应维护对应长期入口。
