# 知识闭环飞轮生命周期设计

## 文档定位

本文档定义 Snail Shell 知识闭环飞轮的核心生命周期模型。

后续凡是涉及以下内容的设计、实现、测试、评审与重构，都必须以本文档为准：

1. 知识候选识别与待审批队列。
2. 知识审批、拒绝、落地和变更请求。
3. 知识文档权威源。
4. SQLite 运行时投影、搜索索引和使用记录。
5. prompt 注入、skill、工具或检查器引用知识的边界。
6. 知识中心 UI、API 和状态展示。
7. 知识更新、停用、替换、归档和审计追溯。

本文档只定义长期模型、边界和不变量，不规定单个 feature 的实现节奏，不替代具体 schema、API、脚本或 UI 设计。

## 裁决优先级

当不同信息源对知识生命周期给出不同说法时，裁决优先级固定如下：

1. 本文档定义的核心原则、生命周期、状态语义和边界。
2. 与本文档一致的 `docs/knowledge` 规范、TypeScript 类型、数据库 schema 和测试。
3. 其他系统文档和用户手册。
4. 历史 feature 文档、PR 说明、临时讨论结论和旧注释。

如果实现与本文档冲突，必须修正实现或更新本文档，不能通过局部兼容逻辑维持两套知识模型。

## 术语约定

1. `知识`
   表示经过 Snail Shell 工作过程沉淀出的可复用规则、偏好、设计决策、事实、经验、术语或开放治理问题。
2. `候选知识`
   表示已被 agent 或系统识别、但尚未人工审批和仓库落地的知识。
3. `文档知识`
   表示已经进入仓库文档权威源的长期知识。
4. `运行时投影`
   表示系统从文档权威源同步到 SQLite 的查询、搜索和注入视图。
5. `变更请求`
   表示一次知识新增、更新、停用、替换、归档或 prompt 策略调整的可追溯工作单。
6. `prompt 注入`
   表示系统根据知识范围、策略和当前上下文，将知识作为 AI 输入的一部分注入。
7. `生效`
   表示知识已经进入当前运行时投影，并满足使用策略，能够被搜索、展示或注入消费。

## 核心原则

### 1. 知识是系统资产，不是单次运行数据

知识表达 Snail Shell 长期行为、约束和经验。已批准并持续有效的知识必须能通过仓库、PR、review 和 Git 历史追溯，不能只存在于本地 SQLite。

### 2. 文档是长期权威源

长期生效知识的权威源必须是仓库中的知识文档。数据库中的 `active` 状态只能来自文档同步结果，不能作为长期权威事实本身。

### 3. 数据库是运行时投影和工作流存储

SQLite 负责保存候选队列、变更请求、运行时投影、搜索索引、使用记录和审计事件。它可以提升运行效率和承载工作流状态，但不能绕过文档权威源让知识长期生效。

### 4. 候选不直接生效

候选知识即使由 agent 自动提炼，也只能进入待审批队列。人工批准候选也不等于运行时生效；批准只允许进入文档落地流程。

### 5. PR 合入不等于运行时生效

知识文档 PR 合入只表示知识进入目标分支。当前运行中的 Snail Shell 必须基于包含该文档的仓库版本启动，并完成知识文档同步后，知识才进入运行时生效状态。

### 6. 使用反馈不直接改写权威源

知识被注入、引用、命中、忽略或产生反馈时，应记录为使用事实。使用事实可以触发新的候选或变更请求，但不能直接修改已生效知识文档。

### 7. 停用必须表达真实语义

停止 prompt 注入、标记过时、被新知识替代和归档是不同语义，不能都用删除数据库记录表达。

### 8. 每个生命周期动作必须可追溯

知识从来源消息到候选、审批、文档 PR、review 修改、合入、同步、使用和后续演进，都必须保留足够的来源和状态记录。

## 分层模型

知识闭环飞轮由七层组成：

1. 观察层：agent、工具、检视、用户反馈和系统事件中出现可复用知识。
2. 候选层：把可复用知识写入待审批队列，状态仍是运行态数据。
3. 审批层：人工确认候选是否值得长期保留，并决定范围、类型、治理等级和来源。
4. 文档权威层：通过仓库文档和 PR review 固化长期知识本体及 prompt 策略。
5. 运行时投影层：启动同步器把文档知识同步到 SQLite，供查询、搜索和注入使用。
6. 使用反馈层：记录知识何时被注入、引用、命中、忽略或产生人工反馈。
7. 演进治理层：基于反馈和系统变化发起更新、停用、替换或归档。

层级约束：

1. 上层使用不能直接绕过下层权威源。
2. 运行时投影可以重建；文档权威源不能由投影反向自动覆盖。
3. 候选层和使用反馈层可以产生新的变更请求，但不能直接修改文档权威层。

## 核心实体

### KnowledgeItem

`KnowledgeItem` 表示一条知识在系统中的统一记录。它可以是候选、待文档落地、文档同步后的运行时投影，或历史保留记录。

核心字段语义：

| 字段 | 含义 |
| --- | --- |
| `id` | 知识稳定 ID。 |
| `kind` | 知识类型，如 rule、preference、decision、fact、procedure、open_question。 |
| `scope_type` / `scope_ref` | 知识适用范围。 |
| `status` | 候选或文档状态。 |
| `governance_level` | 治理等级，用于表达规则强度和审批要求。 |
| `title` / `content` / `rationale` | 知识标题、正文和保留理由。 |
| `document_path` / `document_hash` | 文档权威源路径和同步 hash。 |
| `runtime_state` | 当前运行时是否已生效。 |

约束：

1. 对文档知识，`title`、`content`、`rationale`、长期 `status` 和 prompt 策略必须来自文档同步。
2. 对候选知识，数据库记录可以作为审批前事实来源，但不能进入 prompt 注入。
3. 数据库中的历史 `active` 如果没有文档来源，不得被视为当前生效知识。

### KnowledgeSource

`KnowledgeSource` 表示知识来源，可指向消息、PR、review 评论、测试失败、外部事实或其他可审计输入。

约束：

1. 候选创建时应记录最小可追溯来源。
2. 文档知识必须保留来源摘要，避免长期规则脱离产生语境。
3. 来源记录不替代知识正文；知识正文必须是可长期复用的抽象结论。

### KnowledgeUsagePolicy

`KnowledgeUsagePolicy` 表示知识如何进入 prompt、skill、工具或检查器。

核心字段包括：

1. 是否允许 prompt 注入。
2. 注入模式，如 none、summary、full、reference_only。
3. 适用 stage、snail、工具或检查器。
4. 优先级和 token 预算。

约束：

1. 对文档知识，使用策略属于文档权威源的一部分。
2. 仅停止 prompt 注入时，不应把知识状态改成 deprecated；应调整 usage policy。
3. prompt 注入必须同时满足知识处于运行时 active、文档状态允许使用、策略允许注入和当前上下文匹配。

### KnowledgeChangeRequest

`KnowledgeChangeRequest` 表示一次知识文档变更工作单。

它覆盖以下变更类型：

1. 新增知识。
2. 更新知识。
3. 停用知识。
4. 替换知识。
5. 归档知识。
6. 调整 prompt 策略。

变更请求必须记录：

1. 请求类型和请求状态。
2. 目标知识 ID 和目标文档路径。
3. PR 分支、worktree、PR URL、commit、merge commit。
4. 预期文档 hash 和已同步文档 hash。
5. 运行时状态和错误信息。

### KnowledgeUse

`KnowledgeUse` 表示一次知识使用事实。

使用事实可以记录：

1. 哪条知识被注入或引用。
2. 发生在哪个 conversation、stage 和 snail。
3. 使用类型与结果。
4. 用户、agent 或系统反馈。

约束：

1. 使用事实不得直接修改知识正文或文档状态。
2. 使用事实可以作为新候选或变更请求的来源。

## 状态语义

### 候选状态

| 状态 | 语义 |
| --- | --- |
| `candidate` | 待人工审批，不进入 prompt 注入。 |
| `rejected` | 已拒绝，保留来源和拒绝理由，不进入落地流程。 |
| `pending_document` | 已批准进入文档落地流程，但尚未运行时生效。 |

### 文档状态

| 状态 | 语义 |
| --- | --- |
| `active` | 文档层当前有效；是否注入还要看运行时状态和使用策略。 |
| `deprecated` | 已过时，保留历史，不进入 prompt 注入。 |
| `superseded` | 已被其他知识替代，保留演进链路，不进入 prompt 注入。 |
| `archived` | 已归档，保留审计，不作为有效知识使用。 |

### 变更请求状态

| 状态 | 语义 |
| --- | --- |
| `draft` | 请求已创建但尚未进入 PR 工作。 |
| `in_progress` | 正在生成文档、创建 PR 或处理 review。 |
| `completed` | 对应文档已合入并完成运行时同步。 |
| `cancelled` | 人工取消，不再继续。 |
| `failed` | 自动化或同步失败，需要人工处理。 |

### PR 状态

| 状态 | 语义 |
| --- | --- |
| `none` | 尚未创建 PR。 |
| `open` | PR 已创建，等待 review 或修改。 |
| `changes_requested` | PR 检视要求修改。 |
| `approved` | PR 已通过 review，但尚未合入。 |
| `merged` | PR 已合入目标分支。 |
| `closed` | PR 未合入关闭。 |

### 运行时状态

| 状态 | 语义 |
| --- | --- |
| `inactive` | 当前运行时未生效。 |
| `pending_restart` | 文档已合入或已变更，但当前运行时尚未同步到该版本。 |
| `active` | 当前运行时已同步并可按策略使用。 |
| `failed` | 同步或校验失败。 |

运行时状态是当前进程事实，不是文档权威源事实。系统重启、代码版本变化或同步失败都可能改变运行时状态。

## 知识全生命周期

### 总流程

一条知识从产生到演进的标准流程如下：

1. 工作过程中出现可复用规则、偏好、事实、设计决策、失败教训、术语或开放问题。
2. agent 判断其具备长期复用价值，并创建候选知识。
3. 候选知识进入 SQLite 待审批队列，状态为 `candidate`。
4. 人工审批候选，确认是否保留、适用范围、类型、治理等级和来源。
5. 拒绝的候选转为 `rejected`，生命周期结束但保留审计。
6. 批准的候选转为 `pending_document`，并创建 `KnowledgeChangeRequest(type = create)`。
7. 系统生成待 review 文档草稿。
8. 系统基于最新目标分支创建隔离分支和 PR，把知识文档提交到仓库权威源目录。
9. PR review 过程中可以修改知识正文、范围、策略、来源和状态。
10. PR 合入后，知识进入仓库目标分支，但当前运行时仍可能是 `pending_restart`。
11. 系统更新到包含该文档的版本并启动。
12. 启动同步器扫描知识文档、校验 frontmatter 和正文、计算 hash，并同步到 SQLite 投影。
13. 同步成功后，变更请求进入 `completed`，运行时状态进入 `active` 或对应非注入状态。
14. prompt 装配、skill、工具、检查器、搜索和知识中心基于运行时投影消费知识。
15. 每次注入、引用、命中、忽略或反馈记录为 `KnowledgeUse`。
16. 使用反馈、检视意见或系统变化触发新的候选或变更请求。
17. 后续通过更新、停用、替换或归档 PR 演进知识。

### 生命周期边界

| 阶段 | 权威来源 | 可执行动作 | 是否可进入 prompt 注入 |
| --- | --- | --- | --- |
| 观察 | 对话、PR、测试、工具、用户反馈 | 判断是否值得提炼 | 否 |
| 候选 | SQLite 候选记录 | 编辑、补充来源、审批、拒绝 | 否 |
| 待文档落地 | SQLite 变更请求和草稿 | 创建 PR、处理 review | 否 |
| 文档已合入 | Git 仓库目标分支 | 等待部署和启动同步 | 否 |
| 运行时已同步 | 文档同步后的 SQLite 投影 | 搜索、展示、注入、记录使用 | 是，需满足策略 |
| 演进中 | 新变更请求和 PR | 更新、停用、替换、归档 | 旧版本按当前运行时状态继续，直到新版本同步 |

## 典型流程

### 新增知识

新增知识必须走以下流程：

1. 创建候选。
2. 人工审批。
3. 创建 `create` 变更请求。
4. 生成文档草稿。
5. 创建知识文档 PR。
6. review 修改并合入。
7. 系统重启同步。
8. 进入运行时投影。

禁止批准候选时直接把数据库记录改为长期 `active`。

### 更新知识

更新知识用于修改正文、范围、治理等级、来源或使用策略。

流程：

1. 基于当前文档知识创建 `update` 或 `prompt_policy_update` 变更请求。
2. 修改对应知识文档。
3. 通过 PR review 合入。
4. 重启同步后替换运行时投影。

约束：

1. 运行时投影不能直接编辑文档托管知识。
2. review 中多次修改文档是正常生命周期，必须更新 commit、hash 和事件记录。

### 停用知识

停用必须先判断真实意图：

1. 仅不再注入 prompt：保持文档状态为 `active`，修改 `KnowledgeUsagePolicy` 为不允许注入。
2. 知识已过时：把文档状态改为 `deprecated`，说明过时原因。
3. 知识被新规则替代：旧知识改为 `superseded`，新知识记录替代关系。
4. 知识只需历史保留：改为 `archived`。

禁止通过删除 SQLite 投影来表达停用语义。

### 替换知识

替换知识必须同时表达旧知识和新知识关系：

1. 新知识通过新增流程进入文档权威源。
2. 旧知识通过 `supersede` 变更请求标记为 `superseded`。
3. 文档中必须能追溯替代关系和替代原因。
4. 运行时同步后，旧知识退出 prompt 注入，新知识按策略进入使用。

### 归档知识

归档用于保留审计但不再作为有效知识使用。

流程：

1. 创建 `archive` 变更请求。
2. 修改文档状态为 `archived` 并记录归档原因。
3. PR 合入并同步后，运行时投影保留历史但不参与注入。

## 文档权威源

长期知识文档必须满足：

1. 每条知识有稳定 ID。
2. 机器可读字段与人类可读正文共存。
3. 文档状态、范围、类型、治理等级、来源和 prompt 策略可审查。
4. 变更通过 PR review 和 Git 历史追溯。
5. 文档不保存运行时使用次数、最近注入时间或搜索索引。

文档权威源应表达：

1. 知识是什么。
2. 为什么值得长期保留。
3. 来源是什么。
4. 适用于哪里。
5. 是否允许进入 prompt，以及如何进入。
6. 是否替代或被替代。

文档权威源不表达：

1. 当前进程是否已经同步。
2. 当前数据库搜索索引内容。
3. 使用次数、最近命中时间或注入结果。
4. PR 自动化的临时失败日志。

---

## 运行时同步

启动同步器负责把文档权威源投影到 SQLite。

同步流程：

1. 扫描知识文档目录。
2. 排除待 review 草稿、README 和非知识文档。
3. 解析 frontmatter 和正文。
4. 校验必填字段、状态、范围、类型和 prompt 策略。
5. 计算文档 hash。
6. upsert `KnowledgeItem`。
7. 同步来源和使用策略。
8. 重建或更新搜索索引。
9. 对本次扫描未出现的旧文档投影执行未生效收敛。
10. 回填变更请求的文档 hash、PR 状态和运行时状态。

同步不变量：

1. 同步必须是从文档到投影的单向过程。
2. 没有文档来源的历史 active 数据不得进入 prompt 注入。
3. 待 review 草稿不得进入运行时 active 投影。
4. 文档 hash 表示当前运行代码仓中被扫描到的最终内容，不等于 PR 创建时的初始草稿 hash。
5. 同步失败必须保留错误状态，不能静默使用旧投影假装成功。

---

## Prompt 注入边界

知识进入 prompt 必须同时满足：

1. 文档状态为 `active`。
2. 运行时状态为 `active`。
3. 使用策略允许 prompt 注入。
4. 当前 Project、Feature、Stage、Conversation、Snail 或工具上下文匹配知识范围。
5. token 预算和优先级规则允许进入本次上下文。

禁止以下做法：

1. 从候选队列直接注入。
2. 从无文档来源的历史数据库 active 记录直接注入。
3. 忽略运行时同步状态，仅因 PR 合入就注入。
4. 把使用反馈临时拼接进长期知识正文。

---

## UI 与 API 边界

知识中心和 API 必须区分以下事实：

1. 候选状态：是否等待审批、已拒绝或等待文档落地。
2. 文档状态：active、deprecated、superseded、archived。
3. PR 状态：none、open、changes_requested、approved、merged、closed。
4. 运行时状态：inactive、pending_restart、active、failed。
5. 使用策略：是否允许 prompt 注入以及适用范围。

对文档托管知识：

1. API 不得直接修改数据库中的知识正文、长期状态或 prompt 策略。
2. UI 应引导创建变更请求和 PR。
3. UI 可以展示运行时投影和使用记录，但必须标明其不是权威源。

对候选知识：

1. API 可以编辑候选字段、补充来源、拒绝或发起审批。
2. 审批通过后只能进入文档落地流程。

## 审计与追溯

每条长期知识至少需要追溯到：

1. 原始来源，如消息、PR、review 评论、测试失败或外部事实。
2. 创建候选的 agent 或系统动作。
3. 审批人和审批时间。
4. 文档 PR URL、分支和 commit。
5. review 修改记录。
6. 合入 commit。
7. 运行时同步 hash 和同步时间。
8. 后续使用事实和反馈。
9. 更新、停用、替换或归档原因。

追溯记录的目标不是还原所有临时对话，而是让未来维护者能判断知识为何存在、为何生效、何时改变、如何安全修改。

---

## 后续拆分实现边界

PR #136 的完整目标应拆成多个可审查 feature。拆分时必须保持本文档定义的生命周期不变量。

建议拆分顺序：

1. 文档权威源格式与 `docs/knowledge` 规范。
2. 数据库 schema 与运行时投影字段。
3. 候选审批到变更请求的状态流转。
4. 知识文档 PR 创建脚本和仓库上下文记录。
5. 启动同步器和历史 active 收敛。
6. prompt 注入过滤和使用记录。
7. 知识中心 UI 与 API 边界。
8. 更新、停用、替换、归档流程。

拆分约束：

1. 不能先实现绕过文档权威源的 active 生效捷径。
2. 不能让候选审批直接改变 prompt 注入结果。
3. 不能把 PR 合入误标为运行时 active。
4. 不能让 UI/API 对文档托管知识执行数据库直改。
5. 每个拆分 PR 都必须说明自己覆盖生命周期中的哪一段，以及未覆盖段如何保持安全不生效。

## 合规要求

任何知识相关改动要被视为合规，必须同时满足以下条件：

1. 说明改动作用于知识生命周期的哪一层。
2. 不破坏文档权威源与运行时投影的边界。
3. 不让候选、草稿、未合入 PR 或未同步文档进入 prompt 注入。
4. 保留必要来源、审批、PR、同步和使用追溯。
5. 对更新、停用、替换和归档使用正确状态语义。
6. 测试或验证覆盖新增场景、既有成功路径、边界路径和失败路径。
