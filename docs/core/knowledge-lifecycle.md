# 知识闭环飞轮生命周期设计

## 文档定位

本文档定义 Snail Shell 知识从工作中被自动识别，到为每条候选启动知识治理 feature，再由 Snail 与用户共同判断其去向的完整流程。

本文档重点定义原则性流程和治理边界，不定义具体数据库 schema、UI 组件、脚本参数、迁移方案或单个 feature 的实现计划。后续知识中心、系统提示词、feature 工作流、prompt 注入或检视规则相关改动，都必须以本文档为准。

## 核心模型

知识闭环飞轮的核心不是“候选知识自动生效”，也不是“知识中心先批量审批再选择是否治理”。核心模型是：

1. Snail 在工作过程中自动识别可复用知识并提交候选。
2. 每一条候选知识都启动一个知识治理 feature。
3. 知识治理 feature 先完成入口校验，判断候选是否具备继续治理价值，或是否应关闭、合并、延后。
4. 通过入口校验后，Snail 与用户判断是否已有重复或相关知识。
5. 如果已有重复或相关知识，本次治理就是负反馈场景：必须分析旧知识最终去了哪里、为什么没有生效、需要如何修正。
6. 如果没有重复或相关知识，本次治理就是新增知识审视场景：必须分析这条候选是否值得保留、应如何抽象、应落到哪里。
7. 治理 feature 的结果可以是一个结论，也可以是一个 PR，具体形式由 Snail 与用户在该 feature 中共同决定。
8. 无论结果是结论还是 PR，都必须回写本条候选知识的最终去向。

知识中心负责记录候选、启动治理 feature、保存裁决去向和帮助后续查重；它不直接替代 Snail 与用户的语义治理，也不把候选文本自动变成系统提示词。

## 与系统提示词结构的关系

知识本身不是独立的提示词分类。候选知识如果最终要进入系统行为，必须根据 `docs/core/prompt-system-structure.md` 判断它应归属到哪类系统提示词或其他长期入口。

知识转化为系统提示词时必须遵守：

1. 全局基础规则归入 `AI Base System Prompt`。
2. Project、Feature、Stage、Conversation 或参与者事实归入 `Project Conversation Prompt / Work Context` 的对应子项。
3. 某角色在某 Stage 的行动规则归入 `Project Conversation Prompt / Stage Role Playbook`。
4. 后台任务规则归入 `Task Runtime Prompts`。
5. skill 的完整能力说明保留在 skill 文档中，系统提示词只引用能力边界。
6. 同一长期规则只能有一个主归属，其他入口只能引用或摘要，不能复制一份不同写法。

如果治理结果不是系统提示词 PR，也必须说明为什么不进入系统提示词，以及最终去向是什么。

## 总流程

每条候选知识的流程固定如下：

1. Snail 在工作过程中识别可复用知识。
2. Snail 创建候选知识，记录来源、初步范围和候选正文。
3. 知识中心为该候选启动一个知识治理 feature。
4. 治理 feature 先完成入口校验，判断候选是否继续治理、关闭、合并或延后。
5. 通过入口校验后，Snail 与用户先查重并定性。
6. 如果发现已有重复或相关知识，进入负反馈治理流程。
7. 如果没有发现重复或相关知识，进入新增知识审视流程。
8. Snail 与用户决定本条候选的最终处理方式。
9. 如果需要修改长期入口，治理 feature 产出 PR，并按普通 PR 流程 review、修改和合入。
10. 如果不需要 PR，治理 feature 产出明确结论。
11. 治理 feature 结束时，把本条候选的最终去向回写知识中心。

这条流程中，入口校验、查重和定性都发生在治理 feature 内。入口校验不是 feature 外的预筛选，也不是知识中心在 feature 之前完成的隐藏裁决。

## 阶段 1：自动识别并提交候选

Snail 在工作过程中持续判断是否出现可复用知识，包括：

1. 用户明确表达的长期偏好、工作原则或流程约束。
2. 研发、检视或复盘中确认的设计决策、架构取舍或系统不变量。
3. 反复出现的问题、失败教训或反模式。
4. 稳定事实、术语定义或可复用操作步骤。
5. 需要后续治理的开放问题。

候选记录必须包含：

1. 候选标题。
2. 候选正文。
3. 初步类型和范围判断。
4. 来源消息、PR、review 评论、测试失败或外部事实。
5. 创建者和创建时间。

候选只是治理输入，不是结论。候选文本可以粗糙、不完整或带有单次事故细节；这些问题应在治理 feature 中由 Snail 与用户共同处理。

## 阶段 2：为每条候选启动治理 feature

每条候选知识都应启动一个知识治理 feature。该 feature 的职责不是机械落地候选，而是给这条候选一个可追溯去向。

feature 创建时应携带：

1. 候选知识 ID。
2. 候选正文和来源摘要。
3. 候选创建场景。
4. 初步类型和范围判断。
5. 需要回写知识中心的裁决字段。

治理 feature 不能无结论结束；即使入口校验后决定不继续治理，也必须说明本条候选的最终去向。

## 阶段 3：入口校验

入口校验是知识治理 feature 的第一项实质工作。它不判断候选最终是否应落地为长期规则，只判断这条候选是否具备继续进入查重和语义治理的最低条件。

入口校验必须检查：

1. 候选必须有可追溯来源，且来源能支撑候选正文。
2. 候选不能只是普通进度、工具日志、临时状态或已覆盖的交付内容。
3. 候选不能明显为空泛、不可行动或完全缺少长期复用价值。
4. 同一 conversation 中短时间产生多条高度相同候选时，可以先合并为一个治理入口，并在回写中保留被合并候选列表。
5. 批量导入或集中提取候选时，可以创建批处理治理 feature，但必须在 feature 内为每条候选记录独立去向。
6. 用户选择暂不继续治理时，可以把候选标记为延后治理，并记录延后原因和再次触发条件；延后不是最终结论，后续仍需可追溯处理。

入口校验允许直接关闭明显误提取或低价值候选，但必须记录关闭原因，不能静默丢弃。通过入口校验后，治理 feature 才进入查重和定性。

入口校验的结果可以是：

1. 继续治理：进入查重并定性。
2. 关闭候选：明确误提取、低价值或非长期知识原因。
3. 合并候选：并入同一治理 feature 或已有治理记录，并保留追溯关系。
4. 延后治理：记录延后原因和再次触发条件。

## 阶段 4：查重并定性

通过入口校验后，治理 feature 的下一项实质工作是查重并定性。

Snail 与用户必须先检查：

1. 知识中心是否已有相同或高度相似候选。
2. 是否已有候选完成治理并产生裁决。
3. 是否已有系统提示词、skill、core 文档、用户手册、代码、检查器或测试覆盖同一语义。
4. 本次候选是否暴露了旧知识未生效、未覆盖、表达不清、归属错误或执行失败。

查重后只能进入两种场景：

1. 负反馈场景：已有重复或相关知识，本次候选说明旧知识没有充分解决问题。
2. 新增知识场景：没有重复或相关知识，本次候选是新的知识审视对象。

不能跳过查重直接把候选写成新规则。重复知识再次出现时，重点不是新增一条更强规则，而是分析旧裁决为什么没有产生预期效果。

## 阶段 5A：负反馈治理流程

负反馈场景表示：同一知识或同类问题已经出现过，但系统仍然再次遇到。

负反馈治理必须分析：

1. 旧候选或旧知识的最终裁决是什么。
2. 旧知识最终落到了哪里，或者为什么没有落地。
3. 如果已落地，对应的系统提示词、skill、文档、代码或检查器内容是什么。
4. 本次再次出现问题的原因是什么。
5. 原因属于未覆盖、归属错误、表达太弱、提示词未注入、规则冲突、执行能力不足、测试缺失、用户目标变化，还是旧裁决本身错误。
6. 应修正旧入口、替代旧知识、补充新入口，还是确认本次不是同一问题。

负反馈治理的结果可以是：

1. 修改已有长期入口的 PR。
2. 新增补充入口的 PR。
3. 替代旧知识或旧规则的 PR。
4. 只更新知识中心裁决，说明旧知识适用但本次问题另有原因。
5. 拒绝本次候选，说明它不是可复用知识或不是旧知识失效。

负反馈治理必须回写本条候选与旧知识的关系，以及最终修正方案或不修正理由。

## 阶段 5B：新增知识审视流程

新增知识场景表示：未发现已有重复或相关知识，需要判断这条候选是否值得长期保留。

新增知识审视必须分析：

1. 候选指出的是表层症状、流程漏洞、角色职责、提示词归属、系统模型、设计决策、事实基线还是单次事故。
2. 候选是否应该抽象成更高层规则，而不是保留具体事故细节。
3. 候选的适用范围、强度和例外是什么。
4. 候选是否需要拆成多条知识，或与相邻规则合并。
5. 候选是否应该进入系统提示词、skill、core 文档、用户手册、代码注释、检查器、测试，还是仅保留为参考。
6. 如果进入系统提示词，应归属到 `docs/core/prompt-system-structure.md` 定义的哪个分类。

新增知识审视的结果可以是：

1. 产出系统提示词或其他长期入口 PR。
2. 产出 core 文档、用户手册、skill、代码、检查器或测试 PR。
3. 得出不落地结论，并说明原因。
4. 仅保留知识中心参考，不改变系统行为。

新增知识审视必须回写本条候选最终去向，不能只停留在讨论结论。

## 阶段 6：决定产物形式

治理 feature 的产物形式由 Snail 与用户共同决定。

允许的产物形式包括：

1. `conclusion_only`：只形成结论，不修改仓库。
2. `system_prompt_pr`：修改系统提示词。
3. `skill_pr`：修改或新增 skill。
4. `core_doc_pr`：修改核心设计文档。
5. `user_manual_pr`：修改用户手册。
6. `code_or_checker_pr`：修改代码、检查器或测试。
7. `merge_or_supersede_record`：并入或替代已有知识记录。

知识治理 feature 必须能够产出两类结果之一：

1. 结论：例如误提取关闭、低价值关闭、延后治理、拒绝、仅保留参考、并入已有知识、无需修改长期入口。
2. PR：例如修改系统提示词、skill、core 文档、用户手册、代码、检查器或测试。

如果产物是 PR，必须说明：

1. 候选知识来源。
2. 查重结果。
3. 本次是负反馈还是新增知识。
4. 最终归属判断。
5. 为什么采用该产物形式。
6. PR 合入后本条候选的去向。

如果产物只是结论，必须说明：

1. 为什么不需要 PR。
2. 候选是否被拒绝、合并、替代、保留参考或延后。
3. 后续再次命中时应如何处理。

## 阶段 7：系统提示词转化要求

当治理结果需要修改系统提示词时，Snail 不能复制候选正文，而必须完成语义转化。

转化步骤：

1. 根据 `docs/core/prompt-system-structure.md` 判断主归属。
2. 检查现有提示词是否已有同类规则。
3. 如果已有规则表达不清，优先修改原规则，而不是新增重复规则。
4. 如果规则跨越多个入口，只保留一个主归属，其他入口引用或摘要。
5. 删除事故细节，只保留未来可执行的判断标准、边界和动作要求。
6. 明确规则适用的角色、Stage、场景和例外。
7. 检查是否需要同步 `AGENTS.md` 与 `.meta/prompts/` 双线入口。
8. 补充必要测试、文档或手动验证说明。

系统提示词 PR 的 review 关注点不是候选是否“被写进去”，而是候选背后的语义是否被放在正确位置、以正确强度表达，并且没有制造重复或冲突。

## 阶段 8：回写知识去向

治理 feature 结束时，必须把本条候选知识的去向回写知识中心。

回写内容至少包括：

1. 候选知识 ID。
2. 治理 feature ID 或链接。
3. 场景类型：入口关闭、延后治理、负反馈或新增知识。
4. 查重结果和关联知识 ID。
5. 最终产物形式。
6. PR URL 和合入状态，若存在。
7. 最终落地入口，若存在。
8. 不落地、合并、替代或仅保留参考的原因，若适用。
9. 后续再次命中时应参考的位置或处理方式。

知识中心的权威内容不是最终系统提示词全文，而是“这条候选被如何治理、最终去了哪里、再次出现时该看哪里”。

## 知识本体状态与治理状态

知识中心需要同时表达三类状态，但它们不能混为同一个概念：

1. 知识本体状态：描述一条知识是否为候选、是否可被运行时使用、是否被拒绝或归档。
2. 治理 feature 状态：描述围绕候选发起的治理工作流是否打开、进行中、等待 PR、已完成或延后。
3. 治理裁决/去向状态：描述候选最终被关闭、拒绝、合并、仅参考、落地到某个入口、等待合入或已回写。

目标模型至少需要表达以下治理进度和去向：

| 状态 | 归属 | 语义 |
| --- | --- | --- |
| `candidate` | 知识本体状态 | Snail 已提交候选，尚未完成本体层面的批准或拒绝。 |
| `active` | 知识本体状态 | 已被确认为可用知识；是否进入系统行为仍取决于治理裁决和最终落地入口。 |
| `rejected` | 知识本体状态 | 候选被拒绝保留。 |
| `superseded` | 知识本体状态 | 已被新裁决或新知识替代。 |
| `deprecated` | 知识本体状态 | 不再推荐使用，但保留历史追溯。 |
| `archived` | 知识本体状态 | 已归档，只保留历史记录。 |
| `governance_feature_open` | 治理 feature 状态 | 已为该候选启动治理 feature。 |
| `governance_deferred` | 治理 feature 状态 | 已通过入口校验但用户或系统决定延后治理，并记录再次触发条件。 |
| `closed_at_entry_check` | 治理裁决/去向状态 | 入口校验后判定为误提取、低价值或不具备继续治理价值，并记录关闭原因。 |
| `duplicate_feedback` | 治理裁决/去向状态 | 治理中判定为已有知识的负反馈场景。 |
| `new_knowledge_review` | 治理裁决/去向状态 | 治理中判定为新增知识审视场景。 |
| `conclusion_recorded` | 治理裁决/去向状态 | 已形成结论且不需要 PR。 |
| `pr_open` | 治理裁决/去向状态 | 治理产物包含 PR，等待 review 或合入。 |
| `landed` | 治理裁决/去向状态 | PR 已合入并回写去向。 |
| `merged_with_existing` | 治理裁决/去向状态 | 已并入已有知识或长期入口。 |
| `reference_only` | 治理裁决/去向状态 | 仅保留参考，不改变系统行为。 |

治理 feature 状态和治理裁决/去向状态只描述知识治理进度和去向，不等同于系统提示词运行时装配状态。

## 追溯要求

每条候选知识必须能追溯到：

1. 原始来源。
2. 候选创建记录。
3. 知识治理 feature。
4. 入口校验结果。
5. 查重结果。
6. 负反馈或新增知识定性。
7. Snail 与用户的语义审视结论。
8. 最终产物形式。
9. PR URL 和合入状态，若存在。
10. 最终去向回写记录。

追溯的目标是让未来 Snail 和用户看到同类问题时，能理解这条候选曾经如何被判断、是否已有旧知识、最终为什么这样处理。

## 后续实现拆分边界

后续实现应围绕“每条候选进入治理 feature，并在 feature 内完成入口校验和可追溯去向回写”这条流程拆分。拆分必须以要建设的正向能力为主线；禁止事项只能作为每项能力的实现约束和验收要求，不能被包装成独立的“防止某坏事发生”的 PR 动作。

如果能力设计本身正确，例如候选没有自动生效路径、治理结果通过明确裁决进入后续能力，那么不应再单独规划“防止候选自动生效”这类修补型步骤。出现这种步骤通常说明计划把约束当成了功能，或默认假设了一个本不该存在的错误路径。

建议能力建设顺序：

1. 候选提交能力：Snail 能创建带来源、初步范围和候选正文的知识候选。
2. 治理任务能力：知识中心能为每条候选创建独立的知识治理 feature，并建立治理对话入口。
3. 入口校验能力：治理 feature 能记录继续治理、关闭、合并或延后的入口校验结论。
4. 查重定性能力：治理 feature 能展示和记录相关候选、已有知识、长期入口，并定性为负反馈或新增知识审视。
5. 治理裁决能力：治理 feature 能记录结论型或 PR 型产物、最终落地入口、关联知识、合并替代关系和不落地原因。
6. 知识中心展示能力：知识中心按知识本体状态、治理 feature 状态和治理裁决/去向分别展示，并帮助后续查重和追溯。
7. 知识反哺接入能力：当系统需要把已治理知识接入 prompt、skill、检查器或其他运行时能力时，应由治理裁决明确允许的知识提供输入，并记录具体生效形式。

实现约束：

1. 不实现候选知识自动注入 prompt。
2. 不实现候选创建后自动改写系统提示词。
3. 不把知识中心变成系统提示词权威源。
4. 不用使用次数或正向反馈决定知识是否生效。
5. 不绕过 Snail + 用户治理流程直接修改长期入口。
6. 不允许治理 feature 无结论结束。
7. 不把治理进度、治理裁决和知识本体混为同一个概念。
8. 不把约束、禁止事项或不存在的错误路径拆成独立“防治型”实现步骤；应把它们纳入相关能力的设计和验收。

## 合规要求

任何知识闭环相关改动要被视为合规，必须说明：

1. 它作用于流程中的哪个阶段。
2. 是否保持“每条候选进入治理 feature，并且每条候选都有可追溯去向”的边界。
3. 是否在治理 feature 中先完成入口校验、查重和负反馈/新增知识定性。
4. 是否会改变系统提示词归属判断。
5. 是否可能绕过 Snail + 用户治理。
6. 是否把本条候选的最终去向回写清楚。
