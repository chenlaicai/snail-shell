# 知识闭环飞轮生命周期设计

## 文档定位

本文档定义 Snail Shell 知识从一次工作发现，到候选沉淀、人工裁决、系统提示词转化、PR 合入、裁决回写和负反馈再治理的完整流程。

本文档重点定义流程，不定义具体数据库 schema、UI 组件、脚本参数或单个 feature 的实现计划。后续知识中心、系统提示词、prompt 注入、feature 工作流或检视规则相关改动，都必须以本文档的流程边界为准。

## 与系统提示词结构的关系

知识本身不是独立的提示词分类。知识如果要进入系统行为，必须根据 `docs/core/prompt-system-structure.md` 判断它应归属到哪类系统提示词或长期入口。

知识转化为系统提示词时必须遵守：

1. 全局基础规则归入 `AI Base System Prompt`。
2. Project、Feature、Stage、Conversation 或参与者事实归入 `Project Conversation Prompt / Work Context` 的对应子项。
3. 某角色在某 Stage 的行动规则归入 `Project Conversation Prompt / Stage Role Playbook`。
4. 后台任务规则归入 `Task Runtime Prompts`。
5. skill 的完整能力说明仍保留在 skill 文档中，系统提示词只引用能力边界。
6. 同一长期规则只能有一个主归属，其他入口只能引用或摘要，不能复制一份不同写法。

知识中心负责发现和追踪知识；系统提示词结构负责决定知识如果要生效，应以什么语义形态进入长期系统行为。

## 核心原则

1. 知识是语义资产，不能只靠自动同步决定是否生效。
2. 候选知识只表示“值得审视”，不表示已经正确、完整或应该生效。
3. 知识是否进入系统行为，必须经过 Snail 与用户共同治理。
4. 知识落地的目标不是“把候选文本原样注入 prompt”，而是把真实经验转化为正确位置、正确强度、正确边界的系统提示词或其他长期入口。
5. 知识中心不直接完成最终语义转化；它提出治理 feature，并追踪该 feature 的裁决结果。
6. PR 合入是系统提示词或长期入口变更生效的代码仓边界；知识中心只记录这条知识最终如何被裁决，不替代 PR review。
7. 当前不建立正向使用反馈闭环。只有重复问题、再次提取相同知识或旧知识未生效造成问题时，才进入负反馈诊断流程。

## 总流程

知识闭环飞轮的主流程固定如下：

1. 工作中识别可复用知识。
2. 创建候选知识。
3. 知识中心聚合候选并进行初步去重。
4. 用户在知识中心批准、拒绝或要求补充候选。
5. 对批准候选，知识中心创建一个知识治理 feature。
6. Snail 与用户在该 feature 中审视知识语义。
7. Snail 与用户判断知识是否应转化为系统提示词或其他长期入口。
8. 如果需要落地，Snail 按系统提示词结构设计完成归属判断、改写和 PR。
9. PR review 和合入决定长期入口是否真实改变。
10. feature 完成后，裁决结果回写知识中心。
11. 知识中心根据裁决结果更新候选状态和追踪信息。
12. 后续如果再次出现相同知识或同类问题，进入负反馈诊断流程。

这条主流程的核心是“候选知识 -> 知识治理 feature -> Snail + 用户语义审视 -> 系统提示词或长期入口 PR -> 裁决回写”，而不是“候选知识 -> 自动生效 -> 使用统计反馈”。

## 阶段 1：识别候选知识

候选知识来自工作过程中的可复用内容，包括：

1. 用户明确表达的长期偏好、工作原则或流程约束。
2. 研发、检视或复盘中确认的设计决策、架构取舍或系统不变量。
3. 反复出现的问题、失败教训或反模式。
4. 稳定事实、术语定义或可复用操作步骤。
5. 需要后续治理的开放问题。

创建候选时必须保留：

1. 候选标题。
2. 候选正文。
3. 类型、范围和治理等级的初步判断。
4. 来源消息、PR、review 评论、测试失败或外部事实。
5. 创建者和创建时间。

候选创建不代表这条知识已经正确。候选只进入知识中心待处理队列。

## 阶段 2：知识中心初筛

知识中心负责把候选组织成可治理对象。初筛只做工作流判断，不做最终语义落地。

初筛动作包括：

1. 判断候选是否重复。
2. 判断候选是否缺少来源或上下文。
3. 判断候选是否只是一次性任务状态。
4. 判断候选是否需要用户裁决。
5. 判断候选是否可能需要进入系统提示词、skill、文档、代码注释、用户手册或其他长期入口。

初筛结果：

1. `rejected`：不具备长期复用价值，记录拒绝原因。
2. `needs_context`：来源或语义不足，需要补充。
3. `ready_for_governance`：值得进入 Snail + 用户治理流程。
4. `duplicate_candidate`：与已有候选或已裁决知识重复，需要关联旧记录。

知识中心不能在初筛阶段把候选直接变成系统提示词。

## 阶段 3：批准候选并创建知识治理 feature

当用户在知识中心确认某条候选值得治理时，知识中心创建一个新的 feature，而不是直接创建系统提示词 PR。

该 feature 的目标是审视候选知识并得出裁决：

1. 是否需要落地。
2. 应落地到哪个长期入口。
3. 如果进入系统提示词，应归属到哪个提示词分类。
4. 原候选应该如何改写，才能成为可长期维护的系统规则。
5. 是否需要合并、替代、停用或修正已有知识。

feature 创建时应携带：

1. 候选知识 ID。
2. 候选来源摘要。
3. 候选与已有知识的关联。
4. 知识中心提出的初步建议。
5. 需要回写的裁决字段。

## 阶段 4：Snail + 用户共同审视知识语义

知识治理 feature 中，Snail 不能把候选文本当成可直接落地的最终规则。必须先完成语义审视。

审视内容包括：

1. 候选指出的是表层症状、流程漏洞、角色职责、提示词归属、系统模型还是单次事故。
2. 候选是否已经被现有系统提示词、skill、文档、代码或知识覆盖。
3. 如果已有覆盖，为什么仍然需要新增或调整。
4. 候选是否应该抽象成更高层规则，而不是保留具体事故细节。
5. 候选的适用范围和强度是什么。
6. 候选是否需要与其他规则合并、替代或拆分。
7. 候选是否真的应该进入系统提示词，还是应进入 skill、用户手册、core 文档、代码注释、检查器或保持为知识中心记录。

需要用户决策时，Snail 必须把真实分支说明清楚，让用户决定。不能为了推进 PR 自行替用户决定知识的语义归属或规则强度。

## 阶段 5：决定落地入口

审视后必须形成明确裁决。允许的裁决类型包括：

1. `land_as_system_prompt`：转化为系统提示词。
2. `land_as_skill`：转化为 skill 能力说明或 skill 使用规则。
3. `land_as_core_doc`：转化为核心设计文档。
4. `land_as_user_manual`：转化为用户手册。
5. `land_as_code_or_checker`：转化为代码约束、检查器或测试。
6. `merge_with_existing`：并入已有知识或已有长期入口。
7. `supersede_existing`：替代旧知识或旧规则。
8. `reject_after_review`：审视后确认不应长期保留。
9. `keep_as_reference_only`：只保留为知识中心参考，不进入系统行为。

如果裁决为 `land_as_system_prompt`，必须继续执行系统提示词归属判断。

## 阶段 6：转化为系统提示词

系统提示词转化不是复制候选正文，而是把候选背后的语义改写成稳定规则。

转化步骤：

1. 根据 `docs/core/prompt-system-structure.md` 判断主归属。
2. 检查现有提示词是否已有同类规则。
3. 如果已有规则表达不清，优先修改原规则，而不是新增重复规则。
4. 如果规则跨越多个入口，只保留一个主归属，其他入口引用或摘要。
5. 删除事故细节，只保留未来可执行的判断标准、边界和动作要求。
6. 明确规则适用的角色、Stage、场景和例外。
7. 检查是否需要同步 `AGENTS.md` 与 `.meta/prompts/` 双线入口。
8. 补充必要测试、文档或手动验证说明。

系统提示词转化必须通过普通代码仓 PR 完成。PR 标题、正文、commit 和 feature 文档必须说明：

1. 候选知识来源。
2. 最终归属判断。
3. 与现有提示词的关系。
4. 为什么这样改写，而不是原样写入。
5. 哪些旧规则被合并、替代或删除。
6. 验证范围。

## 阶段 7：PR review 与合入

知识治理 feature 的 PR review 关注点不是候选是否“被写进去了”，而是转化是否正确。

必须检查：

1. 是否解决候选暴露的真实问题。
2. 是否放在正确的系统提示词分类或长期入口。
3. 是否与现有规则重复、冲突或漂移。
4. 是否把事故细节错误固化成长期规则。
5. 是否保留了必要边界和例外。
6. 是否需要同步其他规则入口。
7. 是否说明不落地或部分落地的理由。

PR 合入后，长期入口才发生改变。知识中心不能在 PR 合入前把候选标记为已落地。

## 阶段 8：裁决结果回写知识中心

知识治理 feature 完成后，必须把最终裁决回写知识中心。

回写内容包括：

1. 候选知识 ID。
2. 裁决类型。
3. 最终落地入口。
4. PR URL 和合入状态。
5. 最终系统提示词归属，若适用。
6. 是否合并、替代或拒绝。
7. 裁决摘要。
8. 后续再次命中时应参考的位置。

知识中心的角色是追踪“这条知识被如何裁决”，不是复制最终系统提示词全文作为另一个权威源。

如果最终裁决为不落地，知识中心也必须记录原因，避免后续重复提出同一候选时丢失历史判断。

## 阶段 9：负反馈诊断

当前不建立正向反馈流程，例如“知识被成功使用多少次”。知识闭环只处理负反馈。

触发负反馈诊断的条件：

1. 同一条或高度相似的知识再次被提取。
2. 已裁决知识对应的问题再次发生。
3. Snail 或用户指出某条已落地知识没有产生预期效果。
4. 检视发现已有提示词规则存在但 agent 仍然违反。

负反馈诊断必须在新的 feature 对话中完成，不能由知识中心自动修改提示词。

诊断步骤：

1. 找到已有候选、裁决记录和最终落地入口。
2. 读取对应系统提示词、skill、文档或代码入口的当前内容。
3. 分析再次出现问题的原因。
4. 判断是规则未覆盖、归属错误、表达太弱、注入范围错误、上下文未命中、规则冲突、执行能力不足，还是用户目标已经变化。
5. 给出修复方案。
6. 如需修改长期入口，创建 PR。
7. PR 合入后回写新的裁决结果。

负反馈不是“增加一条更强的重复规则”。如果问题来自原规则位置错误或表达冲突，应修正原规则或调整归属。

## 知识中心状态

知识中心至少需要表达以下状态：

| 状态 | 语义 |
| --- | --- |
| `candidate` | 已识别，待初筛或用户处理。 |
| `needs_context` | 信息不足，不能治理。 |
| `rejected` | 已拒绝，保留原因。 |
| `ready_for_governance` | 可进入 Snail + 用户治理。 |
| `governance_feature_open` | 已创建知识治理 feature。 |
| `pr_open` | 已有长期入口变更 PR。 |
| `landed` | PR 已合入并完成裁决回写。 |
| `merged_with_existing` | 已并入已有知识或长期入口。 |
| `reference_only` | 仅保留参考，不进入系统行为。 |
| `superseded` | 已被新裁决替代。 |

这些状态只描述知识治理进度，不等同于系统提示词运行时装配状态。

## 追溯要求

每条进入治理流程的知识必须能追溯到：

1. 原始来源。
2. 候选创建记录。
3. 用户批准或拒绝记录。
4. 知识治理 feature。
5. 语义审视结论。
6. 最终裁决类型。
7. PR URL 和合入状态。
8. 最终落地入口。
9. 负反馈诊断记录，若存在。

追溯的目标是让未来 Snail 和用户看到同类问题时，能理解这条知识曾经如何被判断、为何这样落地、为什么再次出现问题。

## 后续实现拆分边界

后续实现应围绕流程拆分，而不是围绕数据库表或自动同步能力拆分。

建议顺序：

1. 候选知识与知识中心初筛。
2. 知识中心发起知识治理 feature。
3. 知识治理 feature 的裁决回写。
4. 系统提示词归属辅助信息和重复检测。
5. PR 追踪与合入状态回写。
6. 负反馈诊断入口。

实现约束：

1. 不实现候选知识自动注入 prompt。
2. 不实现候选批准后自动改写系统提示词。
3. 不把知识中心变成系统提示词权威源。
4. 不用使用次数或正向反馈决定知识是否生效。
5. 不绕过 Snail + 用户治理流程直接修改长期入口。

## 合规要求

任何知识闭环相关改动要被视为合规，必须说明：

1. 它作用于流程中的哪个阶段。
2. 是否会改变候选、治理 feature、PR 或裁决回写的边界。
3. 是否涉及系统提示词归属判断。
4. 是否可能绕过 Snail + 用户治理。
5. 是否会制造重复规则或多权威源。
6. 负反馈场景下如何定位已有裁决并分析未生效原因。
