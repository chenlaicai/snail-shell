# 提示词效果评估框架

## 定位

本文档定义 Snail Shell 系统提示词的效果评估模型，用于回答“改动前后是否真的变好”。它补充 `docs/core/prompt-system-structure.md` 的结构治理能力，但不替代具体 feature 文档、运行时实现或人工使用反馈。

本文档只定义长期评估边界、样本组织方式和证据分层，不记录单次 feature 的临时结论。

## 为什么需要独立评估

系统提示词优化天然带有经验驱动色彩，但经验本身不能直接证明提示词已经变好。仅凭日常使用感受会混入任务分布变化、上下文差异、模型波动和回忆偏差，无法稳定判断某次改动是在修复问题，还是只改变了说法。

因此，提示词优化必须区分三类证据：

1. 结构证据：提示词是否被正确归属、渲染和注入。
2. 行为证据：给定固定输入后，运行时是否更稳定地表现出期望行为。
3. 体验证据：真实使用过程中是否更少出现跑偏、停顿、越权或误判。

## 评估层次

### 结构评估

结构评估用于确认提示词资产本身没有写乱。典型关注点包括：

1. 规则归属是否正确。
2. 关键约束是否仍进入运行时 prompt。
3. `.meta/prompts/` 与 `AGENTS.md` 是否发生漂移。
4. 提示词是否把场景规则错误上移到 `ai.base.system`。

结构评估可以通过静态测试完成，但它只能证明“提示词被正确装配”，不能证明模型已经按预期行动。

### 行为评估

行为评估用于比较固定样本在不同提示词版本、不同 agent runtime 下的实际表现。它是提示词效果判断的核心层。

行为评估样本至少要包含：

1. 样本要验证的行为维度。
2. 样本输入依赖的场景事实。
3. 期望行为。
4. 明确禁止的失败行为。
5. 适用的 agent runtime。
6. 自动执行结果与自动判定结果。

行为评估默认应由 AI 自动执行：评估器按 `sample x runtime` 调用目标 runtime 生成输出，再调用 judge runtime 根据样本的期望行为和禁止行为生成结构化判定。人工只用于处理 runtime 缺失、权限失败、输出不可解析或判定争议，不能作为常规评估主路径。

当前责任边界是：系统只负责提供评估样本资产、runner 和命令行入口；当 Snail 在提示词调整场景下完成验证时，应由负责该改动的 Snail 主动调用 runner，而不是要求系统工作流或 CI 自动触发。

### 体验评估

体验评估保留真实使用反馈，但必须结构化记录，不允许只留下“感觉更好”这类不可复核的结论。推荐按事件分类记录，例如：

1. 提前停顿。
2. 错误扩大行动强度。
3. 错误缩小任务范围。
4. 没有按协议 mention 或输出结构化消息。
5. 事实判断与任务归属错误。

## Agent Runtime 维度

Snail Shell 的提示词评估不能把“模型行为”抽象成单一对象。当前至少要把以下 runtime 作为一等维度分别记录：

1. `opencode-cli`
2. `claude-code-cli`
3. `codex-cli`

原因不是这三个 runtime 名字不同，而是它们对上下文传递方式、会话状态模型和 CLI 行为约束并不相同：

1. `claude-code-cli` 当前走 stateless 路径，每次响应依赖 Snail Shell 重建完整上下文。
2. `opencode-cli` 当前走 stateful 路径，bootstrap 后主要依赖运行时 session 持续推进。
3. `codex-cli` 当前也走 stateful 路径，但线程恢复、参数协议和最终输出形态与 OpenCode 不同。

因此，提示词评估结果必须至少回答两个问题：

1. 某个样本在每个 runtime 下是否都通过。
2. 某次提示词改动是否只改善了某个 runtime，却让另一个 runtime 回归。

## 样本组织规则

仓库中的评估样本应作为正式资产存放，并满足以下规则：

1. 每个样本必须有稳定 `id`。
2. 每个样本必须声明所属评估维度，例如 `scope-boundary`、`action-restraint`、`continuous-execution`。
3. 每个样本必须声明 `agent_runtimes`，不能默认“所有 runtime 一样”。
4. 每个样本必须同时声明 `expected_behaviors` 与 `forbidden_behaviors`。
5. 每个样本必须说明该样本源自什么真实问题或长期风险。
6. 样本应尽量复用真实失败案例，而不是只写抽象口号。

## 自动执行流程

提示词行为评估的默认流程是：

1. 选择待评估样本和目标 runtime。
2. 为每个 `sample x runtime` 生成目标任务输入。
3. 调用目标 runtime 收集原始输出。
4. 调用 judge runtime 对照 `expected_behaviors` 与 `forbidden_behaviors` 生成结构化判定。
5. 将目标输出、判定、runtime、样本 ID、错误或阻塞原因写入报告。

如果某个 runtime 在本地不可用、凭据缺失、CLI 执行失败或超时，评估结果应标记为 `blocked` 或 `error`，并记录原因。不能因为存在这些工程阻塞，就把提示词评估设计成依赖人工主观验证。

系统是否在未来补充自动触发机制，是独立演进问题，不影响当前默认责任划分。

## 推荐评分方式

自动判定结果使用以下状态：

1. `pass`：输出满足期望行为，且没有触发禁止行为。
2. `partial`：只满足部分期望，或出现轻微偏差但未破坏主要语义。
3. `fail`：触发禁止行为，或没有实现样本核心目标。
4. `blocked`：目标 runtime 未执行成功，原因是 CLI、凭据、权限、网络或环境阻塞。
5. `error`：评估器、目标 runtime 或 judge runtime 出现非预期错误。

评分记录必须按 `sample x runtime` 粒度保留，不能只给整个提示词版本一个总印象分。

## 回归集维护规则

每次遇到新的真实失败模式时，都应判断是否需要新增评估样本。以下情况默认应进入回归集：

1. 用户指出系统提示词让 agent 错误升级行动强度。
2. 用户指出 agent 提前停下，要求重复发送“继续”。
3. 用户指出 agent 把单个例子误当成任务范围上限。
4. 用户指出跨 Stage、跨 Feature 或跨 PR 的归属判断错误。
5. 不同 runtime 对同一提示词表现出稳定分歧。

没有长期复用价值的一次性噪声，不必强行沉淀为样本。

## 与现有测试的关系

`tests/meta/prompt-assets-test.ts` 这类测试仍然重要，但它们主要证明提示词资产的结构正确性。新增的提示词效果评估资产用于补齐“行为比较”和“跨 runtime 回归判断”，两者不能互相替代。
