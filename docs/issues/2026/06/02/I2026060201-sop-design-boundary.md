# I2026060201 [prompts] SOP 设计者角色边界定义

<!-- [design-time] 以下章节在需求收敛与设计阶段（代码前）完成并锁定 -->
<!-- 进入实现阶段后不得单方面修改，如需变更须通过问题卡片向用户提出并确认 -->

## 背景

S-09 设计者手册定义了设计者"做什么"，但**完全没有定义"不做什么"**。具体缺失：

1. **无角色边界声明**——没有明确"设计者只产出设计，不碰实现"
2. **对抗性审视要点越界**——"实现复杂度是否合理？"直接引导设计者思考实现细节
3. **无反模式警示**——设计者自然滑向"我来改代码"时，没有任何机制拉回来

这导致设计者在实际工作中越界到实现层面，提出具体的代码修改方案，违反了阶段分工原则。

## 目标

在 S-09 设计者手册中新增角色边界约束，明确设计者的职责范围，防止越界到实现层面。

### P1 — 角色边界定义

1. 在 S-09 中新增「角色边界」段落，明确设计者的职责和禁止事项
2. 修正「对抗性审视要点」，将"实现复杂度"改为"设计复杂度"，避免引导设计者关注实现细节
3. 在自检清单表格中新增角色边界行，强化边界意识

## 非目标

- 不修改其他 SOP 文档（如 S-03 研发者手册）
- 不改变现有的设计工作流程
- 不引入新的工具或自动化机制

## 设计

### P1 详设

**方案**：在 S-09 中新增「角色边界」段落 + 修正审视要点

**具体修改（3 处）**：

**1. 新增角色边界段落**

在"设计者手册"标题下、工作流程之前，新增：

```markdown
## 角色边界

设计者**只负责**需求对齐、方案设计和交叉审视，**不负责**实现。

| 设计者职责 | 非设计者职责（禁止） |
|---|---|
| 理解需求、定义问题边界 | 编写或修改代码 |
| 提出设计方案、记录取舍 | 制定实现步骤或伪代码 |
| 交叉审视方案的完备性和风险 | 直接执行文件创建/修改 |
| 产出锁定的 Issue 文档 | 提议具体的代码修改方案 |

**自检规则**：如果发现自己在说"具体修改 XX 文件的 XX 行"，立即停止——这是研发者的活。
```

**2. 修正对抗性审视要点**

将"实现复杂度是否合理？"改为"设计复杂度是否合理？"，避免引导设计者关注实现细节。

**3. 新增自检清单行**

在自检清单表格中新增：

```markdown
| 角色边界 | 未提出代码修改方案 · 未越界到实现细节 · 输出仅为设计产物 |
```

**设计取舍**：

| 取舍 | 正面论述 | 反面论述 |
|---|---|---|
| 只改 S-09 一个文件 | 最小改动，影响范围可控 | 如果其他 SOP 也有类似问题，需要分别修改 |
| 使用表格+自检规则双重约束 | 正面定义职责 + 反面禁止越界，双重保障 | 增加了自检负担，但这是必要的 |
| 不引入自动化检查 | 简单直接，不需要新工具 | 依赖设计者自觉，可能有遗漏 |

**为什么是这个方案而不是其他**：
- 只改 S-09 一个文件，不动代码、不动配置
- 通过正面定义（职责表）+ 反面禁止（自检规则）+ 审视修正 三重约束，把边界钉死
- 不需要新工具或新流程，纯粹是 SOP 文本层面的修正

## 生效路径

修改 S-09 模板 → 下次加载系统提示词时自动生效
