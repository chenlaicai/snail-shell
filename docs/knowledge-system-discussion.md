# 知识体系设计再修正：范围、审批、反哺与 UI\n\n## 结论更新\n\n你的这轮意见会改变设计重心：知识系统不能只是一套后台记忆机制，它必须有明确生效范围、人工审批中心、可解释的使用方式，以及面向用户的知识运营 UI。\n\n我现在的修正结论是：\n\n1. 知识的核心属性不是“重要程度”，而是“语义类型 + 生效范围 + 治理状态 + 使用方式”。\n2. prompt、skill、MCP、检查器不是升级层级，而是不同的反哺载体；选择哪个载体由知识内容决定。\n3. 知识转正必须全部人工审批，系统只能做候选提炼、推荐分类、冲突提示和影响分析。\n4. UI 是知识体系的一等能力，必须有“知识中心”，并和“项目管理”并列成为首层功能。\n\n## 1. 生效范围：知识必须可限定作用域\n\n### 为什么生效范围是核心字段\n\n不同知识天然有不同边界：\n\n1. 用户偏好可能是全局的。\n2. 某项目设计决策通常只在该 project 生效。\n3. 某 feature 方案只对该 feature 生效。\n4. 某代码模块经验只对某个 code area 生效。\n5. 某 snail 工作方式只对特定角色生效。\n6. 某 stage 经验只对特定阶段类型生效。\n\n如果没有生效范围，知识反哺会变成污染：A 项目的设计决策可能错误影响 B 项目；某个临时 feature 的约束可能被全局使用。\n\n### Scope 模型建议\n\n建议知识项必须包含：\n\n1. `scope_type`\n2. `scope_ref`\n3. `scope_label`\n4. `applies_to`\n5. `exclusion`\n\n第一版可先简化，但概念必须完整。\n\n#### scope_type\n\n建议枚举：\n\n| scope_type | 含义 | 示例 |\n| --- | --- | --- |\n| `global` | 整个 Snail Shell 实例生效 | 用户偏好、系统级原则 |\n| `project` | 某个 project 内生效 | 项目设计决策 |\n| `feature` | 某个 feature 内生效 | 特定功能方案约束 |\n| `stage_type` | 某类 stage 生效 | review 阶段检视规则 |\n| `conversation` | 某个 conversation 生效 | 临时讨论约束，通常不自动注入 |\n| `snail` | 某个角色生效 | Acceptance Snail 的检视偏好 |\n| `code_area` | 某个目录/模块/文件生效 | runtime adapter 边界经验 |\n| `workflow` | 某个工作流机制生效 | stage advance 不受知识提炼阻塞 |\n\n#### applies_to\n\n用于表达更细粒度条件，例如：\n\n```json\n{\n  \"project_id\": \"...\",\n  \"feature_id\": \"...\",\n  \"stage_type\": \"development\",\n  \"snail_names\": [\"Implementation Snail\"],\n  \"code_paths\": [\"src/snails/**\", \"src/project/**\"],\n  \"tags\": [\"knowledge\", \"prompt\"]\n}\n```\n\n第一版可以存在 `metadata` 里，不必过早拆太细表。\n\n### 作用域匹配规则\n\n反哺时必须按“就近优先”匹配：\n\n1. conversation 级别，如果显式引用。\n2. feature 级别。\n3. project 级别。\n4. code_area 级别，如果当前任务涉及路径。\n5. snail/stage_type 级别。\n6. global 级别。\n\n同时必须避免跨域污染：\n\n1. project scope 的知识只能用于同 project。\n2. feature scope 的知识只能用于同 feature。\n3. code_area scope 只有任务涉及相关路径时才自动候选。\n4. conversation scope 默认不自动反哺，只用于溯源和手动查询。\n\n## 2. 项目设计决策应作为知识库承载\n\n同意。某 project 的设计决策不应该散落在 conversation summary 或 artifact 里，也不应该仅靠 prompt 短期注入。\n\n更好的设计是：每个 project 天然拥有一个“项目知识库视图”。\n\n它包括：\n\n1. 设计决策：为什么这么设计。\n2. 架构约束：哪些边界不能破坏。\n3. 术语定义：项目内概念是什么。\n4. 用户偏好在本项目内的具体化。\n5. 历史事故与反模式。\n6. 未决问题。\n7. 与代码区域绑定的经验。\n\nAgent 使用方式可以是 skill，也可以是工具查询：\n\n1. 设计前调用“查询项目知识库”。\n2. 实现前查询相关 code_area 知识。\n3. 检视时查询 project 的 accepted rules 和 anti_patterns。\n4. 回答用户问题时引用相关 design decision。\n\n关键是：知识库存储与治理在 KnowledgeService，skill 只是使用入口。\n\n## 3. prompt、skill、MCP 不是升级关系\n\n你这个纠正是对的。\n\n我之前把 `prompt -> skill -> mcp/checker` 描述成升级路径，不准确。它们不是知识等级，而是知识的使用/反哺方式。\n\n### 正确模型\n\n知识本身有治理生命周期：\n\n```text\ncandidate -> approved/accepted -> active -> revised/superseded/deprecated/archived\n```\n\n知识也有成熟度或稳定性：\n\n```text\nunverified -> confirmed -> battle-tested -> obsolete\n```\n\n知识还有反哺方式：\n\n```text\nprompt injection / skill guidance / tool query / MCP operation / checker / workflow policy / document / UI card\n```\n\n这些是正交维度，不应该混在一个“升级阶梯”里。\n\n### 知识升级到底是什么\n\n知识升级不等于换成 skill 或 MCP。知识升级应该指治理状态和系统承诺的升级。\n\n我建议定义为：知识从“可参考”升级为“系统承诺”。\n\n可分四级：\n\n| 等级 | 名称 | 含义 | 影响 |\n| --- | --- | --- | --- |\n| L0 | 候选知识 | 系统提炼出的待审批项 | 不反哺 |\n| L1 | 已确认知识 | 人工审批通过，可被引用 | 可搜索、可按范围注入 |\n| L2 | 运行约束 | 被确认会影响 agent 工作判断 | prompt/skill/tool 默认使用 |\n| L3 | 系统规则 | 被确认应由系统强制维护 | checker/workflow/API 约束 |\n\n这里的 L1-L3 是治理承诺升级，不是技术载体升级。\n\n同一条知识在 L2 时可以用 prompt，也可以用 skill，也可以用查询工具。技术载体由内容决定。\n\n### 反哺方式如何选择\n\n按知识内容选载体：\n\n| 知识内容 | 首选反哺方式 | 原因 |\n| --- | --- | --- |\n| 用户偏好 | prompt + UI 展示 | 语义性强，需要 agent 知道 |\n| 项目设计决策 | 知识库查询 + prompt 摘要 + 引用卡 | 内容较长，不能全塞 prompt |\n| 操作流程 | skill | 需要指导 agent 按步骤做 |\n| 可执行能力 | MCP/tool | 需要读写数据库或执行动作 |\n| 不变量/禁止项 | checker + prompt | 需要强校验 |\n| 术语定义 | prompt 摘要 + 知识库 | 用于降低歧义 |\n| 历史事故 | 检视 skill + 查询工具 | 主要服务 review 和风险识别 |\n| 未决问题 | UI 待办 + prompt 提醒 | 需要人决策 |\n\n所以，prompt/skill/MCP/checker 都是“使用方式”，不是知识级别。\n\n## 4. 转正必须人工审批\n\n同意，应该改成硬规则：所有 candidate 转 accepted 必须人工审批。\n\n包括用户显式说“记住”也应进入“待审批”吗？我建议这里做一个细分：\n\n1. 用户在 UI 或命令中明确点击/执行“批准入库”：直接 accepted。\n2. 用户在自然语言中说“记住”：系统创建高优先级 candidate，并在 UI 中标记为“用户显式记忆请求”，等待审批。\n3. Agent 推断出的知识：普通 candidate，等待审批。\n\n这样最安全，也满足“知识使用直接影响系统运行效果”。\n\n### 审批原则\n\n审批时用户需要看到：\n\n1. 知识内容。\n2. 提炼原因。\n3. 来源引用。\n4. 生效范围。\n5. 知识类型。\n6. 预期反哺方式。\n7. 冲突检测结果。\n8. 审批后会影响哪些 agent/项目/流程。\n\n审批动作：\n\n1. 批准。\n2. 拒绝。\n3. 编辑后批准。\n4. 修改范围。\n5. 标记为重复。\n6. 合并到已有知识。\n7. 标记冲突，暂不处理。\n\n### 审批队列优先级\n\n排序建议：\n\n1. 用户显式记忆请求。\n2. 影响范围大的候选知识。\n3. 与已有 accepted 冲突的候选知识。\n4. 多次重复出现的候选知识。\n5. 来源于 review/test failure 的候选知识。\n6. 普通 agent 推断。\n\n## 5. UI 设计：首层功能列表与知识中心\n\n当前仓库基本只有后端 API，没有现成前端；因此这里先定义 UI 信息架构和页面设计，后续再实现。\n\n### 首层信息架构\n\n建议首层不是直接进入某个 project，而是一个工作台：\n\n```text\nSnail Shell\n├── 工作台 / Dashboard\n├── 项目管理 / Projects\n├── 知识中心 / Knowledge\n├── Snail 与能力 / Agents & Capabilities\n├── 系统运行 / Runtime\n└── 设置 / Settings\n```\n\n第一版可以只做三个核心入口：\n\n1. 工作台\n2. 项目管理\n3. 知识中心\n\n### 布局建议\n\n使用左侧主导航 + 顶部上下文栏 + 右侧主内容。\n\n```text\n┌──────────────────────────────────────────────────────────┐\n│ Top Bar: 当前 workspace / 搜索 / 新建 / 通知 / 用户        │\n├──────────────┬───────────────────────────────────────────┤\n│ 左侧导航      │ 主内容区                                  │\n│              │                                           │\n│ 工作台        │ 当前页面内容                              │\n│ 项目管理      │                                           │\n│ 知识中心      │                                           │\n│ Snails       │                                           │\n│ 设置          │                                           │\n└──────────────┴───────────────────────────────────────────┘\n```\n\n### 工作台\n\n作用：展示系统当前需要用户关注的事项。\n\n核心卡片：\n\n1. 待审批知识数量。\n2. 活跃项目数量。\n3. 等待用户回复的 conversation。\n4. 等待合入的 PR。\n5. 最近失败的任务。\n6. 最近新增的高价值知识候选。\n\n工作台不是知识管理主页面，只负责提醒和入口。\n\n### 项目管理\n\n项目管理保留当前主链路。\n\n页面结构：\n\n1. 项目列表。\n2. 项目详情。\n3. Feature 列表。\n4. Stage 状态。\n5. Conversation。\n6. Artifact。\n7. PR 状态。\n\n项目详情页应增加一个“项目知识”标签页，但它只是 Knowledge Center 的 project-filtered view，不是另一套知识系统。\n\n项目详情页 tabs：\n\n1. 概览\n2. Features\n3. Conversations\n4. Artifacts\n5. PR / Review\n6. 项目知识\n\n### 知识中心\n\n知识中心是新系统核心。\n\n建议分为 5 个页面：\n\n1. 知识库\n2. 待审批\n3. 冲突与过期\n4. 使用与反馈\n5. 反哺配置\n\n#### 1. 知识库\n\n用于查看 accepted/active/deprecated 的知识。\n\n左侧过滤器：\n\n1. Scope: global/project/feature/snail/code_area/workflow。\n2. Project。\n3. Feature。\n4. Kind: decision/rule/preference/incident/anti_pattern/glossary/open_question。\n5. Status。\n6. Confidence 或治理等级。\n7. Source type。\n8. Tags。\n\n列表字段：\n\n1. 标题。\n2. 类型。\n3. 生效范围。\n4. 状态。\n5. 反哺方式。\n6. 最近使用。\n7. 来源数量。\n8. 更新时间。\n\n详情页展示：\n\n1. 标题与状态。\n2. 内容正文。\n3. 生效范围。\n4. 适用/排除条件。\n5. 来源引用。\n6. 反哺方式。\n7. 使用记录。\n8. 反馈记录。\n9. 关联知识：支持、冲突、替代、重复。\n10. 操作：编辑、废弃、替代、修改范围、配置反哺。\n\n#### 2. 待审批\n\n这是最关键页面。\n\n列表分组：\n\n1. 用户显式记忆请求。\n2. 系统自动提炼。\n3. Agent 主动提交。\n4. Stage sweep 提炼。\n5. Review/test failure 提炼。\n\n每个候选卡片展示：\n\n1. 候选知识标题。\n2. 提炼内容。\n3. 建议类型。\n4. 建议生效范围。\n5. 来源摘录。\n6. 提炼理由。\n7. 准入评分。\n8. 冲突提示。\n9. 预期反哺方式。\n\n审批操作：\n\n1. 批准。\n2. 编辑后批准。\n3. 拒绝。\n4. 合并。\n5. 改范围。\n6. 标记为未决问题。\n\n审批页必须支持“左右分栏”：\n\n```text\n┌──────────────────────┬──────────────────────────────┐\n│ 候选列表              │ 候选详情 + 来源上下文          │\n│                      │                              │\n│ K-CAND-1             │ 内容                          │\n│ K-CAND-2             │ 来源消息 / artifact / PR       │\n│ K-CAND-3             │ 冲突检测                      │\n│                      │ 审批表单                      │\n└──────────────────────┴──────────────────────────────┘\n```\n\n#### 3. 冲突与过期\n\n用于治理知识健康。\n\n场景：\n\n1. 新 candidate 与 accepted 冲突。\n2. 两条 accepted 知识互相矛盾。\n3. source 指向对象不存在。\n4. code_area 文件被删除。\n5. 某条知识长期未使用。\n6. 某条知识多次被反馈 misleading。\n\n操作：\n\n1. 标记 superseded。\n2. 合并。\n3. 修改 scope。\n4. 降级为 archived。\n5. 创建用户决策问题。\n\n#### 4. 使用与反馈\n\n展示知识如何影响系统。\n\n视图：\n\n1. 哪些知识被 prompt 注入最多。\n2. 哪些知识被 agent 查询最多。\n3. 哪些知识被反馈为无关/冲突/误导。\n4. 哪些知识关联了失败或检视意见。\n5. 哪些 agent/项目最依赖知识。\n\n这页回答一个问题：知识系统到底有没有让系统变好，还是制造噪音。\n\n#### 5. 反哺配置\n\n这页不是配置知识等级，而是配置使用方式。\n\n每条 accepted knowledge 可以配置：\n\n1. 是否允许 prompt 注入。\n2. 是否在某些 skill 中可见。\n3. 是否作为 MCP/tool 查询结果优先返回。\n4. 是否绑定到 checker。\n5. 是否绑定到 project/stage/snail。\n6. 注入预算和优先级。\n\n默认策略：\n\n1. project decision：项目内查询优先，prompt 只注入摘要。\n2. rule：允许 prompt 注入，必要时进入 checker。\n3. preference：允许 prompt 注入。\n4. incident/anti_pattern：review 阶段优先展示。\n5. glossary：按需注入。\n\n## 6. UI 的关键交互\n\n### 全局搜索\n\n顶部搜索框应能搜：\n\n1. project\n2. feature\n3. conversation\n4. artifact\n5. knowledge\n\n搜索结果要标注类型和生效范围。\n\n### 引用卡片\n\n在 conversation 中引用知识时，应该显示 knowledge card：\n\n1. 标题。\n2. 类型。\n3. 生效范围。\n4. 状态。\n5. 摘要。\n6. 查看详情。\n\n### 审批时查看来源\n\n审批候选知识时，必须能一键打开来源上下文：\n\n1. message window。\n2. artifact 内容。\n3. PR/review 链接。\n4. stage/conversation。\n\n没有来源上下文的候选不能批准。\n\n### 项目知识视图\n\n在项目详情里，“项目知识”应默认展示：\n\n1. 当前 project 的 design decisions。\n2. 当前 project 的 rules。\n3. 当前 project 的 glossary。\n4. 当前 project 的 incidents/anti_patterns。\n5. 与当前 active feature 相关的 candidate。\n\n这能让项目设计决策真正成为项目知识库。\n\n## 7. 后端 API 需求\n\n为 UI 需要新增知识 API：\n\n### 查询\n\n1. `GET /api/knowledge`\n2. `GET /api/knowledge/:id`\n3. `GET `scope_type`\n2. `scope_ref`\n3. `kind`\n4. `status`: candidate/approved/active/rejected/superseded/deprecated/archived\n5. `governance_level`: L0/L1/L2/L3\n6. `title`\n7. `content`\n8. `rationale`\n9. `created_by`\n10. `approved_by`\n11. `approved_at`\n12. `metadata`\n\n### knowledge_usage_policy\n\n不要把反哺方式塞成单个字段。应独立建 policy：\n\n1. `knowledge_id`\n2. `allow_prompt_injection`\n3. `prompt_mode`: none/summary/full/reference_only\n4. `skill_visibility`\n5. `tool_visibility`\n6. `checker_binding`\n7. `stage_types`\n8. `snail_names`\n9. `priority`\n10. `token_budget`\n\n### knowledge_candidate_review\n\n用于审批留痕：\n\n1. `knowledge_id`\n2. `reviewer`\n3. `decision`\n4. `comment`\n5. `before_snapshot`\n6. `after_snapshot`\n7. `created_at`\n\n## 9. 需要写进系统规则的硬约束\n\n1. PR/review 链接。\n4. stage/conversation。\n\n没有来源上下文的候选不能批准。\n\n### 项目知识视图\n\n在项目详情里，“项目知识”应默认展示：\n\n1. 当前 project 的 design decisions。\n2. 当前 project 的 rules。\n3. 当前 project 的 glossary。\n4. 当前 project 的 incidents/anti_patterns。\n5. 与当前 active feature 相关的 candidate。\n\n这能让项目设计决策真正成为项目知识库。\n\n## 7. 后端 API 需求\n\n为 UI 需要新增知识 API：\n\n### 查询\n\n1. `GET /api/knowledge`\n2. `GET /api/knowledge/:id`\n3. `GET `scope_type`\n2. `scope_ref`\n3. `kind`\n4. `status`: candidate/approved/active/rejected/superseded/deprecated/archived\n5. `governance_level`: L0/L1/L2/L3\n6. `title`\n7. `content`\n8. `rationale`\n9. `created_by`\n10. `approved_by`\n11. `approved_at`\n12. `metadata`\n\n### knowledge_usage_policy\n\n不要把反哺方式塞成单个字段。应独立建 policy：\n\n1. `knowledge_id`\n2. `allow_prompt_injection`\n3. `prompt_mode`: none/summary/full/reference_only\n4. `skill_visibility`\n5. `tool_visibility`\n6. `checker_binding`\n7. `stage_types`\n8. `snail_names`\n9. `priority`\n10. `token_budget`\n\n### knowledge_candidate_review\n\n用于审批留痕：\n\n1. `knowledge_id`\n2. `reviewer`\n3. `decision`\n4. `comment`\n5. `before_snapshot`\n6. `after_snapshot`\n7. `created_at`\n\n## 9. 需要写进系统规则的硬约束\n\n1. 所有知识都必须有生效范围。\n2. 所有 candidate 转 accepted/active 必须人工审批。\n3. 未审批知识不得自动进入 prompt、skill、MCP 查询优先结果或 checker。\n4. prompt/skill/MCP/checker 是使用方式，不是知识等级。\n5. 项目设计决策默认 project scope，不得跨项目生效。\n6. 没有来源上下文的知识不能批准。\n7. 知识系统不得阻塞主工作流，但可以在工作台产生待办提醒。\n8. UI 必须提供审批、冲突、来源、使用反馈的可视化入口。\n\n## 10. 第一版实现建议\n\n如果下一步进入实现，我建议第一版同时做后端与极简 UI 骨架，而不是只做后台：\n\n1. 后端：knowledge schema、store、API、FTS、审批状态流转。\n2. 后端：scope 匹配、usage policy、record use。\n3. 后端：候选知识创建接口，先不做复杂自动提炼。\n4. UI：首层导航，包含“项目管理”和“知识中心”。\n5. UI：知识中心的知识库列表、待审批列表、详情审批页。\n6. UI：项目详情增加“项目知识”视图。\n7. Prompt builder：只读取人工审批后的 active knowledge，并按 scope/policy 注入摘要或引用。\n\n这版能把关键体系打通：有范围、有候选、有审批、有知识库、有 UI、有反哺，但提炼智能化可以后续增强。\n
