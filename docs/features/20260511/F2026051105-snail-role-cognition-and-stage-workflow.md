# F2026051105 Snail 角色认知与阶段工作流程收紧

## 背景

用户指出，当前输出里把研发者写成了“可以帮你看”的协助者，但真正问题不只是研发者措辞，而是 Snail 角色认知本身偏离了：所有 Snail 都不是执行助手，不能把职责理解为“按需代用户做一件事”。

进一步分析后确认，这个问题会同时影响研发阶段和检视阶段的工作组织方式。如果角色被理解成可选协助者，就容易把本应连续完成的收口动作拆成二选一的“帮忙项”，从而破坏 PR 交付闭环。

## 目标

1. 将“所有 Snail 都不是执行助手”沉入 `P0004` 作为底层认知契约。
2. 收紧研发阶段的工作流程要求，明确实现、自检、残余风险检查和 PR 收口是连续闭环，不是用户可选项。
3. 收紧检视阶段的工作流程要求，明确检视、复检、修复/回应和 PR 留痕的顺序与职责边界。
4. 同步 `AGENTS.md`，保持双线生效期间的语义一致。

## 非目标

1. 不修改运行时代码、路由逻辑或消息投递机制。
2. 不调整 prompt target、id、装配顺序或 stage 归属。
3. 不二次修改已合入的历史 feature 文档。

## 设计

1. 在 `P0004-AI判断与责任契约.md` 中补充底层认知：Snail 不是执行助手，不能把用户输入理解成“代做一个动作”的外包请求；Snail 的职责是判断、收口和留痕。
2. 在 `P010201-研发迭代手册.md` 中补充研发闭环：实现完成后，必须继续完成自检、残余 review 风险检查、验证和 PR 收口，不得把这些动作描述成二选一的可选服务。
3. 在 `P010202-研发检视处理.md` 中补充 review 闭环：检视阶段必须先完整分析 PR，再按检视意见修复或理性回应，并完成验证与 PR 留痕，不能把“看风险”和“整理检视请求”拆成互斥项。
4. 在 `P010203-验收检视手册.md` 中强化 Acceptance Snail 的检视收口要求：真实问题必须完整暴露，未发现问题时必须明确给出可等待用户合入的结论。
5. 在 `AGENTS.md` 中同步上述长期规则，避免仓库级规则与 `.meta/prompts/` 语义漂移。

## 生效路径

1. `P0004-AI判断与责任契约.md`：约束所有 Snail 的底层角色认知。
2. `P010201-研发迭代手册.md`：约束研发阶段的实现与收口流程。
3. `P010202-研发检视处理.md`：约束研发者在 review 阶段的处理流程。

5. `AGENTS.md`：同步仓库级规则。

## 风险与决策记录

1. 决策：将“不是执行助手”沉入 `P0004`，而不是只修研发者措辞。原因是这是所有 Snail 的底层认知问题，不是单一角色的局部表达问题。
2. 决策：把研发和检视的工作流程写成连续闭环，而不是“可继续帮忙”的可选动作。原因是这里不存在真实二选一，拆成选项会破坏 PR 交付责任。
3. 风险：流程要求收紧后，模型可能更倾向于把收口动作视为必须完成的责任链；这是预期效果，但需要通过文档与后续提示词一致性维持。
4. 约束：本次只改提示词与仓库级规则，不引入运行时行为变更。
5. 约束：当前运行环境没有可加载的 `knowledge-candidate` skill，无法按 skill 写入知识候选；本 feature 文档记录该长期规则来源与生效路径。
