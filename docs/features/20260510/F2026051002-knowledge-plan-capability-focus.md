# F2026051002 知识飞轮计划能力导向修正

## 背景

PR145 的知识飞轮分阶段改造步骤中，把“Prompt 注入门禁调整”列为独立后续 PR。用户指出当前系统本来没有知识自动生效路径，如果后续能力按规则设计，也不应出现候选绕过治理自动生效的问题。因此，把“防止候选自动注入”规划成独立 PR，会把约束误写成功能动作，暗示系统存在一个本不该有的错误路径。

用户进一步明确：计划应聚焦要做什么、做完后能达成什么目的；不准做的事情可以写成要求或约束，而不是拆成具体 PR 动作。只要能力做对了，“防止”就是多余的。

## 目标

1. 将知识生命周期后续实现拆分改成目标能力导向。
2. 明确禁止事项是实现约束和验收要求，不是独立 PR 动作。
3. 去除“Prompt 注入门禁调整”这类防治型规划语义，改为“知识反哺接入能力”。
4. 把这条纠偏沉淀到长期核心文档，而不是二次修改已合入的 PR145 feature 文档。

## 非目标

1. 不修改 PR145 已合入的 feature 文档。
2. 不实现知识治理代码、schema 或 UI。
3. 不实现知识反哺能力。
4. 不调整 AI 原生工作原则提示词；PR146 已覆盖通用规划原则，本次只修正知识生命周期文档中的具体实现拆分。

## 设计

### 问题本质

原“Prompt 注入门禁调整”混淆了两类内容：

1. 目标能力：未来如果需要让已治理知识进入 prompt、skill、检查器或其他运行时能力，需要建设知识反哺接入能力。
2. 实现约束：候选知识不得自动注入 prompt，使用次数或正反馈不得替代治理裁决。

正确做法是把目标能力写成后续建设事项，把约束写入该能力的实现要求和验收标准。不能为了表达“不准做错”而单独规划一个“防止错误路径”的 PR。

### 文档修正

`docs/core/knowledge-lifecycle.md` 的“后续实现拆分边界”改为：

1. 明确拆分必须以正向能力为主线。
2. 明确禁止事项只能作为每项能力的实现约束和验收要求。
3. 将“建议顺序”改为“建议能力建设顺序”。
4. 将末尾能力改为“知识反哺接入能力”，描述为治理裁决明确允许后接入 prompt、skill、检查器或其他运行时能力。
5. 在实现约束中新增：不把约束、禁止事项或不存在的错误路径拆成独立防治型实现步骤。

## 生效路径

1. `docs/core/knowledge-lifecycle.md` 是知识闭环飞轮长期核心设计文档，后续知识飞轮实现必须按其能力导向拆分执行。
2. `docs/features/20260510/F2026051002-knowledge-plan-capability-focus.md` 记录本次纠偏的背景、设计取舍和验证。

## 改动范围

1. `docs/core/knowledge-lifecycle.md`
2. `docs/features/20260510/F2026051002-knowledge-plan-capability-focus.md`

## 验证

1. 对照用户反馈，确认文档不再把“防止候选自动注入”作为独立 PR 动作。
2. 对照 `docs/core/knowledge-lifecycle.md` 的核心模型，确认每条候选进入治理 feature、入口校验、查重定性和去向回写的边界保持不变。
3. 对照 PR146 的 AI 原生工作原则，确认后续拆分以语义闭合能力为主线，约束不被误写成需要长期记忆串联的防治型步骤。
4. 本 PR 仅修改文档，不需要运行构建或测试。

## 风险与决策记录

1. 决策：不修改 PR145 feature 文档。原因是已合入 feature 文档是历史交付记录；新结论应进入长期核心文档和当前 feature 文档。
2. 决策：保留“候选不自动注入 prompt”等约束。原因是这些仍是知识生命周期不变量，只是不应作为独立 PR 动作。
3. 决策：使用“知识反哺接入能力”替代“Prompt 注入门禁调整”。原因是后续真正要建设的是已治理知识如何进入运行时能力，而不是修补一个当前不存在、正确设计下也不应存在的漏洞。
