# F2026050904 知识闭环飞轮核心设计文档

## 背景

PR #136 尝试一次性完成知识文档权威源、候选审批、PR 落地、启动同步、运行时投影和知识中心展示等完整改造，改动范围过大，不利于分步审查和稳定交付。

当前阶段先把“知识闭环飞轮”的长期核心设计沉淀到 `docs/core`，作为后续拆分实现、检视和验收的裁决依据。用户反馈后确认，设计文档必须以知识治理流程为核心骨架，后半段应从“自动生效 + 正向反馈”调整为“知识中心发起 feature，由 Snail 与用户共同完成知识到系统提示词或其他长期入口的语义转化，并把最终裁决回写知识中心”。

## 目标

1. 以 PR #136 为输入，抽取知识全生命周期的长期模型和关键不变量。
2. 新增 `docs/core/knowledge-lifecycle.md`，明确知识从候选、初筛、治理 feature、语义审视、系统提示词转化、PR 合入、裁决回写到负反馈诊断的流程。
3. 将 PR #136 中过细的实现步骤收敛为后续多 feature 可复用的流程裁决依据。
4. 保留当前 feature 的需求结论、设计取舍、改动范围和验证记录。

## 非目标

1. 本 feature 不实现 PR #136 中的数据库 schema、API、UI、脚本或启动同步代码。
2. 本 feature 不创建 `docs/knowledge` 权威源目录，也不迁移现有数据库知识。
3. 本 feature 不决定每个后续拆分 PR 的具体边界，只提供拆分时必须遵守的核心模型。
4. 本 feature 不修改 `AGENTS.md`、`.meta/prompts` 或运行时 prompt 注入逻辑。

## 设计

新增核心设计文档 `docs/core/knowledge-lifecycle.md`，定位为 Snail Shell 知识闭环飞轮的长期流程入口。文档采用以下结构：

1. 文档定位，以及与 `docs/core/prompt-system-structure.md` 的关系。
2. 核心原则：知识是语义资产，候选不直接生效，知识中心不替代 Snail + 用户治理，正向反馈暂不纳入闭环。
3. 知识闭环总流程：候选识别、知识中心初筛、创建知识治理 feature、语义审视、裁决、系统提示词转化、PR 合入、裁决回写、负反馈诊断。
4. 各流程阶段的动作、边界和输出。
5. 知识中心状态、追溯要求和后续实现拆分边界。

设计取舍：文档不再以“分层模型 + 自动运行时生效 + 使用反馈”为主线，避免重复和偏离重点；改为以“知识如何通过 AI + 人治理转化为系统提示词或其他长期入口”为主线。

## 生效路径

1. `docs/core/knowledge-lifecycle.md` 作为后续知识相关设计、实现、测试和评审的核心裁决依据。
2. `docs/features/20260509/F2026050904-knowledge-flywheel-core-doc.md` 记录本 feature 的交付目标、范围和验证结果。
3. 后续实现 PR 需要引用该 core 文档，并在实际代码、测试、prompt 或用户手册中落实对应生效入口。

## 改动范围

1. 新增 `docs/core/knowledge-lifecycle.md`。
2. 新增 `docs/features/20260509/F2026050904-knowledge-flywheel-core-doc.md`。

## 验证

1. 检查新增 core 文档覆盖用户反馈后的核心生命周期：候选、初筛、知识治理 feature、Snail + 用户语义审视、系统提示词转化、PR 合入、裁决回写、负反馈诊断。
2. 检查新增文档符合 `docs/README.md` 的目录职责：长期模型进入 `docs/core`，本次交付记录进入 `docs/features`。
3. 初次运行 `npm run check` 时，build、lint 和前置测试通过，但执行到 `dist/tests/agent/managed-process-test.js` 时失败，错误为 `timeout escalation should be marked forced`；该次失败发生在文档改动之外的运行时测试。
4. 用户反馈后重写文档并再次运行 `npm run check`，build、lint 和全部 33 个编译后测试文件均通过。

## 风险与决策记录

决策记录：用户要求先从 PR #136 中拆出最关键的设计文档，不直接推进大规模实现。因此本 feature 只沉淀核心设计文档和 feature 记录，不做代码改造。

决策记录：知识生命周期设计以“知识中心发起治理 feature + Snail 和用户完成语义转化 + PR 合入长期入口 + 裁决回写知识中心”为目标模型。知识中心不直接替代系统提示词权威源，也不以正向使用反馈决定知识是否生效。

决策记录：负反馈是当前唯一需要设计的反馈形态。当同一知识再次被提取或同类问题再次出现时，Snail 与用户应在 feature 对话中定位既有知识和最终落地入口，分析为何没有生效，再决定是否调整长期入口。

当前没有未经确认的问题。

## 范围变更记录

1. 用户反馈后，将 core 文档从“分层模型 + 自动生效/反馈”重写为“流程主线 + Snail/用户治理 + 系统提示词转化 + 裁决回写”。
