# F2026050904 知识闭环飞轮核心设计文档

## 背景

PR #136 尝试一次性完成知识文档权威源、候选审批、PR 落地、启动同步、运行时投影和知识中心展示等完整改造，改动范围过大，不利于分步审查和稳定交付。

当前阶段先把“知识闭环飞轮”的长期核心设计沉淀到 `docs/core`，作为后续拆分实现、检视和验收的裁决依据。该设计文档需要重点回答知识从产生、候选、审批、文档落地、运行时生效、使用反馈到演进停用的完整生命周期。

## 目标

1. 以 PR #136 为输入，抽取知识全生命周期的长期模型和关键不变量。
2. 新增 `docs/core/knowledge-lifecycle.md`，明确知识权威源、运行时投影、状态流转和生效边界。
3. 将 PR #136 中过细的实现步骤收敛为后续多 feature 可复用的核心设计依据。
4. 保留当前 feature 的需求结论、设计取舍、改动范围和验证记录。

## 非目标

1. 本 feature 不实现 PR #136 中的数据库 schema、API、UI、脚本或启动同步代码。
2. 本 feature 不创建 `docs/knowledge` 权威源目录，也不迁移现有数据库知识。
3. 本 feature 不决定每个后续拆分 PR 的具体边界，只提供拆分时必须遵守的核心模型。
4. 本 feature 不修改 `AGENTS.md`、`.meta/prompts` 或运行时 prompt 注入逻辑。

## 设计

新增核心设计文档 `docs/core/knowledge-lifecycle.md`，定位为 Snail Shell 知识闭环飞轮的长期模型入口。文档采用以下结构：

1. 文档定位与裁决优先级。
2. 核心原则：文档权威源、数据库运行时投影、候选不直接生效、PR 合入不等于运行时生效、使用反馈不回写权威源。
3. 分层模型：观察层、候选层、审批层、文档权威层、运行时投影层、使用反馈层、演进治理层。
4. 知识实体和状态定义，包括候选状态、文档状态、运行时状态、PR 状态和变更请求状态。
5. 知识全生命周期总流程，覆盖识别、候选、审批、草稿、PR、合入、部署同步、生效、注入、反馈、更新、停用和归档。
6. 新增、更新、停用、替换、归档等典型流程。
7. 权威源、投影同步、prompt 注入、UI/API、审计追溯和后续拆分边界。

设计取舍：文档只定义长期模型和不变量，不把 PR #136 的具体文件清单、测试名或阶段节奏固化为核心规范，避免大 PR 被拆分后核心文档失效。

## 生效路径

1. `docs/core/knowledge-lifecycle.md` 作为后续知识相关设计、实现、测试和评审的核心裁决依据。
2. `docs/features/20260509/F2026050904-knowledge-flywheel-core-doc.md` 记录本 feature 的交付目标、范围和验证结果。
3. 后续实现 PR 需要引用该 core 文档，并在实际代码、测试、prompt 或用户手册中落实对应生效入口。

## 改动范围

1. 新增 `docs/core/knowledge-lifecycle.md`。
2. 新增 `docs/features/20260509/F2026050904-knowledge-flywheel-core-doc.md`。

## 验证

1. 检查新增 core 文档覆盖 PR #136 中的核心生命周期：候选、审批、文档 PR、合入、重启同步、运行时生效、使用反馈、更新停用。
2. 检查新增文档符合 `docs/README.md` 的目录职责：长期模型进入 `docs/core`，本次交付记录进入 `docs/features`。
3. 已运行 `npm run check`：build、lint 和前置测试通过，执行到 `dist/tests/agent/managed-process-test.js` 时失败，错误为 `timeout escalation should be marked forced`。本 feature 只新增 Markdown 文档，未修改运行时或测试代码，该失败记录为既有测试环境/用例问题，需后续独立处理。

## 风险与决策记录

决策记录：用户要求先从 PR #136 中拆出最关键的设计文档，不直接推进大规模实现。因此本 feature 只沉淀核心设计文档和 feature 记录，不做代码改造。

决策记录：知识生命周期设计以“文档权威源 + SQLite 运行时投影”为目标模型。PR 合入只是文档进入 main 的事实，运行时生效必须等待包含该文档的系统版本启动并完成同步。

当前没有未经确认的问题。
