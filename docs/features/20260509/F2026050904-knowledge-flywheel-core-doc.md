# F2026050904 知识闭环飞轮核心设计文档

## 背景

PR #136 尝试一次性完成知识文档权威源、候选审批、PR 落地、启动同步、运行时投影和知识中心展示等完整改造，改动范围过大，不利于分步审查和稳定交付。

当前阶段先把“知识闭环飞轮”的长期核心设计沉淀到 `docs/core`，作为后续拆分实现、检视和验收的裁决依据。用户反馈后确认，设计文档必须以知识治理流程为核心骨架：Snail 在工作中自动识别候选知识，通过最低门槛的候选进入知识治理 feature；治理 feature 中先查重，命中已有知识就是负反馈场景，未命中才是新增知识审视场景；治理结果可以是结论或 PR，但必须回写本条候选的最终去向。文档同时必须说明该目标模型与当前 `candidate -> approve -> active -> usage policy -> prompt injection` 链路的兼容和迁移边界。

## 目标

1. 以 PR #136 为输入，抽取知识全生命周期的长期模型和关键不变量。
2. 新增 `docs/core/knowledge-lifecycle.md`，明确知识从自动识别候选、入口校验、启动治理 feature、查重定性、负反馈或新增知识治理、产出结论/PR 到回写候选去向的流程。
3. 将 PR #136 中过细的实现步骤收敛为后续多 feature 可复用的流程裁决依据。
4. 保留当前 feature 的需求结论、设计取舍、改动范围和验证记录。

## 非目标

1. 本 feature 不实现 PR #136 中的数据库 schema、API、UI、脚本或启动同步代码。
2. 本 feature 不创建 `docs/knowledge` 权威源目录，也不迁移现有数据库知识。
3. 本 feature 不决定每个后续拆分 PR 的具体边界，只提供拆分时必须遵守的核心模型。
4. 本 feature 不修改 `AGENTS.md`、`.meta/prompts` 或运行时 prompt 注入逻辑。

## 设计

新增核心设计文档 `docs/core/knowledge-lifecycle.md`，定位为 Snail Shell 知识闭环飞轮的长期流程入口。文档采用以下结构：

1. 文档定位，以及与 `docs/core/prompt-system-structure.md` 的关系。
2. 核心模型：Snail 自动提交候选，通过入口门槛的候选启动治理 feature，feature 内先查重并区分负反馈/新增知识场景。
3. 与现有审批和运行时链路的关系：当前 `approve/active/usage policy` 是兼容路径，后续实现必须显式迁移，不能把未治理候选直接等同于长期规则。
4. 知识闭环总流程：候选识别、入口校验、创建治理 feature、查重定性、负反馈治理或新增知识审视、决定产物形式、必要时转化为系统提示词、回写知识去向。
5. 各流程阶段的动作、边界和输出，尤其是结论产物与 PR 产物都必须回写去向。
6. 知识本体状态、治理 feature 状态、治理裁决/去向状态的职责分离，以及追溯要求和后续实现拆分边界。

设计取舍：文档不再以“知识中心初筛批准后再治理”为主线，而是改为“通过最低门槛的候选进入治理 feature，每条候选必须有可追溯去向”。负反馈不是后置统计反馈，而是治理 feature 查重后发现已有知识时的场景定性。入口校验只处理明显误提取、低价值、批量合并和延后治理，不承担语义查重和最终裁决。

## 风险与决策记录

决策记录：用户要求先从 PR #136 中拆出最关键的设计文档，不直接推进大规模实现。因此本 feature 只沉淀核心设计文档和 feature 记录，不做代码改造。

决策记录：知识生命周期设计以“通过门槛的候选启动治理 feature + Snail 和用户先查重定性 + 负反馈或新增知识分流治理 + 结论/PR 产物 + 候选去向回写”为目标模型。知识中心不直接替代系统提示词权威源，也不以正向使用反馈决定知识是否生效。

决策记录：当前 `candidate | active | rejected | superseded | deprecated | archived` 仍是知识本体状态集合；治理 feature 状态和治理裁决/去向状态必须作为单独记录或派生展示，不得直接混入现有 `knowledge_item.status`。

决策记录：现有 `approve/active/usage policy/prompt injection` 链路在目标模型落地前是兼容路径；后续实现必须显式迁移或映射，不能无说明地废弃，也不能把未治理候选直接视为可注入规则。

决策记录：负反馈不是独立的后置统计流程，而是治理 feature 的查重结果之一。当本条候选命中已有重复或相关知识时，本次治理必须先定位旧知识和最终落地入口，分析为何没有生效，再决定是否调整长期入口或记录不调整理由。

当前没有未经确认的问题。

## 范围变更记录

1. 用户反馈后，将 core 文档从“分层模型 + 自动生效/反馈”重写为“流程主线 + Snail/用户治理 + 系统提示词转化 + 裁决回写”。
2. 用户进一步纠偏后，将流程主线从“知识中心初筛批准后发起治理”调整为“每条候选知识都启动治理 feature，并在 feature 内先查重定性为负反馈或新增知识”。
3. PR 检视后，将“每条候选自动启动 feature”收敛为“通过入口门槛的候选进入治理 feature，每条候选都有可追溯去向”，并补充误提取、低价值、批量候选和延后治理的节流边界。
4. PR 检视后，补充目标治理模型与当前审批 API、本体状态、usage policy 和 prompt 注入链路的兼容和迁移要求。
