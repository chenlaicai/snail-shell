# F2026060701 [testing] AI 时代测试范式转变：从覆盖率填充到业务行为契约守护

## 背景

用户在 Snail Shell 项目的 AI 辅助开发实践中，发现两个互相关联的测试质量问题：

**问题一：AI 写测试是为了写而写**

AI 被要求"写测试"时，默认行为是扫描已有函数签名和代码分支，然后生成覆盖这些结构的用例。这些用例覆盖的是代码结构（how），而非业务行为（what）。结果是测试套件膨胀但守护价值低——代码一重构就全挂，业务逻辑出错却未必能捕获。

**问题二：AI 为了让测试通过而修改主代码**

当测试断言绑定在实现细节上（特定函数名、特定调用顺序、特定 CSS class），AI 遇到测试挂了，本能反应是改主代码让测试通过，而不是修正测试。这颠倒了测试与被测代码的关系——测试应该是行为的守护者，而不是实现的枷锁。

**问题三（AI 时代的放大效应）**

在人工编码时代，代码变化频率低、变化幅度小，上述问题虽存在但影响可控。AI 时代代码发生不兼容修改是常态——AI 重构代码的速度和频率远超人类，如果测试绑在实现细节上，每次 AI 改代码都会触发大量测试维护工作，测试从"安全网"退化为"摩擦力"。

这三个问题的共同根因：**测试的编写范式不适应 AI 时代的能力结构**。人工时代的测试范式假设"代码变化慢、人能维护测试"，AI 时代需要"代码变化快、测试只守护业务行为"。

关联 feature：
- F2026052102（测试重构：删除覆盖率填充式测试）：已建立源码字符串匹配反模式的识别和清理规则，本次在此基础上建立完整的 AI 时代测试范式
- F2026051002（AI 原生工作原则）：已建立"AI 不应机械照搬人类时代工作方式"的基础判断契约，本次将此原则具体应用到测试领域

## 目标

建立适应 AI 时代能力结构的测试编写范式，确保：
- 测试守护的是业务行为，而非代码结构
- 测试场景来源于 feature spec 的业务行为定义，而非 AI 从代码中反推
- 测试维护成本与 AI 代码变更频率匹配
- 核心业务场景有精确的行为契约守护

### P1 — 测试编写范式转变

- 调整 Feature 文档模板，增加"核心业务行为"章节（设计阶段由 AI 起草、人认可）
- 定义"行为契约测试"与"实现绑定测试"的边界
- 建立测试失败时的决策规则（从根源上消除"改主代码绕过测试"的动机）

### P2 — 测试分层策略

- 按守护价值对测试分层：行为契约 > 回归测试 > 可访问性契约
- 定义每层的编写规则和维护策略
- 建立"回归测试只出可退"的增量守护机制

### P3 — 测试质量审查与验收

- 在检视流程中增加"测试是否绑定实现"的对抗性检查
- 建立 AI 编写测试时的自检清单
- 定义验收标准：实现后的首个 feature 必须验证测试是否断言外部可观测行为

## 非目标

- 不删除所有现有测试——F2026052102 已完成源码字符串匹配测试的清理，本次不重复。现有 workspace/persistence 层测试断言的是状态转移和数据行为，属于行为契约测试，不在清理范围内
- 不引入新的测试框架或工具——现有 Vitest + 自定义 runner 已满足需求
- 不追求测试覆盖率指标——覆盖率不是目标，业务守护是目标
- 不禁止所有 mock——禁止的是 mock 实现细节，不禁止 mock 外部依赖（数据库、第三方 API）

## 设计

### 核心概念：行为契约 vs 实现绑定

**行为契约测试**的特征：
- 测试描述的是业务行为："当用户创建 issue 但未指定 SOP 时，系统应报错"
- 断言的是外部可观测行为：函数返回值、状态变化、事件触发、错误抛出
- 场景来源于 feature spec 的核心业务行为列表（设计阶段已定义）
- 代码重构时只要行为不变，测试就不该挂
- 即使测试挂了，说明的是"行为被改变了"，需要人工判断是有意变更还是回归

**实现绑定测试**的特征：
- 测试描述的是代码结构："调用了 validateSOP() 函数"
- 断言的是内部实现：函数调用次数、调用参数、内部状态、调用顺序
- 场景来源于 AI 扫描代码结构
- 代码重构（提取函数、重命名、调整调用顺序）就会导致测试挂
- 测试挂了无法区分"行为变了"还是"实现变了"

**边界判定规则**：

| 判定维度 | 行为契约（保留） | 实现绑定（禁止） |
|----------|-----------------|-----------------|
| 断言对象 | 外部可观测行为（输入/输出/状态变化/错误） | 内部实现（函数调用/参数/调用顺序/内部状态） |
| 变更敏感度 | 只在行为变更时挂 | 实现微调即挂 |
| 测试描述 | "当 X 时，应该 Y" | "函数 A 应调用函数 B" |
| 场景来源 | feature spec 的核心业务行为列表 | AI 从代码结构推导 |

**"业务场景"的判定标准**：

一个业务场景必须同时满足：
1. **有明确的行为**：系统做了什么（状态转移、数据变更、事件触发、错误抛出）
2. **外部可观测**：不需要知道内部实现就能从外部观察到该行为是否发生
3. **可独立验证**：只看输入和输出（或状态变化），不看内部调用链

| 是业务场景 | 不是业务场景 |
|-----------|-------------|
| Issue 创建时未指定 SOP → 报错 | validateSOP() 被调用了 1 次 |
| Stage 从 design 转移到 development | transferStage() 内部调用了 updateDB() |
| 对话分页查询返回正确的消息列表 | queryMessages() 使用了 LIMIT OFFSET |
| SOP 快照在 issue 创建时被冻结 | createSnapshot() 的参数是 issue 对象 |

**容易误判的边界案例**：

| 描述 | 判定 | 原因 |
|------|------|------|
| "createIssue 应先调用 validateSOP 再调用 saveToDB" | 不是 | 断言的是调用顺序（内部实现），不是外部可观测行为 |
| "createIssue 未指定 SOP 时应抛出 InvalidSOPErrror" | 是 | 错误抛出是外部可观测行为 |

判定方法：**断言的是外部可观测行为（输入/输出/状态变化/错误），还是内部实现（函数调用/参数/调用顺序/内部状态）？** 前者是业务场景，后者不是。

**"外部可观测"标准的适用范围**：此标准适用于行为契约测试（本文档的核心对象）。其他类型的测试（设计契约测试、性能测试等）不受此标准约束——它们可以测试内部状态机、缓存行为、日志输出等非外部可观测的行为，但仍须避免落入禁止层（源码字符串匹配、实现绑定断言）。

### P1 详设：测试编写范式

**规则 0：测试场景来源——Feature spec 的核心业务行为列表**

测试场景不是 AI 从代码中推导的，而是在设计阶段就已经定义在 feature spec 中。

**适用范围**：修改系统功能语义的 PR。判断标准：PR 是否改变了系统的功能语义（输入/输出/状态转移/错误类型）？是 → 需要"核心业务行为"章节；否 → 不需要。不要求的 PR 仍须遵循行为契约规则（断言外部可观测行为），场景来源为开发者判断 + 审查者把关。

**边界案例**：

| PR 类型 | 是否需要 | 原因 |
|---------|----------|------|
| 新增 API 端点 | 需要 | 新增输入/输出 |
| 修改 Stage 转移逻辑 | 需要 | 改变状态转移 |
| 修改错误类型（Error → ValidationError） | 需要 | 改变错误类型 |
| 修改错误消息措辞 | 不需要 | 措辞不是功能语义 |
| CSS 样式调整 | 不需要 | 不影响功能语义 |
| 依赖版本升级 | 不需要 | 不改变系统行为 |
| 纯重构（提取函数、重命名） | 不需要 | 不改变功能语义 |
| 日志格式调整 | 不需要 | 不影响功能语义 |
| 性能优化（缓存、索引） | 不需要 | 不改变功能语义 |
| 重构 + 改变错误处理逻辑 | 需要 | 改变了错误类型/行为 |

Feature 文档模板新增"核心业务行为"章节（实际模板内容，放入 docs/README.md）：

```markdown
## 核心业务行为

本 feature 涉及的核心业务行为列表。每条行为是"当 X 时，应该 Y"的形式，
断言的是外部可观测行为（输入/输出/状态变化/错误），不是内部实现。

| # | 场景 | 预期行为 | 测试覆盖 |
|---|------|----------|----------|
| B1 | 当 X 时（触发条件和上下文） | 系统应该 Y（具体可观测结果：返回值/状态变化/错误） | tests/xxx-test.ts::testFunctionName |

列说明：
- **#**：行为编号（B1, B2, ...）
- **场景**：触发条件和上下文，必须包含"当……时"的条件描述，不能只写动作（如"创建 issue"）
- **预期行为**：系统的具体可观测结果，不能只写"成功"或"正确"（如"返回 201 并创建 issue 记录"）
- **测试覆盖**：实现阶段填写，格式为"测试文件路径::测试函数名"
```

**行为列表的使用规则**（放入 developer handbook，不在模板中）：

- Feature 文档是 per-PR 的，生命周期就是一个 PR，不需要持续维护
- 粒度指导：一条行为是一个可独立测试的断言。判定标准：能否为这条行为写一个不超过 20 行的测试？能 → 粒度合适；不能 → 需要拆分
- 由 AI 在设计阶段根据业务需求起草，人认可后进入实现阶段
- 实现阶段 AI 根据此列表编写行为契约测试
- 实现阶段可以修改行为列表（新增、修正、删除），无需升级给用户，但必须在本 feature spec 的"范围变更记录"章节中说明修改原因和内容
- 只有当修改涉及 feature 的核心目标或非目标时，才需要升级给用户确认
- 实现阶段结束前，每条行为都必须有对应的测试覆盖记录（实现完成的验收条件）
- PR 合入后，此文档作为历史记录，不需要更新
- 空值处理：如果"核心业务行为"章节存在但列表为空，AI 不得自行推导测试场景，必须升级给用户要求补充行为列表后再编写测试

**行为列表与"修改设计"的边界**：行为列表的细节调整（新增边界条件、修正措辞、删除过时条目）不属于"修改设计"，不受 developer handbook 阶段二"不得自行修改设计"的约束。只有行为列表变更涉及 feature 的核心目标或非目标时，才属于"修改设计"，需要升级给用户。

这样做的好处：
- 测试场景的语义来源是 feature spec（有业务意图），而非代码（只有实现细节）
- 人在设计阶段审核场景，而非事后审核测试代码
- AI 在实现阶段只需翻译（场景 → 测试），不需要推导（代码 → 场景）
- 模板与规则分离：模板是干净格式，规则在 handbook 中

**规则 1：从业务行为到测试**

实现阶段，AI 根据 feature spec 的核心业务行为列表编写测试：

```
1. 读取 feature spec 的"核心业务行为"章节
2. 为每条行为编写测试（可多个，覆盖不同条件），断言外部可观测行为
```

所有测试都从行为列表来——边界条件如果值得测试，就应该在行为列表中（由设计阶段定义或实现阶段补充，见范围变更记录）。不存在"行为列表之外的补充测试"。

禁止的行为：
```
1. 扫描函数签名 → 为每个函数/分支写测试
2. 断言函数内部行为（调用顺序、参数、内部状态）
3. 为代码结构写测试（不为函数签名、分支覆盖、调用顺序写测试）
4. 在行为列表之外编写"补充"测试（没有行为列表条目对应的测试）
```

**规则 2：测试失败时的决策规则**

这条规则不是禁止 AI 改主代码——那不可执行。而是通过确保测试是行为契约测试，从根源上消除"改主代码绕过测试"的动机。

当测试失败时，AI 必须按以下顺序判断：

1. **代码变更是否是有意的*行为*变更？**（注意区分：有意的代码变更 ≠ 有意的行为变更）
   - 有意的行为变更（用户明确要求改变系统行为）→ 更新测试以匹配新行为
   - 有意的代码变更但非有意的行为变更（重构、优化、可读性改进）→ 测试不该挂；如果挂了，说明引入了无意的行为变更 → 进入步骤 2
   - 无意的代码变更 → 进入步骤 2

2. **测试是否断言的是外部可观测行为？**（行为契约测试）
   - 是 → 这是无意的回归 → 修复主代码
   - 否 → 进入步骤 3

3. **测试断言的是内部实现**（函数调用、内部状态、源码结构）
   - → 删除测试，不要改主代码来让它通过

**预防措施**：在编写测试时就确保它是行为契约测试（规则 1），这样测试失败时的判断就自然落在步骤 1 或 2，不需要走到步骤 3。

**规则 3：mock 边界**

- 允许 mock：数据库、文件系统、网络请求、第三方 API、时间/随机数
- 禁止作为断言依据：mock 的调用次数（N 次）、调用参数、调用顺序——这些是实现细节
- 允许作为行为否定断言：断言某个函数未被调用（`expect(fn).not.toHaveBeenCalled()`）——"当 X 时，Y 不应发生"是行为契约
- 允许作为隔离手段：mock 被测模块的内部函数（无论是否有独立测试覆盖），目的是隔离复杂依赖、不是断言实现。但测试必须断言的是外部可观测行为（规则 1）

mock 是隔离手段，行为契约是断言约束——两者独立判定。一个测试可以 mock 内部函数（隔离），同时断言外部可观测行为（契约）。

### P2 详设：测试分层策略

**第一层：行为契约测试（最高优先级）**

- 守护对象：核心业务流程的行为正确性
- 编写时机：新功能开发时，基于业务场景编写
- 维护策略：行为变更时更新，代码重构时不应需要更新
- 示例：
  - Stage 生命周期状态转移（design → development → review → merge）
  - SOP 快照在 issue 创建时的冻结行为
  - 对话持久化和分页查询的正确性
  - Issue 未指定 SOP 时的报错行为

**第二层：回归测试（增量守护）**

- 守护对象：已发现的真实 bug 不再复现
- 编写时机：发现 bug 并修复后，补写对应的回归测试
- 维护策略：只出可退——只在发现 bug 时增加，不为覆盖率而增加；当被测功能被移除或行为被永久变更时，关联的回归测试可以删除
- 规则：每个回归测试必须关联一个真实的 bug 描述，说明"曾经出过什么问题"

**行为契约测试与回归测试的关系**：

两者的区分维度不是"什么时候写的"，而是"断言的是什么"：
- 行为契约测试：断言业务行为的正确性（如 Stage 状态转移、SOP 快照冻结）
- 回归测试：断言某个已知 bug 不再复现

功能开发时写的测试，如果断言的是业务行为，就是行为契约测试。现有 workspace/persistence 层的测试（Stage 生命周期、SOP 快照、对话持久化）属于这一类——它们不是回归测试，而是行为契约测试。

两层可以重叠：一个测试可以同时是行为契约测试（守护业务行为）和回归测试（防止已知 bug 复现）。

**第三层：可访问性契约测试**

- 守护对象：面向辅助技术的运行时 API 契约（如 `aria-current`）
- 编写时机：实现可访问性特性时
- 断言方式：通过运行时 DOM 行为验证，禁止源码字符串匹配
- 参见 F2026052102 中的 aria-current 决策记录

**禁止层：实现绑定测试**

- 源码字符串匹配（读取文件 + 字符串包含检查）
- 函数调用次数/参数断言（expect mock toHaveBeenCalledWith）
- 内部状态断言（直接访问模块私有变量）
- CSS class 名称断言（通过源码匹配）

### P1.5 详设：AI 测试编写指令模板

**问题**：handbook 规则是长期生效的通用约束，但 AI 被要求写测试时收到的具体指令才是真正的触发器。最高杠杆的改动是在 AI 收到"写测试"任务时的 prompt 中嵌入行为契约约束。

**指令模板**（嵌入 developer playbook 的测试编写阶段）：

```
编写测试前，读取当前 feature spec 的"核心业务行为"章节。
该章节在设计阶段已由 AI 起草、人认可，是测试场景的唯一来源。

如果"核心业务行为"章节不存在或列表为空：
- 不得自行推导测试场景
- 升级给用户要求补充行为列表，等待回复后再编写测试

按以下顺序编写测试：
1. 为"核心业务行为"中的每条行为编写测试（可多个，覆盖不同条件），断言外部可观测行为
2. 所有测试都必须对应行为列表中的某一条——边界条件如果值得测试，应在行为列表中（设计阶段定义或实现阶段补充并记录到范围变更记录）
3. 不为代码结构写测试（不为函数签名、分支覆盖、调用顺序写测试）
4. 实现阶段结束前，回填 feature spec 中每条行为的"测试覆盖"列

测试失败时的处理：
- 如果是有意的行为变更（用户明确要求改变系统行为）→ 更新测试
- 如果是有意的代码变更但非有意的行为变更（重构、优化）→ 测试不该挂，挂了说明引入了无意的行为变更 → 修复主代码
- 如果测试断言的是内部实现（函数调用/内部状态）→ 删除测试
```

**生效位置**：developer playbook 的"阶段四：自检与测试"阶段，作为 AI 收到测试编写任务时的直接指令。

### P3 详设：测试质量审查

**开发者自检清单（提交 PR 前）**

```
模板完整性：
□ feature spec 包含"核心业务行为"章节（设计阶段已定义，实现阶段可修改，见范围变更记录）
□ 每条行为的"测试覆盖"列已填写（测试文件路径::测试函数名）

测试质量：
□ 每个测试用例对应 feature spec 中的一条业务行为（无行为列表之外的测试）
□ 断言的是外部可观测行为（输入/输出/状态变化/错误），而非内部实现
□ mock 仅作为隔离手段，不作为断言依据
□ 回归测试关联了真实的 bug 描述
□ 无失效测试（被测功能已移除的测试已清理）
```

**审查者对抗性检查（检视时）**

```
□ 测试是否对应 feature spec 中的核心业务行为？
□ 断言的是外部可观测行为，还是内部实现（函数调用/参数/调用顺序）？
□ 如果删除测试中的 mock，断言是否仍然成立？（成立 = 行为契约；不成立 = 可能绑定了实现）
□ 是否存在为覆盖率而写的测试？
□ 是否存在源码字符串匹配反模式？
```
