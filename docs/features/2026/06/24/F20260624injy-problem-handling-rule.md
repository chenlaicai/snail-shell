# F20260624injy [prompt] 问题处理行为准则

<!-- [design-time] 以下章节在需求收敛与设计阶段（代码前）完成并锁定 -->
<!-- 进入实现阶段后不得单方面修改，如需变更须通过问题卡片向用户提出并确认 -->

## 问题描述

AI 用"后续优化""技术债"等说辞逃避立即解决问题的责任：

1. 发现问题后错误定性（把 bug 说成"优化"）
2. 提出"临时方案"后声称"后续单独优化"
3. 没有创建追踪机制 → 问题永远不会被解决

### 实际案例

**场景**：getUnreadMessages 内部调用 listByStage(stageId) 默认 limit=50，只取最近 50 条消息，再在 JS 层过滤 m.id > cursor。长对话中如果 cursor 之前有 60 条消息，第 1-10 条会被静默截断。

**AI 的错误回应**：
- 把功能 bug 说成"优化问题"
- 提出"临时方案"（全量加载再过滤）后声称"后续单独优化"
- 没有创建追踪机制，问题永远不会被解决

## 设计方案

在 T-01 的 `<execution>` 部分追加两条规则：

```
- 发现问题必须解决，不逃避。一次 PR 可以包含多个问题修复，做好规划、说清楚即可
- 禁止用"后续优化""技术债"等说辞逃避立即解决问题的责任。如果问题确实超出当前 PR 能力，必须说明具体原因和具体后续计划
```

## 设计决策

| 决策点 | 结论 | 理由 |
|--------|------|------|
| 规则焦点 | 行为而非术语 | 术语可以绕过，行为无法绕过 |
| 态度 vs 规则 | 态度优先，规则可执行 | 用户强调"做事风格"，但规则需要边界 |
| 问题处理 | 发现问题就解决 | 不用"不影响当前任务"作为逃避借口 |
| 合理边界 | 允许超出当前 PR 能力的情况 | 必须说明具体原因和具体后续计划 |
| 放置位置 | 追加到 `<execution>` | 不新增标签，避免标签膨胀 |
| 格式决策 | 不新增标签 | XML 标签只是分隔命令和上下文，核心是内容质量 |

## 逃避行为 vs 合理边界

| 逃避行为 | 合理边界 |
|----------|----------|
| "这是个优化问题" | "这个问题需要架构重构，具体原因是..." |
| "后续单独处理" | "这个问题依赖 X 未完成，计划是..." |
| "技术债" | "这个问题需要用户决策，已记录等待用户确认" |

## 与现有规则的关系

- **T-01 `<execution>`** 已有"完整分析、完整实现"——新规则补充了"发现问题后必须处理"的具体行为
- **通用指南 - 分步原则** 已禁止"临时方案 vs 完整方案"的伪选项——新规则补充了"后续优化"这个具体逃避模式

## 核心业务行为

- 当 AI 发现问题时，必须解决，不逃避
- 当 AI 建议"后续处理"时，必须说明具体原因和具体后续计划
- 当 AI 用"后续优化""技术债"等模糊话术时，视为空头支票
