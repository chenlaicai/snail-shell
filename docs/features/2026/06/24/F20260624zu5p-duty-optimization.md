# F20260624zu5p [sop] 职责优化：对抗机制、质量门禁与流程补全

<!-- [design-time] 以下章节在需求收敛与设计阶段（代码前）完成并锁定 -->
<!-- 进入实现阶段后不得单方面修改，如需变更须通过问题卡片向用户提出并确认 -->

## 背景

当前 code-delivery SOP 在实际运行中暴露了 10 个问题，覆盖四个类别：

1. **SOP 规则缺失**：PR 标题同步、检视后通知、设计文档输出、前端覆盖、开发者自检
2. **SOP 规则执行不力**：签名合规（advisory）、审查报告中的变体话术绕过
3. **对抗机制结构性缺陷**：两位架构师/审查者缺乏独立分析保障，容易"确认偏误"
4. **AI 思维模式问题**：用当前代码逻辑反驳用户的修改要求

这些问题导致设计质量不稳定、审查流于形式、用户无法看到设计文档、前端修改被遗漏。

### 问题依赖关系

问题之间存在依赖链，优化方案应按依赖顺序实施：

| 上游问题 | 下游问题 | 依赖说明 |
|---------|---------|---------|
| 4/5 对抗机制 | 8 忽略小问题 | 对抗审视有效 → 审查者不会放过小问题 |
| 4/5 对抗机制 | 9 忽略前端 | 对抗检查点包含前端维度 → 自然覆盖 |
| 7 不输出文档 | 6 用代码反驳用户 | 都是 AI 与用户信息不对称 |
| 8 审查报告结构化 | 10 开发者自检 | 自检清单 = 审查清单子集 |

**含义**：解决问题 4/5 的对抗机制改造，会自动改善问题 8 和 9。问题 10 的自检清单应复用问题 8 的结构化模板。

## 目标

### P1 — 结构性改造

1. 改造设计阶段的对抗机制：从"一方主导 + 另一方审视"改为"背靠背独立分析 → 交换对抗 → 合并收敛"
2. 设计文档锁定前必须输出给用户审阅，禁止架构师自行猜测用户意图
3. 审查报告结构化：每个问题必须有"处置方式"字段，禁止变体话术绕过

### P2 — 规则补全与原则提取

4. PR 标题特性编号与 Feature 文档编号一致性检查
5. 检视后在系统内呼叫对应 role instance
6. 签名合规提升为 required
7. 变更影响分析增加前端强制维度
8. 开发者自检步骤（自检清单 = 审查清单子集）
9. 3 条通用原则提取到 B-01（禁止猜测、禁止用代码反驳、审视展示独立分析）

## 非目标

- 不改变 SOP 的四阶段结构（design → development → review → merge）
- 不改变特性编号规则（创建后终身不变）
- 不引入自动化校验机制（本次优化以 SOP 规则和 skill 文件为主）
- 不改变 stage transition 的用户确认机制

## 核心业务行为

| # | 场景 | 预期行为 | 测试覆盖 |
|---|------|----------|----------|
| B1 | 当 design 阶段开始时 | 两位架构师各自独立完成分析后才交换方案，架构师-1 聚焦业务/用户/前端视角，架构师-2 聚焦技术/架构/风险视角 | |
| B2 | 当审视者表示同意时 | 必须先展示独立分析过程（分析了什么 → 得出什么结论 → 与对方对比），不能只输出"同意" | |
| B3 | 当设计文档准备锁定时 | 必须先输出完整内容给用户确认；用户确认后才能锁定；有疑问必须向用户确认，禁止自行猜测；用户对部分内容有异议时，针对异议点局部回退重新分析 | |
| B4 | 当合入者执行 squash 时 | 必须核对 PR 标题中的特性编号与当前 Issue 关联的 Feature 文档编号一致 | |
| B5 | 当审查者提交检视意见时 | 必须在 PR 上评论并通过 message-payload 在系统内呼叫对应 role instance | |
| B6 | 当审查者提交审查报告时 | 每个问题必须有"处置方式"字段且只能填"在当前 PR 修复"，禁用"不堵塞/可遗留/建议合入"等变体话术 | |
| B7 | 当开发者提交 PR 前 | 必须完成结构化自检（自检清单 = 审查清单子集）并写入 gate_evidence | |
| B8 | 当架构师/开发者回应用户修改要求时 | 不得以"当前代码是这样做的"作为反驳，必须分析用户意图和新逻辑的合理性 | |
| B9 | 当 PR 评论需要签名时 | 签名中的角色名和 Snail 名称必须与当前 system prompt 注入的值严格一致，合规性为 required | |

## 设计

### P1 详设

#### D-对抗：对抗机制改造

**当前问题**：两位架构师共享完全相同的上下文（系统提示词、代码库、需求描述），"相同输入 + 相同角色 → 相同输出"，导致对抗审视流于形式。

**改造方案**：从"一方主导 + 另一方审视"改为"背靠背独立分析 → 交换对抗 → 合并收敛"。

| 步骤 | 架构师-1 | 架构师-2 | 产出 |
|------|---------|---------|------|
| Phase 1 独立分析 | 业务流程、用户视角、功能完整性、前端交互 | 技术架构、系统边界、变更影响、风险点、后端约束 | 各自的独立分析文档 |
| Phase 2 交换审视 | 审视架构师-2 的方案 | 审视架构师-1 的方案 | 审视报告（风险点 ≥2、遗漏场景 ≥1、替代方案 ≥1） |
| Phase 3 合并收敛 | 合并讨论，解决分歧 | 合并讨论，解决分歧 | 最终方案 |

**关键约束**：

1. **角度分工**：架构师-1 聚焦业务/用户/前端，架构师-2 聚焦技术/架构/风险。两人分析角度不同，即使看到对方的方案也不会被完全引导
2. **质疑义务**：审视者必须产出具体价值——风险点、遗漏场景、替代方案。审视报告有最低数量要求
3. **禁止无条件同意**：审视者在同意任何一点之前，必须先展示自己的独立分析过程。禁止"分析全面，同意方案""没有补充意见"作为审视的唯一输出
4. **审视质量检查**：审视意见少于 2 条风险点 + 1 个遗漏场景 + 1 个替代方案时，视为审视不充分

**对抗审视检查点**（在现有基础上补充）：
- 是否有未经用户确认的假设被当作确定决策？
- 前端影响是否被遗漏？
- 变更影响分析是否覆盖后端/前端/提示词三个维度？

**变更影响分析强制维度**（整合自 D-前端）：
- 后端：API、数据模型、业务逻辑、配置
- 前端：UI 组件、交互流程、状态管理、路由
- 提示词/SOP：相关 skill 和 SOP 的变更

#### D-输出：设计阶段强制输出

**当前问题**：两位架构师在设计收敛后直接锁定文档，用户无法看到设计内容。有疑问时两人自行猜测用户意图。

**改造方案**：

1. **强制输出**：设计文档锁定前，必须将完整文档内容通过消息输出给用户审阅
2. **确认机制**：整体确认 + 局部异议回退。用户确认后才能锁定
3. **局部回退**：用户对部分内容有异议时，只针对异议点重新分析，不需要整体回退
4. **禁止猜测**：任何无法从需求、历史文档、代码中确定的决策，必须向用户确认。两人自行猜测达成的共识视为无效
5. **提醒机制**：用户长时间未确认时，系统提醒一次（不设超时，用户是最终决策者）

#### D-审查：审查报告结构化

**当前问题**：审查者用"不堵塞，可遗留后续""不影响，建议合入"等变体话术绕过"所有问题必须在当前 PR 修复"的规则。

**改造方案**：

1. **结构化模板**：审查报告中每个问题必须有"处置方式"字段，只允许填"在当前 PR 修复"，不允许填"后续优化""不堵塞"
2. **自检**：审查者在提交审查报告前，必须检查报告中是否有任何"可遗留""不堵塞""建议合入"的表述
3. **禁用话术清单**：在 adversarial-check.md 的 MUST NOT 列表中增加变体话术："不堵塞""可遗留""建议合入""后续优化""不影响功能""不影响，建议合入"

#### D-原则：通用原则提取到 B-01

**当前问题**：部分约束具有通用性（不局限于 code-delivery SOP），但当前只写在 SOP skill 文件中，其他 SOP 无法受益。

**分层标准**：原则层面约束"做什么"，SOP 层面约束"怎么做"。

**提取到 B-01-身份与责任契约.md 的 3 条通用原则**：

| 原则 | 来源 | 放入 B-01 的分区 | 说明 |
|------|------|-----------------|------|
| 禁止猜测用户意图 | B3 的通用部分 | 输入处理 | 任何无法从已有信息确定的决策，必须向用户确认 |
| 禁止用代码反驳用户 | B8 | 行为原则 | 当前代码逻辑不是正确性论据，必须分析用户意图和新逻辑合理性 |
| 审视必须展示独立分析过程 | B2 | 协作协议 | 同意任何观点前，必须先说明自己分析了什么、得出什么结论 |

**保留在 SOP/skill 的流程实现**：
- 背靠背独立分析 + 角度分工（B1 的实现细节 → cd-design/cross-review.md）
- 设计文档锁定前输出给用户确认 + 局部异议回退（B3 的实现细节 → cd-design/workflow.md）
- B4-B7、B9 不变

**与 SOP 的关系**：B-01 中的通用原则是"上位约束"，SOP skill 中的流程步骤是"下位实现"。SOP 不得违反 B-01 原则。

### P2 详设

#### D-标题：PR 标题特性编号同步

**改造方案**：
- 合入阶段增加硬条件：PR 标题中的特性编号必须与当前 Issue 关联的 Feature 文档编号一致
- 如果不一致，合入者必须先修正 PR 标题再 squash
- 开发者在 Feature 文档编号变化时有主动更新 PR 标题的责任

#### D-通知：检视后系统内呼叫

**改造方案**：
- `cd-review` Phase 5 增加步骤：PR 评论完成后，必须在 Snail Shell 系统中通过 `message-payload` 向开发者发送消息，@对应 role instance
- 消息内容包含：PR 链接、检视结论摘要、待处理问题列表

#### D-签名：签名合规提升为 required

**改造方案**：
- 将 `cd-shared/references/pr-signature.md` 的合规性从 advisory 提升为 required
- 将 `code-delivery.yaml` 中 `rev-03` 的 `required` 从 `false` 改为 `true`
- 合入阶段增加硬条件：PR 评论签名合规

#### D-前端：变更影响分析强制维度

**改造方案**：变更影响分析强制维度清单已整合到 D-对抗 的"变更影响分析强制维度"和"对抗审视检查点"中。对抗审视检查点增加"前端影响是否被遗漏？"。

#### D-自检：开发者自检

**改造方案**：
- 在 `cd-development` Phase 3（实现）和 Phase 4（验证与 PR 提交）之间增加 Phase 3.5：开发者自检
- 自检清单 = 审查清单的子集：
  1. 对照核心业务行为列表逐条确认覆盖
  2. 对照设计约束确认无违反
  3. 检查边界条件和错误处理
  4. 检查前端/后端是否同步修改
  5. 检查"为什么"注释覆盖非显而易见的逻辑
- 自检结果写入 gate_evidence

#### D-思维：禁止用代码反驳用户

**改造方案**：通用原则已提取到 B-01（见 D-原则）。SOP 层面无需重复定义，B-01 原则作为上位约束自动生效。

## 设计约束摘要

- **边界**：不改变 SOP 四阶段结构，不改变特性编号规则，不引入自动化校验
- **关键决策**：对抗机制采用"角度分工"而非"物理隔离"；确认机制采用"整体确认 + 局部异议回退"；审查报告采用结构化模板约束而非文字禁用；通用原则提取到 B-01（上位约束），SOP 实现细节保留在 skill 文件
- **非目标约束**：不处理自动化校验、不处理 stage transition 机制变更
- **语义不变量**：审视者必须产出独立分析，不能只输出"同意"；设计文档必须经用户确认后才能锁定
- **路径核实**：改动范围中的文件路径需在开发阶段核实实际位置（skill 文件可能位于 `data/file/skills/` 或 `.claude/skills/`）
