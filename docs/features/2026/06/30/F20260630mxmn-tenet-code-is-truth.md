# F20260630mxmn [prompt] 消除迁移思维：cd-design 审视清单补全

## 背景

F2026052204（2026-05-22）确立了"代码仓完美状态原则"，删除了 `src/persistence/migrations.ts`，并在 S-03 开发者手册中写入了三条硬性规则（禁止 ALTER TABLE、禁止迁移脚本、不兼容变更由人手工处理）。

然而，此规则在后续的架构师交叉审视中**反复被违反**。架构师在审视数据库 schema 变更时，本能地提出"需要迁移策略"、"ALTER TABLE ADD COLUMN 是幂等的"等建议。

### 根因分析

**第一轮诊断（架构师-1）**：问题在 tenet 层——T-01 的"不写向后兼容代码"太抽象，AI 无法映射到 schema 变更场景。需要在 T-01 新增"代码即真相"约束。

**对抗性审视（架构师-2）**：此诊断有三个问题：

1. **`<constraints>` 层级误用**：T-01 现有 constraints 都是元认知约束（关于 agent 如何思考），而"代码只描述最终状态"是实践约束（关于代码仓如何被管理）。两者不属于同一语义层级
2. **语义重复**：T-01 现有 behavior 规则"兼容性是 bug 放大器——不写向后兼容代码，直接废弃旧方案、写新方案"的后半句已经是肯定式，已覆盖"不写迁移代码"的含义。新增规则违反"不为已有规则覆盖的场景添加冗余例外"
3. **隐含假设不成立**："代码和数据分离"是 SaaS/云端系统的假设，不适用于 Snail Shell 的本地优先架构（SQLite 本地持久化，数据与代码共存于同一部署单元）

**修正后的根因**：F2026052204 的规则写在 S-03（开发者手册），没有写入架构师的审视清单。这是 skill 层的覆盖缺失，不是 tenet 层的规则不够强。"如果一个 tenet 规则需要具体映射才能生效，那它可能就不是有效的 tenet 规则——它应该是 skill 层的检查项。"

## 目标

在 cd-design skill 的审视清单中添加 `[HARD]` 检查项，将 F2026052204 的规则从开发者手册扩展到架构师审视阶段。

## 非目标

- 不修改 T-01 tenet prompt（现有规则已覆盖，无需冗余）
- 不修改 S-03 开发者手册（已由 F2026052204 覆盖）
- 不修改 cd-review 等其他 skill

## 设计

### 核心业务行为

- **当架构师审视数据库 schema 变更时**：不得要求添加 ALTER TABLE、迁移脚本或兼容性桥接
- **当架构师发现表结构变更时**：确认新列在 CREATE TABLE IF NOT EXISTS 中定义，在 feature 文档 `## 不兼容更新` 中记录，结束

### 变更内容

在 cd-design SKILL.md 的 Gotchas 中新增一条 `[HARD]` 检查项：

> **[HARD] 禁止要求迁移策略或兼容性桥接**：本系统遵循"代码仓完美状态原则"（F2026052204）。数据库 schema 变更只允许在 `CREATE TABLE IF NOT EXISTS` 中完成；严禁 ALTER TABLE、迁移脚本或兼容性桥接。不兼容变更记录在 feature 文档 `## 不兼容更新` 段落，由人手工处理。审视中不得以"已有数据库实例需要平滑升级"为由要求添加迁移逻辑——这不是待解决的问题，是系统设计决策。

### 方案选择理由

| 层级 | 方案 | 结论 |
|------|------|------|
| T-01 tenet 层 | 新增"代码即真相"约束 | 否决——语义重复、层级误用、前提假设不成立 |
| cd-design skill 层 | 新增 `[HARD]` 审视检查项 | 采纳——规则与检查机制在同一层级，精确命中场景 |

### 不兼容更新

无。纯增量变更，不影响现有功能。

## 改动范围

- 修改：`data/file/skills/cd-design/SKILL.md`（Gotchas 中新增一条 `[HARD]` 条目）

## 验收标准

- [ ] cd-design SKILL.md 的 Gotchas 中包含"禁止要求迁移策略或兼容性桥接"检查项
- [ ] 检查项引用 F2026052204 作为依据
- [ ] 检查项明确列出禁止项（ALTER TABLE、迁移脚本、兼容性桥接）和正确做法（CREATE TABLE IF NOT EXISTS + feature 文档记录）

## 风险与决策记录

- **决策 1**：不修改 T-01。理由：现有"兼容性是 bug 放大器"规则已覆盖此场景，新增规则违反"不添加冗余例外"原则
- **决策 2**：修改 cd-design skill 而非 cd-review skill。理由：问题发生在 design 阶段的架构师审视中，应在设计阶段拦截，而非等到 review 阶段
- **决策 3**：检查项使用具体操作描述（ALTER TABLE、CREATE TABLE IF NOT EXISTS）。理由：skill 层允许具体操作描述，与 tenet 层的行为准则不同
