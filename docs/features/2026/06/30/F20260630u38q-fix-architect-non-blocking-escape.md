# F20260630u38q [prompt] 修复架构师审视"不阻塞"逃逸口

<!-- [design-time] 以下章节在需求收敛与设计阶段（代码前）完成并锁定 -->

## 背景

在另一个 Issue 的 design 阶段，架构师-2 交叉审视时发现了两个问题：

1. handleSelect 无条件调用 updateMention，即使 mention 未激活也执行 setMentionState(INITIAL_STATE) 触发 re-render
2. useMention 当前无单元测试，extractMentionQuery 是纯函数但未覆盖边界场景

架构师-2 对这两条的处置方式是："建议 development 阶段处理，不阻塞设计。"

用户极度不喜欢 AI 说"不阻塞"，因为系统的做事风格是：发现问题就要修复好、就要改进、做到尽善尽美、追求完美。

## 目标

**P1 — 堵死 design 阶段的"不阻塞"逃逸口**

使 cd-design skill 的规则与 cd-review 对齐：审视者提出的问题，审视者必须在当前阶段处理完毕，不能以"属于其他阶段"为由推卸。

## 非目标

- 不修改 cd-review 阶段的规则（已有效，无需改动）
- 不修改 cd-development 阶段的规则
- 不改变"架构师不写代码"的边界（架构师仍然不改代码文件，但必须在设计层面给出解决方案）

## 核心业务行为

| # | 场景 | 预期行为 |
|---|------|----------|
| B1 | 当架构师在交叉审视中发现一个问题时 | 架构师必须在当前阶段给出处置方案，不得以"属于 development 阶段"为由标记为"不阻塞"。分类标准：去掉具体函数名后问题仍成立→行为规格或质量问题；问题完全依赖具体代码结构→实现建议。同一发现只归入一个类别 |
| B2 | 当架构师审视报告中出现禁用话术（"不阻塞"、"建议后续阶段处理"、"属于实现细节"等）时 | 视为审视不充分，必须重新处置该条发现 |
| B3 | 当架构师发现的问题确实是具体代码写法建议时 | 架构师记录到 Feature 文档的"实现指引"章节，必须描述 (1) 什么问题 (2) 预期方向 (3) 关键约束。"建议优化性能"不达标 |
| B4 | 当架构师发现自己之前的判断有误时 | 可以撤回发现，但必须满足：(1) 说明原始判断依据 (2) 说明为何该依据不成立 (3) 对方架构师同意撤回。撤回记录保留在决策记录中 |
| B5 | 当架构师缺乏技术知识来写出具体实现指引时 | 应升级到用户决策，不得以"不阻塞"逃避 |

## 设计

### P1 详设

#### 根因分析

**问题不是提示词没写禁令，而是 design 阶段规则自身存在逻辑矛盾——后句架空前句。**

对比两套规则：

**review 阶段**（`cd-review/references/adversarial-check.md`）：
> 审查者提出的所有问题（**无论严重度**）都必须在当前 PR 中处理，不得以"不阻塞"为由推到后续 feature。

零漏洞，无例外。

**design 阶段**（`cd-design/SKILL.md` Gotchas 第 25 条）：
> 交叉审视中发现的设计层面问题，必须在当前 feature 文档中给出解决方案，不得标记为"非阻塞"或"后续迭代"。**代码实现细节（具体文件行号、函数签名、类型定义）属于 development 阶段，设计阶段不越界。**

后半句给了 AI 合法逃逸路径：

```
if (问题看起来像代码层面) {
    → "这是 implementation detail，属于 development 阶段"
    → "建议 development 阶段处理，不阻塞设计"
    → 合法逃逸
}
```

架构师-2 的两个"不阻塞"就是精确利用了这个漏洞：

| 发现 | AI 分类逻辑 | 逃逸路径 |
|------|-----------|---------|
| handleSelect 无条件调用 updateMention | "函数调用逻辑" → 代码细节 → development | "不阻塞设计" |
| useMention 无单元测试 | "测试是开发者的活" → development | "不阻塞设计" |

但这两条完全可以在设计层面处理：
- 第一条 → 行为条目："当 mention 未激活时，handleSelect 不应触发状态更新"
- 第二条 → 验收标准："extractMentionQuery 必须覆盖的边界场景列表"

**根因一句话**：review 阶段有效是因为它没有二分口；design 阶段失效是因为"代码细节属于 development"这句话把"必须当下解决"架空了。

#### 修复方案

**核心原则**：审视者提出的问题，审视者负责在当前阶段处理。不能用"这属于另一个阶段"来转嫁。

**具体变更 1**：修改 `cd-design` SKILL.md 的 Gotchas 第 25 条，替换为以下文本：

> **审视中的问题必须当下解决**：交叉审视中发现的所有问题，必须在当前阶段处理完毕。"架构师不写代码"不等于"架构师可以把问题推给开发者"。处理方式因问题性质而异（见下方分类标准），但不得以"属于 development 阶段"或其他理由将问题标记为"非阻塞"或"后续迭代"。
>
> **问题分类与处置标准**：
> - **行为规格问题**（逻辑遗漏、边界未定义、交互未明确）→ 写入满足 S1-S5 的行为条目或可验证的验收标准
> - **质量问题**（性能隐患、测试覆盖缺失、可维护性问题）→ 写入可验证的验收标准或约束条件
> - **实现建议**（具体代码写法、算法选择）→ 写入实现指引，描述问题、预期方向和关键约束，供 development 阶段参考
>
> **分类判断规则**：如果去掉具体函数名/变量名后，问题仍然成立，就是行为规格或质量问题；如果问题完全依赖于具体代码结构才是问题，就是实现建议。同一发现不得归入多个类别——选择最接近的一个。
>
> **实现指引的最低标准**：必须描述 (1) 什么问题 (2) 预期方向 (3) 关键约束。"建议优化性能"不达标；"当前 O(n²) 遍历在大数据量下有性能风险，建议改用索引查找或缓存方案，约束：不能改变查询结果的语义"达标。架构师确实缺乏技术知识时，应升级到用户决策，不得以"不阻塞"逃避。
>
> **纠错机制**：审视者在讨论中发现自己的判断有误时，可以撤回发现。撤回必须满足：(1) 说明原始判断依据 (2) 说明为何该依据不成立 (3) 对方架构师同意撤回。撤回记录保留在决策记录中。

**具体变更 2**：在 `cd-design` cross-review.md 的"质疑义务"章节增加以下内容，与 review 阶段的 adversarial-check.md 对齐：

处置约束：
> 审视产出的每条发现，必须在当前阶段有明确处置——写入 Feature 文档或经纠错机制撤回。不得以"建议后续阶段处理"作为处置方式。

禁用话术清单（审视报告中禁止出现以下表述）：
> - "不阻塞" / "不堵塞"
> - "建议 development 阶段处理"
> - "属于实现细节"
> - "后续迭代" / "后续优化"
> - "不影响设计"
> - 任何实质表达"可以不在当前阶段处理"的变体话术

**设计约束**：
- 保留"架构师不写代码"边界（实现建议只记录到 Feature 文档，不改代码文件）
- 与 cd-review 的零漏洞规则对齐
- 三个问题性质分类（行为规格 / 质量 / 实现建议）覆盖所有审视发现类型，不留灰色地带
- 分类判断规则确保同一发现只能归入一个类别
- 纠错机制允许撤回错误判断，但必须有记录

### 关键决策：为什么不用"分级处置"

曾考虑将审视发现按严重度分级（阻塞 vs 非阻塞），但 reject 了这个方案：
- review 阶段的经验表明，"分级"会被 AI 利用来把大部分问题归为"非阻塞"
- 零漏洞规则（你提出的，你就得处理）更简单、更难被绕过
- 处理方式的多样性（行为条目 / 验收标准 / 实现指引）已经提供了灵活性，不需要再加"不处理"这个选项

本 feature 的变更通过修改以下 skill 文件生效：
- `data/file/skills/cd-design/SKILL.md`（Gotchas 章节）
- `data/file/skills/cd-design/references/cross-review.md`（质疑义务章节）

## 设计约束摘要

- **边界**：不改代码文件，只改 skill 定义文件；不改 review/development 阶段规则
- **关键决策**：采用零漏洞规则（不采用分级处置），与 review 阶段对齐；同时改 Gotchas #25 和 cross-review.md（不采用只改 cross-review.md 的方案）
- **分类判断规则**：去掉具体函数名后问题仍成立→行为规格/质量；完全依赖代码结构→实现建议；同一发现只归一个类别
- **实现指引最低标准**：必须描述问题+预期方向+关键约束；不达标时升级到用户决策
- **纠错机制**：允许撤回错误判断，但必须说明依据并经对方同意，记录保留在决策记录中
- **语义不变量**：审视者发现问题 = 审视者负责在当前阶段给出处置方案（或经纠错机制撤回）
