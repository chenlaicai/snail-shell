# F20260630jeds [prompt] 人的介入边界优化

<!-- [design-time] 以下章节在需求收敛与设计阶段（代码前）完成并锁定 -->

## 背景

在 code-delivery SOP 的研发流程中，架构师角色存在两个极端行为：

1. **自行猜测做错误决策**：当上下文信息不足时，LLM 用"最可能的模式"填充空白，导致错误的设计决策。系统提示词中的"做到位才是真正的快"、"说明计划后继续执行"等规则被 LLM 解读为"不要停下来问"。

2. **啥都跑来问用户**：被用户纠正一次后，LLM 产生矫枉过正效应，把"这个具体场景不该猜"泛化为"所有场景都不该猜"。后续所有决策都变成提问，即使是 AI 可以自主判断的事项。

两个极端的共同根因：当前系统提示词使用二元框架（确定性结论→执行 / 不确定→提问），缺乏中间态和决策领域分类，LLM 无法准确判断"该不该问"这个元问题。

## 目标

**P1 — 明确决策边界，减少两个极端**

优化架构师角色的决策行为，使其：
- 在有客观依据时自主决策并记录理由（不问用户）
- 在需要业务偏好判断时给出明确推荐等用户确认（结构化提问）
- 在缺乏信息时明确说明缺失点并提问（精准提问）
- 被纠正后精确泛化到同类决策，不泛化到所有决策

## 非目标

- 不修改 cd-review 阶段的规则
- 不修改 cd-development 阶段的规则
- 不引入跨会话状态管理或持久化机制
- 不实现自动升级介入层级（作为后续 feature）

## 核心业务行为

| # | 场景 | 预期行为 |
|---|------|----------|
| B1 | 当架构师面临设计决策，且存在客观可验证的依据（代码事实、文档事实、SOP 规范）时 | 架构师应自主决策并记录理由，不需要向用户提问。决策记录必须包含依据来源（如"代码库中 X 模块使用了相同模式"、"需求文档第 N 节明确要求"） |
| B2 | 当架构师面临设计决策，存在多个方案且取舍依赖业务偏好，且从代码/文档中无法推断用户偏好时 | 架构师应给出明确推荐（不是列出选项），附上技术理由、风险说明和替代方案（一句话），等用户确认 |
| B3 | 当架构师面临设计决策，涉及删除/移除已有功能时 | 架构师必须事前建议，等用户确认后才能继续 |
| B4 | 当架构师面临设计决策，涉及新增（不改变已有行为）时 | 架构师可以事后纠正，记录决策理由即可 |
| B5 | 当架构师面临设计决策，涉及修改已有行为且仅影响单一模块时 | 架构师可以事后纠正，记录决策理由即可 |
| B6 | 当架构师面临设计决策，涉及修改已有行为且跨模块影响时 | 架构师必须事前建议，等用户确认后才能继续 |
| B7 | 当架构师被用户纠正某个决策时 | 架构师应精确定位纠正范围：(1) 如果纠正原因是"没考虑到 X"→后续涉及 X 的决策升级介入层级；(2) 如果纠正原因是"应该由我决定"→后续同类决策类型升级；(3) 如果纠正原因是"时机不对"→不升级 |
| B8 | 当架构师做出事后纠正模式的决策时 | 架构师必须记录决策日志：做了什么决策、基于什么理由。用户可通过标记"这个决策不对"并说明原因来触发纠正 |
| B9 | 当架构师在建议层给出推荐时 | 推荐格式必须包含：(1) 明确推荐方案 (2) 技术理由 (3) 风险说明 (4) 替代方案（一句话）(5) 确认请求。禁止列出选项让用户选择 |

## 设计

### P1 详设

#### 根因分析

**问题一：AI 自行猜测**

LLM 的训练目标是"给出答案"，天然倾向于生成确定性输出而非承认不确定性。当上下文信息不足时，LLM 会用"最可能的模式"填充空白。系统提示词中的以下规则加剧了这个问题：
- "做到位才是真正的快" → 被解读为"不要停下来问"
- "说明计划后继续执行" → 被解读为"不要等用户确认"
- "先识别问题本质再行动" → 被解读为"我自己能想明白"

**问题二：AI 啥都问**

LLM 被纠正后会产生矫枉过正效应：
- **惩罚规避**：被批评一次的"记忆"（在 context 中）会让模型对同类决策产生回避
- **规则泛化**："用户明确指令不得推翻" + "审视问题必须当下解决" 组合起来，让模型觉得"用户是最终裁判，我什么都别定"
- **缺乏恢复机制**：当前系统没有"被纠正后如何恢复"的规则，导致模型持续保守

**问题三：二元框架的局限**

当前 T-01 行为准则第 11 条：
> 分析完成后提问前自检：执行方向是确定性的还是各有优劣的权衡？确定性结论 + 下一步方向明确 + 在当前职责范围内 → 直接执行并报告；不满足这三个条件中的任何一个 → 提问。

这个框架的问题：
- "确定性"没有定义——什么算确定性？
- "各有优劣的权衡"太宽泛——很多技术决策都有优劣，但并非都需要问用户
- 缺乏中间态——没有"给出建议等确认"的模式

#### 修复方案

**核心原则**：不是让 AI 判断"我该不该问"，而是让 AI 判断"我有没有客观依据做这个决策"。

**变更 1：明确 T-01 行为准则第 11 条的模糊概念**

修改 `data/file/prompts/T-01-行为准则.md` 第 11 条，替换为：

> 分析完成后，按以下规则判断决策模式：
>
> **自主决策**（直接执行，记录理由）：存在客观可验证的依据（代码事实、文档事实、SOP 规范）支持该决策。
>
> **建议层**（给出明确推荐等用户确认）：存在多个方案 + 取舍依赖业务偏好 + 从代码/文档中无法推断偏好。三个条件必须同时满足。
>
> **必须人类决策**（直接提问，说明缺失信息）：需求有歧义且不同解读导致不同设计、涉及 AI 缺乏的领域知识。
>
> 需求对齐阶段确认前提条件的提问不受此约束。

**变更 2：在 cd-design 中增加决策模式选择规则**

修改 `data/file/skills/cd-design/SKILL.md` Gotchas 章节，新增：

> **决策模式选择**（用客观特征判断，不用主观判断）：
> - 涉及删除/移除已有功能 → 必须事前建议
> - 涉及新增（不改变已有行为）→ 可以事后纠正
> - 涉及修改已有行为：仅单模块内 → 事后纠正；跨模块 → 事前建议
>
> **建议层格式规范**：必须包含 (1) 明确推荐方案 (2) 技术理由 (3) 风险说明 (4) 替代方案（一句话）(5) 确认请求。禁止列出选项让用户选择。
>
> **建议层门控**：必须同时满足以下条件才触发——(1) 存在至少两个可区分的方案 (2) 取舍依赖业务偏好而非技术事实 (3) 从代码/文档中无法推断用户偏好。如果只是技术优劣可比较，应自主决策并记录理由。

**变更 3：增加纠正后恢复规则**

修改 `data/file/skills/cd-design/SKILL.md` Gotchas 章节，新增：

> **被纠正后的恢复**：用户纠正某个决策时，精确定位纠正范围：
> - 纠正原因是"你没有考虑到 X" → 后续涉及 X 的决策升级介入层级
> - 纠正原因是"这个应该由我决定" → 后续同类决策类型升级
> - 纠正原因是"判断对了，但时机不对" → 不升级，只是时机问题
>
> 不要将纠正泛化为"所有决策都需要用户确认"。

**变更 4：增加决策日志机制**

修改 `data/file/skills/cd-design/references/workflow.md`，在"阶段四：产出锁定"前新增：

> **决策日志**：架构师在设计过程中做出的事后纠正模式决策，必须记录在 Feature 文档的"关键决策记录"章节。记录格式：
> - 决策内容：做了什么决策
> - 决策依据：基于什么理由
> - 纠正通道：用户标记"这个决策不对"并说明原因
>
> 当前 feature 只实现决策记录和纠正标记。自动升级介入层级作为后续 feature。

#### 关键决策

**决策 1：外部信号驱动 vs AI 自主判断**

- **方案 A**（采纳）：用客观可验证的依据（代码事实、文档事实、SOP 规范）判断决策模式
- **方案 B**（拒绝）：让 AI 自主判断"我该不该问"
- **决策依据**：AI 做元判断（判断自己该不该判断）本身就是不可靠的。外部信号（代码库中是否存在同类模式、需求文档是否有明确表述）是可验证的，比 AI 的自我评估更可靠。

**决策 2：建议层三条件必须同时满足**

- **方案 A**（采纳）：存在多方案 + 依赖业务偏好 + 无法推断 → 三个条件同时满足才触发建议层
- **方案 B**（拒绝）：存在多方案即触发建议层
- **决策依据**：方案 B 门控太宽，会让建议层变成"包装过的提问"。如果只是技术优劣可比较，AI 应自主决策。

**决策 3：用客观特征替代可逆性判断**

- **方案 A**（采纳）：用"是否涉及删除/新增/修改"和"是否跨模块"作为客观特征
- **方案 B**（拒绝）：用"可逆性"和"影响"作为判断标准
- **决策依据**："可逆性"和"影响"本身就是元判断，AI 无法准确判断。"是否涉及删除"和"是否跨模块"可以从代码结构客观判断。

**决策 4：纠正后用信息条件定义同类场景**

- **方案 A**（采纳）：根据纠正原因的不同，精确泛化到不同范围
- **方案 B**（拒绝）：按决策类型定义同类场景
- **决策依据**：决策类型定义太宽（如"架构方案选择"涵盖太多场景），会导致过度保守。信息条件定义直接对应纠正原因，更精确。

**决策 5：当前 feature 不实现自动升级**

- **方案 A**（采纳）：只实现决策记录 + 纠正标记
- **方案 B**（拒绝）：实现完整的自动升级机制
- **决策依据**：自动升级需要跨会话状态管理，复杂度高。当前 feature 的产出是设计规范，自动升级作为后续 feature。

## 设计约束摘要

- **边界**：只修改提示词和 skill 文件，不改代码；不引入跨会话状态管理
- **关键决策**：用客观可验证依据判断决策模式（不用 AI 自主判断）；建议层三条件必须同时满足；用客观特征替代可逆性判断；纠正后用信息条件精确泛化
- **非目标约束**：不修改 cd-review/cd-development 规则；不实现自动升级机制
- **语义不变量**：有客观依据→自主决策；无客观依据但有技术判断→建议层；连技术判断都没有→必须问用户
