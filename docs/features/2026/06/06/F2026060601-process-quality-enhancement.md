# F2026060601 [sop] 流程质量增强：自检、决策记录与过度设计防护

<!-- [design-time] 以下章节在需求收敛与设计阶段（代码前）完成并锁定 -->
<!-- 进入实现阶段后不得单方面修改，如需变更须通过问题卡片向用户提出并确认 -->

## 背景

用户在实际使用过程中发现七个流程执行问题：

1. **自检缺失**：开发者修复检视意见时，容易"头痛医头"，修复 A 问题却引入 B 问题
2. **检视项处理漏洞**：开发者可能滥用"不合理"作为借口跳过检视意见
3. **过度设计借口**："未来扩展"成为增加复杂度的常见理由，但扩展需求往往未被确认
4. **特性拆分策略不当**：将完整特性拆分为多个独立特性，导致中间态难以维护和验证
5. **低风险问题被忽略**：AI 或审查者以"低风险"为由将问题标记为"可忽略"，违背"目标是完美"的原则
6. **决策记录缺失**：多架构师对抗的讨论过程没有标准化记录，只有结论没有论据
7. **平台层 prompt 分层不合理**：S-01 中包含角色职责定义（"开发者负责讨论、实现、自检和提交 PR；审查者负责 PR 检视和复检"），这些业务场景规则应该放在手册中，而不是 platform 层

这些问题的根因是：现有规则覆盖了大部分场景，但在执行层面存在差距——规则不够显式、定义不够明确、格式不够完善。

关联 feature：
- F2026060402（检视手册质量闭环强化）：已建立质量改进闭环，本次在此基础上扩展

## 目标

消除流程执行中的认知偏差和规则漏洞，确保：
- 修复检视意见时不会引入新问题
- 检视项处理必须有明确依据，不得以模糊理由跳过
- 设计复杂度必须有已确认的需求支撑，不得以"未来扩展"为借口
- 特性拆分策略优先选择"特性内分 Part"，中间态必须可验证
- 任何有修复价值的问题都应在当前 PR 中处理，不得以"低风险"为由忽略
- 关键决策必须记录完整的讨论过程，包括正反论点和决策依据
- 平台层 prompt 分层合理，业务场景规则放在手册中，platform 层只包含通用规则

### P1 — 自检与检视闭环强化

- 审查者复检时重点关注修复是否引入新问题（强化现有"自检验证"规则的执行）
- "不合理"的边界明确定义为三种情况
- 禁止以"低风险"为由忽略问题

### P2 — 设计约束与特性拆分

- "未来扩展"作为设计理由时，必须证明扩展需求已确认
- 特性拆分必须评估中间态质量风险
- 优先选择"特性内分 Part"而非"特性拆分"

### P3 — 决策记录机制

- 扩展 Feature 文档的"风险与决策记录"章节
- 增加决策过程字段：正方论点、反方论点、决策依据、参与者
- 将决策记录要求扩展到开发和检视阶段

## 非目标

- 不改变现有的五阶段检视工作流程结构
- 不改变现有的四阶段开发工作流程结构
- 不引入新的角色或工具
- 不改变 merge 阶段的硬性条件

## 设计

### 规则关系说明

改动 1、2、3 都涉及"修复"和"风险"，但它们是不同维度的约束，是互补的而非冲突的：

| 改动 | 维度 | 约束对象 | 核心含义 |
|---|---|---|---|
| 改动 1 | 检查修复结果 | 审查者 | 审查者需要验证开发者的回归检查是否完整，防止修复引入新问题 |
| 改动 2 | 修复方式 | 开发者 | 开发者修复时要考虑端到端链路，不能只看到单点问题，必须提出全面的修复方案 |
| 改动 3 | 是否修复 | 审查者 | 审查者不能以"低风险"为由跳过问题，所有有修复价值的问题都应处理 |

**关系图**：
```
问题发现 → 改动 3（不能以低风险跳过） → 改动 2（修复时要考虑全面） → 改动 1（验证修复是否引入新问题）
```

**共同目标**：确保所有问题都得到全面、彻底的处理，不留隐患。

### P1 详设

**改动 1：审查者手册·复检流程——修复回归检查**

在复检流程第 2 步"完整重新检视 PR diff"后，增加：

```
3. 重点关注修复是否引入新的回归风险，而非仅确认原问题已解决
   - 对比修复前后的 diff，检查被修改逻辑的关联路径
   - 如果修复涉及多个文件，确认文件间的依赖关系未被破坏
   - 注意：此规则是强化现有"自检验证"规则的执行，开发者仍应在提交 PR 前完成回归检查

**"强化"的具体含义**：
- 审查者需要验证开发者的回归检查是否完整（通过检查 PR 描述、commit message 或直接询问开发者）
- 如果开发者没有做回归检查，审查者必须打回，要求开发者完成回归检查后再提交
- 审查者不需要自己做回归检查，但需要验证开发者的回归检查是否充分

**"完整"的最小标准**：
- PR 描述中必须包含回归检查的范围和结果，不能只写"已做回归检查"
- 回归检查范围必须覆盖与被修改逻辑相关的既有成功路径、边界路径和失败路径
- 如果没有测试覆盖，必须说明人工验证范围

**MUST NOT**：
- 开发者不得跳过回归检查，审查者不得通过未做回归检查的 PR
- 审查者不得忽略验证开发者的回归检查，否则可能导致引入新问题
```

**改动 2：开发者手册·阶段二——"不合理"边界定义**

在阶段二（设计确认与实现准备）的"不得自行修改设计"规则后，增加：

```
**"不合理"边界定义**：

审查者提出的改进意见，开发者认为不合理时，必须满足以下三种情况之一：

1. **事实错误**：检视意见基于错误的事实（必须提供正确的事实依据）
2. **理解偏差**：检视者误解了设计意图或业务需求（必须说明正确的设计意图）
3. **修复引入更大风险**：修复时必须考虑端到端链路，不能只看到眼前的单点问题。如果修复会导致更严重的问题，必须具体说明风险是什么、为什么修复会导致该风险，并提出替代方案

**替代方案格式要求**：
替代方案必须包含以下内容，不能是模糊的"更好的方式"或"我会用其他方法"：
- **具体修复方式**：说明具体会修改哪些文件、哪些逻辑，不能是抽象的描述
- **风险说明**：说明为什么不直接修复，直接修复会导致什么具体风险
- **风险评估**：说明替代方案本身的风险，以及为什么替代方案的风险更小

**"具体"的最小标准**：
- 具体修复方式：必须说明会修改哪些文件、哪些函数/方法，不能是"用更好的方式"或"我会用其他方法"
- 风险说明：必须说明直接修复的具体风险，不能是"有风险"或"可能有问题"
- 风险评估：必须说明替代方案的具体风险，不能是"更安全"或"风险更小"

不得以"不阻塞"、"可后续优化"、"风格偏好"等模糊理由拒绝审查者提出的合理质量改进。

**重要澄清**：第 3 种情况不是"不修复"的理由，而是"修复时要考虑全面"的理由。开发者不能以"修复会引入更大风险"为由拒绝修复，而应该提出更全面的修复方案。
```

**改动 3：审查者手册·阶段三——禁止"低风险"忽略**

在阶段三（对抗性检查）第 8 条（质量改进必须提出）后，增加：

```
**禁止以"低风险"为由忽略问题**：

- 风险评估应基于：(1) 问题发生的概率；(2) 问题发生后的影响程度；(3) 修复的成本
- 只要问题有修复价值，无论风险高低，都应在当前 PR 中修复
- 禁止使用"低风险"、"可忽略"、"不重要"等标签跳过问题
- 目标是完美，不是"没有阻塞项"

**MUST NOT**：
- 审查者不得使用"低风险"、"可忽略"、"不重要"等标签跳过问题
- 审查者不得换一种说法（比如"这个问题不重要"、"这个问题可以后续再处理"）来实质跳过问题
- 复检时，如果发现审查者跳过了问题，必须打回，要求审查者重新检视

**"实质是跳过问题"的判断标准**：
- 审查者没有提供具体的修复方案，且没有说明为什么不修复
- 审查者以"不重要"、"可后续处理"、"不影响功能"等模糊理由拒绝修复
- 审查者以"风险很低"、"概率很小"等理由拒绝修复

**重要澄清**：此规则与开发者手册中的"修复引入更大风险"不冲突。两者是不同维度的约束：
- 本规则解决的是"要不要修复"的问题：要修复，不能以低风险为由跳过
- "修复引入更大风险"解决的是"怎么修复"的问题：修复时要考虑端到端链路，不能只看到单点问题

开发者不能以"低风险"为由拒绝修复，也不能以"修复引入更大风险"为由拒绝修复，而应该提出更全面的修复方案。
```

### P2 详设

**改动 4：设计师手册·对抗性审视要点——"未来扩展"约束**

在"对抗性审视要点"中增加：

```
**"未来扩展"设计约束**：

如果设计方案以"未来扩展"为理由增加复杂度，必须证明：

1. **扩展需求已确认**：有明确的用户需求、业务规划或技术约束支撑扩展需求
2. **当前方案是扩展的必要前置条件**：如果没有当前的复杂设计，未来扩展将无法实现或成本极高
3. **没有更简单的方案**：没有更简单的方案能满足当前需求且支持未来扩展

如果无法满足以上三点，应选择更简单的方案。"未来扩展"不得作为推测性过度设计的借口。
```

**改动 5：设计师手册·阶段三——特性拆分原则**

在"阶段三：交叉审视与设计收敛"中增加：

```
**特性拆分原则**：

当 scope 巨大需要拆分时，必须遵循以下原则：

1. **优先选择"特性内分 Part"**：
   - 将一个特性拆分为多个实施阶段（P1、P2、P3...）
   - 每个阶段都是可独立验证的完整状态
   - 阶段之间有明确的依赖关系和实施顺序

2. **避免"特性拆分"**：
   - 将一个完整特性拆分为多个独立特性会引入中间态
   - 中间态难以维护、难以测试、难以验证质量
   - 除非各 Part 之间有明确的独立边界，否则不应拆分
   - **"明确独立边界"的最小标准**：两个特性可以独立测试、独立验证、独立回滚，且不存在先后依赖关系
   - **"独立测试"的具体含义**：两个特性可以单独运行测试用例，且测试用例不依赖对方的实现。如果测试用例需要依赖对方的实现才能通过，则不满足"独立测试"标准
   - **"不依赖对方的实现"的具体含义**：测试用例不调用对方的函数，不使用对方的数据，不依赖对方的状态。如果测试用例需要调用对方的函数、使用对方的数据或依赖对方的状态，则不满足"独立测试"标准

3. **如果必须拆分为多个特性，必须评估中间态质量风险**：
   - 中间态是否会导致系统行为不一致？
   - 中间态是否难以测试和验证？
   - 中间态是否会导致用户体验混乱？
   - 必须在 Feature 文档中记录中间态风险评估结果
```

**改动 6：Feature 文档模板·目标章节——多阶段约束**

在 Feature 文档模板的"目标"章节增加约束：

```markdown
## 目标

总导览：回应背景中的问题。多阶段 feature 用 `### P1 —` / `### P2 —` 拆分，每个 Phase 说清楚要达成什么。

**多阶段实施约束**：

如果采用多阶段实施，必须说明：
- 每个阶段的交付物和验证方式
- 阶段之间的依赖关系
- 每个阶段都是可独立验证的完整状态

禁止将一个完整特性拆分为多个独立特性，除非各特性之间有明确的独立边界。
```

### P4 详设

**改动 8：平台层 prompt 分层优化**

S-01（工作区上下文）包含了"开发者负责讨论、实现、自检和提交 PR；审查者负责 PR 检视和复检"这条规则，这明显属于业务场景中特定角色需要遵从的规范，但它被放在了 platform 层的 prompt 中。

**优化方案**：
- 移除 S-01 中的角色职责定义
- 保留在手册中：development#developer.handbook.md 已经包含"当前身份：开发者，负责按设计方案实现、自检、提交 PR"
- 保留在手册中：review#reviewer.handbook.md 已经包含"当前身份：PR 审查者，对 PR 正确性、系统风险和可维护性负责的独立质量角色"

**应该保留在 S-01 的内容**：
- 工作区上下文信息（workspace、issue、stage）
- 角色身份信息
- "工作必须遵守当前 stage，并留下可追溯记录"
- "新输入必须能合理归属于当前 Workspace、Issue、Stage 和 Conversation"
- "角色不能把推进 stage、重开 development、完成/归档 Issue 或直接修改工作流状态数据作为自己可主动执行的动作"

### P3 详设

**改动 7：决策记录机制**

本改动统一规范决策记录的要求，适用于 Feature 文档模板、设计师手册、开发者手册和审查者手册。

**7.1 Feature 文档模板·决策记录章节扩展**

将现有的"风险与决策记录"章节扩展为"关键决策记录"，格式从简单表格扩展为：

```markdown
## 关键决策记录

记录本 feature 在设计、实现和检视过程中的关键决策，包括讨论过程和决策依据。

| # | 决策点 | 正方论点 | 反方论点 | 最终决策 | 决策依据 | 参与者 | 日期 |
|---|---|---|---|---|---|---|---|
| D1 | 决策点描述 | 支持该决策的理由 | 反对该决策的理由 | 最终选择的方案 | 选择该方案的依据（用户需求、技术约束、成本收益等） | 参与决策的人员 | YYYY-MM-DD |
```

**7.2 决策记录要求**

- **"关键决策"的最小标准**：涉及架构、设计取舍、范围变更、用户体验、性能权衡的决策
- **"涉及"的具体含义**：
  - **涉及架构**：影响系统结构、模块划分、数据模型、接口设计
  - **涉及设计取舍**：有多个可选方案，需要权衡利弊
  - **涉及范围变更**：改变需求、非目标、实现范围
  - **涉及用户体验**：改变用户可见的行为、界面、交互
  - **涉及性能权衡**：影响性能、资源消耗、响应时间

- **"影响"的具体标准**：
  - **影响系统结构**：增加、删除或修改模块、数据模型、接口
  - **影响模块划分**：增加、删除或修改模块
  - **影响数据模型**：增加、删除或修改数据表、字段、关系
  - **影响接口设计**：增加、删除或修改 API、协议、数据格式

- 关键决策必须记录完整的讨论过程，不能只记录结论
- 正反论点必须具体，不得使用"有风险"、"不合适"等模糊表述
- 决策依据必须可追溯（用户需求、技术约束、成本收益分析等）
- 参与者必须记录实际参与讨论的人员，不得省略

**7.3 设计师手册·阶段三——决策记录要求**

在"阶段三：交叉审视与设计收敛"的第 4 步（关键设计取舍记录）后，增加：

```
**决策记录要求**：

每次对抗性审视后，必须将讨论的关键点记录到 Feature 文档的"关键决策记录"章节：

1. **决策点**：讨论的核心问题是什么
2. **正方论点**：支持当前方案的理由（必须具体）
3. **反方论点**：反对当前方案的理由（必须具体）
4. **最终决策**：选择的方案是什么
5. **决策依据**：为什么选择这个方案（用户需求、技术约束、成本收益等）
6. **参与者**：实际参与讨论的人员

禁止只记录结论而不记录过程。决策记录是未来维护和演进的重要参考。

**遗漏检查**：
阶段结束时，必须检查是否有遗漏的关键决策未被记录：
1. 回顾本阶段的所有对抗性审视
2. 列出所有讨论过的决策点
3. 检查每个决策点是否已记录到 Feature 文档
4. 如果发现遗漏，立即补充记录
```

**7.4 开发者手册与审查者手册——决策记录扩展**

在开发者手册阶段三和审查者手册阶段三中，增加：

```
**检视过程中的决策记录**：

当检视过程中发现设计问题或需要决策时，必须记录到 Feature 文档的"关键决策记录"章节：

- 开发者发现设计问题并通过问题卡片升级时，记录问题和决策过程
- 审查者提出设计改进建议并被采纳时，记录建议和采纳理由
- 开发者和审查者对实现方案有分歧时，记录分歧点和最终决策

**MUST**：
- 发现问题的人必须记录到 Feature 文档
- 做出决策的人必须确认记录的准确性
- 开发者和审查者必须对决策记录达成一致

**MUST NOT**：
- 不得跳过决策记录
- 不得记录不准确的决策
- 不得跳过一致性检查

**一致性检查的具体步骤**：
1. 开发者和审查者共同检查决策记录
2. 确认记录内容与实际讨论一致
3. 如果发现不一致，重新讨论并更新记录
4. 如果无法达成一致，升级到用户决策
```

### 设计决策

| # | 决策点 | 正方论点 | 反方论点 | 最终决策 | 决策依据 | 参与者 | 日期 |
|---|---|---|---|---|---|---|---|
| D1 | 是否需要明确定义"不合理"的边界 | 模糊的定义导致开发者滥用"不合理"作为借口；明确定义可以减少争议 | 定义过于严格可能限制开发者的合理拒绝；需要保留一定的灵活性 | 明确定义三种边界情况 | 用户反馈表明需要减少模糊空间；三种边界情况覆盖了合理的拒绝场景 | 用户 | 2026-06-05 |
| D2 | 是否需要禁止"未来扩展"作为设计理由 | "未来扩展"是常见的过度设计借口；禁止可以减少不必要的复杂度 | 有些扩展需求是真实的，需要预留接口；完全禁止可能限制合理的架构设计 | 不完全禁止，但要求证明扩展需求已确认 | 平衡灵活性和约束性；要求证明可以过滤掉推测性的过度设计 | 用户 | 2026-06-05 |
| D3 | 是否需要强制"特性内分 Part"而非"特性拆分" | 特性拆分引入中间态，难以维护和验证；强制分 Part 可以保证每个阶段都是完整状态 | 有些特性确实需要拆分为独立特性；强制分 Part 可能不适用所有场景 | 优先分 Part，但允许在有明确独立边界时拆分；定义"明确独立边界"的最小标准 | 平衡原则性和灵活性；优先推荐但不完全禁止拆分 | 用户 | 2026-06-05 |
| D4 | 是否需要禁止"低风险"作为忽略问题的理由 | "低风险"不等于"无风险"；任何有修复价值的问题都应处理；与"修复引入更大风险"是不同维度的约束（要不要修复 vs 怎么修复） | 有些问题确实风险很低，修复成本可能高于收益；完全禁止可能拖慢 PR 周期 | 禁止以"低风险"为由忽略问题；与"修复引入更大风险"互补而非冲突 | 用户强调"目标是完美"；已有质量改进闭环可以保证执行 | 用户 | 2026-06-05 |
| D5 | 是否需要扩展决策记录格式 | 现有表格过于简化，无法记录讨论过程；扩展格式可以提供完整的决策上下文 | 扩展会增加文档维护成本；有些决策可能不需要详细记录 | 扩展格式，增加决策过程字段；定义"关键决策"的最小标准 | 用户反馈表明需要记录完整的讨论过程；扩展格式可以提供更好的可追溯性 | 用户 | 2026-06-05 |
