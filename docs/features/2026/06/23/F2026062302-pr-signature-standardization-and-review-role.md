# F2026062302 PR签名标准化与检视阶段主角色修正

<!-- [design-time] 以下章节在需求收敛与设计阶段（代码前）完成并锁定 -->
<!-- 进入实现阶段后不得单方面修改，如需变更须通过问题卡片向用户提出并确认 -->

## 背景

用户反馈两个问题：

1. **PR评论签名不统一**：各Snail在PR上评论时签名格式五花八门，没有遵循已有的签名模板规范。这反映了各Snail对自身身份认知不清晰的问题。

2. **检视阶段主角色配置错误**：当前代码交付SOP中，检视阶段（review）的主角色（`is_primary: true`）是开发者（developer），但检视阶段的核心执行者应该是审查者（reviewer）。

## 目标

### P0 — 签名执行一致性

确保所有Snail在PR评论时严格遵循签名模板，格式统一为 `by <角色名>（<Snail 名称>）`。

### P1 — 检视阶段主角色语义正确

修正检视阶段的主角色配置，使系统语义与实际工作流一致。

## 非目标

1. **不修改签名模板格式**：现有 `by <角色名>（<Snail 名称>）` 格式已足够清晰，无需调整
2. **不修改检视阶段的人员配置**：保持2位审查者 + 1位开发者的配置不变
3. **不涉及其他SOP的主角色配置**：只修正代码交付SOP的检视阶段

## 核心业务行为

| # | 场景 | 预期行为 | 测试覆盖 |
|---|------|----------|----------|
| B1 | 当Snail在PR上发表普通评论时 | 签名必须严格遵循模板格式 `by <角色名>（<Snail 名称>）`，不得自行构造或省略 | |
| B2 | 当Snail不确定自己的角色身份时 | 应从系统提示词注入的上下文获取，不得猜测 | |
| B3 | 当检视阶段开始时 | 系统应将审查者识别为阶段主角色，而非开发者 | |
| B4 | 当阶段转移逻辑判断主角色时 | 检视阶段的主角色应为审查者 | |

## 设计

### 问题1根因分析：签名不统一

**现状**：
- 签名模板存在于 `.meta/templates/pr-comment-signature.md`
- 模板格式清晰：`by <角色名>（<Snail 名称>）`
- 有 `resolveSnailDisplayName()` 函数解析Snail名称
- 但实际执行中签名五花八门

**根因**：
1. **身份认知不清晰**：各Snail不确定自己在当前阶段的角色身份（是开发者还是审查者？）
2. **签名约束强度不足**：签名模板只是optional检查项（rev-03），没有强制执行
3. **Snail名称注入机制可能不完善**：`resolveSnailDisplayName()` 的回退逻辑可能导致名称不一致

**解决方案**：

**方案A：加强签名约束（推荐）**
- 将签名检查从optional提升为required
- 在SOP手册中明确要求Snail必须从系统提示词获取角色身份
- 在签名模板中增加"身份获取指引"

**方案B：强制签名生成**
- 在代码层面自动为评论追加签名
- 优点：完全避免人为错误
- 缺点：增加代码复杂度，可能与现有评论流程冲突

**决策**：选择方案A。理由：
- 签名是身份认知的外在表现，应该由Snail自觉执行
- 强制签名可能掩盖身份认知问题
- 方案A成本低，可通过配置调整实现

### 问题2根因分析：检视阶段主角色

**现状配置**（`code-delivery.yaml` 第106-110行）：
```yaml
- key: developer
  name: 开发者
  description: 在审查阶段回应检视意见、修复代码并推动检视清零。
  is_primary: true
  handbook: "@review#developer.handbook.md"
```

**问题**：
- `is_primary: true` 标记在开发者上
- 但检视阶段的核心价值是"对抗性检视"，执行者是审查者
- 开发者在检视阶段是"被动"角色（回应检视意见）

**`is_primary` 语义分析**：

从各阶段配置看：
- design阶段：架构师是 `is_primary: true`，count: 2
- development阶段：开发者是 `is_primary: true`
- merge阶段：维护者是 `is_primary: true`

`is_primary` 可能的语义：
1. "阶段推进的主要责任方" - 谁负责推动阶段完成
2. "阶段的核心执行者" - 谁做主要工作
3. "阶段的入口角色" - 谁先启动阶段

在检视阶段：
- 审查者是核心执行者（对抗性检视）
- 开发者负责推动检视清零（回应意见、修复代码）
- 但阶段的"价值"来自审查者的对抗性检视

**设计决策**：

**正方论点（审查者应为主角色）**：
1. 检视阶段的核心价值是"对抗性检视"，这是审查者的职责
2. 验收要点（acceptance_focus）5条中4条指向审查者
3. 从阶段产出看，审查者留下可追溯评论是必要条件
4. 语义上，"主角色"应指"阶段价值的主要创造者"

**反方论点（开发者应为主角色）**：
1. `is_primary` 可能指"阶段推进的主要责任方"
2. 开发者负责推动检视清零，是阶段完成的关键
3. 其他阶段的主角色都是"推动阶段完成的角色"
4. 审查者是被动触发（开发者请求检视），开发者是主动发起

**最终决策**：审查者应为主角色

**决策依据**：
1. 检视阶段的核心价值是"对抗性检视"，这是审查者的职责
2. 验收要点明确指向审查者（5条中4条）
3. 从阶段产出看，审查者留下可追溯评论是必要条件
4. `is_primary` 应理解为"阶段价值的主要创造者"而非"阶段推进的主要责任方"

**`is_primary` 对消息路由的影响分析**：

代码路径：`src/domain/issue/model.ts:140-144` 的 `resolveDefaultRoleInstance` 使用 `is_primary` 确定 `default_role_instance`，被 `src/app/issue-collaboration/collaboration.ts:366` 消费为消息路由回退。

| 场景 | 变更前 | 变更后 |
|------|--------|--------|
| 检视阶段无 @mention 时的默认路由 | 开发者 | 审查者-1 |

**影响评估**：此变更是预期行为。检视阶段中，当消息没有明确 @mention 时，默认路由到主角色（审查者）比路由到开发者更合理——审查者是阶段价值的主要创造者，且通常需要先完成检视才能进入后续流程。此变更不改变有明确 @mention 时的路由行为。

## 生效路径

- **配置**：`v1/config/sop/code-delivery/code-delivery.yaml` 第106-115行
- **模板**：`.meta/templates/pr-comment-signature.md`（可能需要增强身份获取指引）
- **SOP手册**：`shared.handbook.md` 中的签名规则章节

## 设计约束摘要

- **边界**：只修改代码交付SOP的检视阶段配置，不涉及其他SOP
- **关键决策**：检视阶段主角色从开发者改为审查者；签名约束从optional提升为required
- **非目标约束**：不修改签名模板格式，不修改检视阶段人员配置
- **语义不变量**：`is_primary` 表示"阶段价值的主要创造者"；签名格式必须为 `by <角色名>（<Snail 名称>）`
- **身份认知**：Snail必须从系统提示词获取角色身份，不得猜测
