# F2026060801 [infra] Snail Shell V2 重建：架构决策与项目脚手架

<!-- [design-time] 以下章节在需求收敛与设计阶段（代码前）完成并锁定 -->
<!-- 进入实现阶段后不得单方面修改，如需变更须通过问题卡片向用户提出并确认 -->

## 背景

V1 代码仓仅 10 周历史（328 次提交），但近一周内 46% 的提交为破坏性变更。同时进行 5 个大规模重构（前端重写、数据模型重做、SOP 引擎重构、Prompt 层重组、MCP 重构），导致：

- 持久层核心文件 `store.ts` 变更 127 次，成为 god-object（656 行）
- 领域类型文件 `domain-types.ts` 变更 90 次，类型定义不稳定
- 无 migration 框架，schema 变更靠手动协调
- 类型重导出链 4 层深（`shared/types.ts` → `persistence/types.ts` → `persistence/store.ts` → `index.ts`）
- AI 辅助开发时频繁出现"哪里需要往哪里加"的问题，缺乏模块边界约束

**根因**：模块没有边界，类型没有归属，AI 没有"该去哪里找"的约束。

## 目标

保留 V1 经过迭代验证的领域模型决策，重建工程基础。具体：

### P1 — 项目脚手架与基础设施

- V1 归档到 `legacy/`（gitignored），V2 在根目录重建
- 技术栈升级：ESM、Hono、Drizzle ORM、Vitest 统一
- GitHub 配置（CI、hooks、templates）迁移
- 设计决策文档化

### P2 — 领域类型冻结

- 按 DDD 原则划分 6 个有界上下文
- 每个模块通过 `api.ts` + `types.ts` + `_internal/` 模式定义公开 API 表面
- 配置与数据分离

### P3 — 持久层

- Drizzle ORM schema 定义
- Migration 框架
- 每个实体独立 Repo

### P4 — 工作流引擎 + Agent 运行时 + API + 前端

- SOP 加载、快照、阶段状态机
- Agent 运行时适配器（Claude Code 优先）
- 协作引擎
- Hono API + React 前端

## 非目标

- V2 不包含飞书/企业微信 IM 集成
- V2 不包含 MCP server endpoint
- V2 不包含 Feature Chain、Lobby
- 不做数据迁移，V2 全新 DB
- 不保留 V1 的类型重导出链

## 设计

### D1：仓库结构 — 同仓库 + legacy/ 归档

**选择**：同仓库，V1 整体搬到 `legacy/`（gitignored），V2 在根目录重建。

**理由**：保留 git 历史，随时可参考旧代码。将来 V2 稳定后删除 `legacy/`。

### D2：包管理 — 单 src/

**选择**：单 `src/` 目录 + ESLint 层间依赖规则，不用 monorepo。

**理由**：单人开发场景下，分包的多人协作优势用不上，工具链摩擦会拖慢迭代速度。层间依赖用 ESLint `no-restricted-imports` 规则强制。

### D3：HTTP 框架 — Hono 替代 Express

**选择**：Hono + @hono/node-server + @hono/node-ws。

**理由**：Snail Shell 核心功能是流式 Agent 事件（SSE + WebSocket），Hono 原生支持，类型安全路由，性能好。新项目无迁移成本。

### D4：ORM — Drizzle ORM

**选择**：Drizzle ORM 替代原生 better-sqlite3。

**理由**：类型安全 schema 定义，自动 migration 生成，SQL-like API 不丢失控制力。V1 的 god-object `ConversationStore`（656 行）证明原生方式不可持续。

### D5：测试 — Vitest 统一

**选择**：Vitest 统一前后端测试，干掉 V1 的自定义 `scripts/run-tests.ts`。

**理由**：一套工具链，无需维护自定义 runner。

### D6：架构模式 — DDD

**选择**：领域驱动设计，每个模块是独立的有界上下文。

**理由**：DDD 非常适合 AI 时代。各个领域模型各自独立，模型与业务场景绑定，AI 只需理解当前所改的业务场景即可。模块边界划分清晰、依赖关系清晰、数据模型清晰且统一一处。

### D7：领域边界 — 6 个有界上下文

| 领域 | 目录 | 业务含义 | 拥有的实体 |
|------|------|---------|-----------|
| 项目空间 | `workspace/` | 一个项目空间 | Workspace、GuardProfile |
| 标准流程 | `sop/` | 工作流模板 | SOP、StageDefinition、Transition、Guard |
| 工作任务 | `issue/` | 一个工作任务 | Issue、Stage、GateEvidence、ChecklistItem |
| Agent 运行时 | `snail/` | Agent 模板和运行时 | SnailTemplate、RuntimeBinding、SnailRuntime、AgentEvent |
| 对话消息 | `conversation/` | 对话和消息 | Conversation、Message、MessageEvent、Dispatch、Context |
| 演进治理 | `evolution/` | 演进治理 | EvolutionItem、KnowledgeEntry |

**命名说明**：
- `snail/` 而非 `agent/` — Snail Shell 的 Agent 模板叫 "Snail"，这是领域语言
- `issue/` 而非 `workflow/` — Issue 是核心业务实体，Stage 是 Issue 的子实体
- `conversation/` 而非 `message/` — Conversation 是协作的容器，Message 是其子实体

### D8：模块内部结构 — api.ts + _internal/

```
<module>/
  api.ts              # 🟢 公开 API — 只导出对外的方法和类型
  types.ts            # 🟢 公开类型 — 对外暴露的结构体定义
  _internal/
    *.ts              # 🔴 内部实现 — 外部禁止 import
```

**规则**：
- 外部 import 只能走 `@/module/api` 或 `@/module/types`
- `_internal/` 下的文件禁止被其他模块 import（ESLint 规则强制）
- `api.ts` 明确列出模块对外提供什么

### D9：不设共享 types/ 目录

**选择**：不设 `src/types/` 共享层。

**理由**：没有真正跨所有领域的共享类型。`IssueId` 属于 `issue/`，`RoleKey` 属于 `sop/`，`MessageId` 属于 `conversation/`。每个概念只有一个定义位置。

### D10：配置与数据分离

| 内容 | 归属 | 理由 |
|------|------|------|
| llm.json | `config/llm.ts` | 纯配置，LLM 提供商连接参数 |
| logging.json | `config/logging.ts` | 纯配置，日志级别 |
| SOP YAML | `sop/_internal/data/` | 领域数据，SOP 定义是 workflow 的核心 |
| snail-den.json | `snail/_internal/pool.ts` | 领域数据，Agent 模板定义 |
| workspaces.json | `workspace/store.ts` | 领域数据，空间列表 |
| guard-profile.json | `workspace/` | 领域数据，权限配置 |

### D11：持久层 — Repo 集中，类型分散

- DB schema、连接、migration → `db/`（集中）
- 类型定义 → 各领域模块的 `types.ts`（分散）
- Repo → `db/repos/`，但 import 类型从各域来

### D12：技术栈保留项

以下从 V1 直接保留：
- React 19 + Vite 8
- Zustand + TanStack Query 5
- Tailwind CSS 4
- Zod 校验
- SQLite (better-sqlite3)
- Node.js 22 + tsx

## 生效路径

- 代码结构：`src/` 目录按 DDD 划分
- 依赖规则：ESLint `no-restricted-imports` 强制层间依赖方向
- 模块边界：`api.ts` + `_internal/` 模式
- 提交规范：`.githooks/commit-msg` 强制格式
- CI：`.github/workflows/ci.yml` 运行 `npm run check`
- 设计约束：本文档 + `CONTRIBUTING.md`

## 设计约束摘要

- **边界**：每个模块通过 `api.ts` 暴露公开 API，`_internal/` 禁止外部 import
- **依赖方向**：`workspace → sop → issue → conversation`，`snail` 提供运行时能力
- **类型归属**：类型跟着领域走，不设共享 types/ 层
- **配置分离**：纯配置在 `config/`，领域数据在各自域内
- **非目标约束**：V2 不含飞书/企业微信/MCP/Feature Chain/Lobby
