# F2026061702 [testing] 测试范式 SOP 对齐：默认不写测试 + 行为契约守护

<!-- [design-time] 以下章节在需求收敛与设计阶段完成并锁定 -->

## 背景

用户在 Snail Shell v2 重构后，要求"全都不写测试"。原因：

1. **历史测试无价值**：v1 的测试代码大部分是实现绑定测试（断言 fetch 参数、内部状态、函数调用次数），重构时全挂但业务逻辑未变
2. **AI 行为问题**：AI 遇到测试挂了，会反过来修改主代码去适配测试代码，颠倒了测试与被测代码的主仆关系
3. **v2 已清理测试**：F2026060901 已移除 v2 的测试代码和测试依赖，等待重新设计架构后再补齐

F2026060701 已建立"行为契约测试"范式，但未明确"什么时候写测试"的准入条件。本次在此基础上增加准入条件，让 SOP 与用户实际要求对齐。

## 目标

调整 SOP 中的测试规范，明确：
- 测试编写判断原则：AI 根据实际情况自行判断是否写测试
- 判断标准：这个行为是否值得守护
- 写测试时必须是行为契约测试
- 测试场景来源是 feature spec 的核心业务行为列表
- 无测试时的验证方式

### P1 — SOP 调整

- 修改 `development#developer.handbook.md`：增加"测试编写判断原则"章节；合并 `reference/测试.md`（自检覆盖）、`reference/提交.md`（Review 修复后验证、Review 完成判定）中的唯一内容
- 修改 `docs/README.md`（feature 模板）："核心业务行为"章节改为可选
- 修改 `review#reviewer.handbook.md`：测试质量检查改为"有测试时检查，无测试时不阻塞"；合并 `reference/检视.md` 中的源码字符串匹配反模式细节
- 修改 `design#designer.handbook.md`：合并 `reference/设计分析.md` 中的"可视化对齐"

### P2 — 清理 v1 测试

- 删除 `v1/src/web/tests/` 目录下的实现绑定测试（保留 v1 目录作为参考，不在本次 PR 处理）

### P3 — 清理 prompts/reference 中的角色专属内容

- 将 `prompts/reference/` 中的角色专属内容合并到对应 handbook，然后删除角色专属文件
- 保留通用文件：`通用指南.md`、`决策记录.md`、`提示词治理.md`、`演进治理.md`
- 删除角色专属文件：`测试.md`、`实现.md`、`提交.md`、`检视.md`、`设计分析.md`

## 非目标

- 不删除 F2026060701 建立的行为契约测试范式——它是未来写测试时的规范
- 不禁止所有测试——只是明确"默认不写，写了就必须是行为契约测试"
- 不引入新的测试框架

## 设计

### 核心概念：测试编写判断原则

AI 作为开发者，应根据实际情况自行判断是否写测试。判断标准是"这个行为是否值得守护"。

**值得写测试的情况**：
- 核心业务流程的行为正确性（如状态转移、数据一致性、关键错误处理）
- 修复已知 bug 后，防止复现（必须关联 bug 描述）
- 用户明确要求写测试

**不值得写测试的情况**：
- 实现细节（函数调用、参数、顺序、内部状态）
- 临时代码或原型
- 纯 UI 外观调整
- 纯重构（不改语义）

**核心原则**：测试守护的是业务行为，不是代码结构。如果一个测试在代码重构后会挂，那它就不该存在。

```markdown
### 测试编写判断原则

AI 作为开发者，应根据实际情况自行判断是否写测试。判断标准是"这个行为是否值得守护"。

**值得写测试的情况**：
- 核心业务流程的行为正确性（如状态转移、数据一致性、关键错误处理）
- 修复已知 bug 后，防止复现（必须关联 bug 描述）
- 用户明确要求写测试

**不值得写测试的情况**：
- 实现细节（函数调用、参数、顺序、内部状态）
- 临时代码或原型
- 纯 UI 外观调整
- 纯重构（不改语义）

**核心原则**：测试守护的是业务行为，不是代码结构。如果一个测试在代码重构后会挂，那它就不该存在。

**无测试时的验证方式**：
- `npm run build` + `npm run check`（编译通过）
- `npm run lint`（代码规范）
- 人工验证核心业务流程（在 PR 中说明验证方式）
```

**docs/README.md 模板修改**：

"核心业务行为"章节改为可选：

```markdown
## 核心业务行为（可选）

本 feature 涉及的核心业务行为列表。每条行为是"当 X 时，应该 Y"的形式，断言的是外部可观测行为（输入/输出/状态变化/错误），不是内部实现。

**填写条件**：开发者根据实际情况判断是否填写。核心业务流程、数据一致性、状态转移等值得守护的行为应填写此章节。实现细节、临时代码、纯 UI 外观调整等不需要填写。
```

**review#reviewer.handbook.md 修改**：

测试质量检查改为：

```markdown
12. 测试质量（有测试时检查，无测试时不阻塞）：
    - 测试是否对应 feature spec 中的核心业务行为？
    - 断言的是外部可观测行为，还是内部实现？

    - 无测试时：不阻塞 PR，但需确认验证方式已说明
```

### 设计决策

| # | 决策点 | 正方论点 | 反方论点 | 最终决策 | 决策依据 |
|---|-------|---------|---------|---------|---------|
| D1 | 测试编写判断方式 | 用户不想承担决策成本；AI 应该有判断能力 | 硬性规则可能导致遗漏 | AI 根据实际情况自行判断，使用"是否值得守护"作为判断标准 | 用户决策：判断责任不应由用户承担 |
| D2 | 是否保留行为契约测试范式 | 未来可能需要写测试 | 当前不需要 | 保留 F2026060701 规范，作为写测试时的标准 | 有规范比没规范好 |
| D3 | 是否删除 v1 测试 | v1 测试是实现绑定测试 | 可能有参考价值 | 删除，v2 会重新设计 | 避免误导 |
