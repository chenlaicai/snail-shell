## Summary

UI 卡住问题（点击进入 issue / 新建 issue / 刷新页面 / tab 切换时页面加载很久或无反应）目前**没有前端可观测性**，无法定位根因。

**本次特性包含两部分**：
1. **前端可观测性**：给前端加耗时日志并上报到后端，下次卡住时从 `web.log` 分析具体是哪个环节慢
2. **低风险优化**：关闭 `refetchOnWindowFocus`，消除 tab 切换时的无意义全量 refetch

## Problem Statement

### 症状

用户反馈多种页面操作都会卡住：
- 点击进入 issue
- 新建 issue
- 刷新页面
- tab 切换回来

### 已排除的后端问题

后端日志证据：
- HTTP 请求最大耗时 48ms — 后端不是瓶颈
- `event_loop.blocked` 无记录 — 事件循环没有阻塞
- `semaphore` 无阻塞记录 — 信号量从未触发等待
- curl 实测 Issues 列表 15ms、Issue Detail 2ms、Stage Messages 4ms

### 缺失的证据

前端完全没有可观测性：
- `web.log` 只有 Vite HMR 日志
- 没有页面加载耗时日志
- 没有 API 请求耗时日志（前端视角）
- 没有 React 渲染耗时日志
- 没有 WebSocket 连接生命周期日志

**在没有前端日志的情况下，任何根因分析都是猜测。**

## [design-time]

### 决策过程

#### 决策 1：如何定位前端卡住原因？

**选项 A：用户 Performance 面板录制**
- 优点：零成本、即时反馈、能直接看到阻塞函数
- 缺点：CLI agent 无法查看截图，用户需要手动操作，且用户明确拒绝

**选项 B：前端日志上报到后端**
- 优点：自动记录、agent 可直接分析 `web.log`、持续监控
- 缺点：需要写代码、下次卡住才有数据

**结论**：选 B。用户无法提供 Performance 截图，前端日志上报是唯一可行路径。

**排除的替代方案**：
- 直接猜根因修代码 — 无证据支撑，可能修错方向
- 只 `console.warn` 不上报 — agent 看不到浏览器控制台

#### 决策 2：日志上报的阈值策略

**全量上报**：每次 API 请求都上报 → 网络开销大，日志量大
**阈值上报**：只上报超阈值的慢操作 → 开销可控，聚焦问题

**结论**：阈值上报。API 请求 > 1 秒、页面加载 > 3 秒、渲染 > 100ms 才上报。

#### 决策 4：是否关闭 refetchOnWindowFocus？

**正方（架构师-2）**：应该关闭。WebSocket 已提供实时性，focus 时 refetch 是多余的。`staleTime: 0` 导致每次 tab 切换都全量 refetch 120KB 消息。

**反方**：无。配置级别改动，风险极低。

**结论**：关闭 `refetchOnWindowFocus`，同时将 messages 的 `staleTime` 从 0 改为 10 秒。

#### 决策 5：后端 API payload 大小是否是问题？

**实测数据**：
- Issues 列表：378~510KB（34 issues, 92 stages）— 15ms 响应
- Issue Detail：8KB — 2ms 响应
- Stage Messages：120KB — 4ms 响应

**结论**：后端响应快，payload 大小不是瓶颈。但前端接收 120KB JSON + Zod 验证 + React 渲染的组合可能有影响，需要日志验证。

## Design

### 前端日志上报系统

在前端关键路径上加耗时日志，超阈值自动上报到后端 `POST /api/frontend-log`，写入 `web.log`。

#### 1. API 请求耗时（前端视角）

在 `api-client.ts` 的 `api()` 函数中记录：
- 请求 URL 和方法
- 请求开始时间 → 完成时间
- 耗时超过 1 秒的请求自动上报

#### 2. 页面加载耗时

在路由切换时记录：
- 路由 loader 开始 → loader 完成（阻塞时间）
- 组件首次渲染 → 所有查询完成（水合时间）
- 总页面加载时间超过 3 秒自动上报

#### 3. WebSocket 生命周期

在 `useWebSocket.ts` 中记录：
- 连接开始 → 连接成功耗时
- 断连时间和原因
- 重连次数和间隔
- 重连后 invalidate 查询的耗时

#### 4. React Query 耗时

在 QueryClient 中记录：
- 查询开始 → 查询完成耗时
- 查询失败原因
- refetch 耗时

### 关闭 refetchOnWindowFocus

**位置**：`src/web/queries/client.ts:9`

将 `refetchOnWindowFocus: true` 改为 `false`。

**理由**：
- WebSocket 已提供实时数据推送，focus 时 refetch 是多余的
- messages 查询 `staleTime: 0`，每次 tab 切换都全量 refetch 120KB 消息
- 34 个 issue 的 workspace 列表也会 refetch（378KB）
- 配置级别改动，风险极低

**同时**：将 messages 查询的 `staleTime` 从 0 改为合理值（如 10 秒），避免无意义的频繁 refetch。

### 后端新增接口

`POST /api/frontend-log` — 接收前端日志，写入 `web.log`

### 日志格式

```json
{
  "level": "warn",
  "type": "frontend.perf",
  "metric": "api_request",
  "url": "/api/stages/:stageId/messages",
  "duration": 1234,
  "ts": 1719600000000
}
```
