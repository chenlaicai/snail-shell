# F20260629gg8m [mcp] db-bridge 脚本移除 — 数据访问收权到 MCP

<!-- [design-time] -->

## 背景

V1 架构中，`.meta/scripts/db-bridge.js` 是所有 skill 脚本的共享数据访问层（735 行），通过 CLI `--mode` 参数路由到不同数据操作模块，直接使用 `better-sqlite3` 执行 SQL，绕过 domain 层的 Port/Adapter/Repository 分层架构。

V2 重构后，domain 层已完整实现 DDD 分层架构（`src/infra/database.ts` → domain repository），db-bridge.js 已从主分支删除。但 **4 个 skill 脚本仍引用 db-bridge**，当前处于断裂状态：

| Skill | 依赖的 db-bridge mode | MCP 覆盖 |
|---|---|---|
| conversation-history | `history-search/page/recent/by-ids/window/reindex` (6 个) | 无 |
| evolution-candidate | `evolution-create` | 部分（MCP 只有 update/complete） |
| feature-chain | `feature-chain-search/get/chain` (3 个) | 无 |
| set-task-anchor | `issue-set-task-anchor` | 无 |

另外，`set-task-anchor` 脚本直接往 issue 表写 `task_anchor` 列，但当前 Issue model 中无此字段——这是脚本直接操作数据库导致的 schema 漂移。

已完全通过 MCP 覆盖的能力（knowledge、issue-context）无需处理。

## 目标

**P1 — 消除断裂路径**
- 移除所有引用 db-bridge 的 skill 脚本
- 移除 `set-task-anchor` 整体（脚本 + skill + task_anchor 体外字段）

**P2 — 数据访问收权到 MCP**
- 将 conversation-history、feature-chain、evolution-candidate create 的能力迁移到 MCP tool
- 所有数据访问统一经过 domain 层（Port → Adapter → Repository）

## 非目标

- 不新建 conversation domain（V1 概念，当前 stage + message 模型已足够）
- 不修改现有 MCP server 架构（JSON-RPC handler、注册机制等）
- 不引入消息 FTS5 全文搜索索引（当前阶段 LIKE 查询满足需求，后续按需扩展）
- ~~不修改 MessagePort 接口签名（跨 stage 聚合在 MCP handler 层组合实现）~~ → 见下方设计演进说明

## 核心业务行为

| # | 场景 | 预期行为 |
|---|------|---------|
| B1 | Agent 需要查询当前 Issue 的历史消息 | 通过 `snail-message-history` MCP tool 查询，不再调用 skill 脚本 |
| B2 | Agent 需要按关键词搜索 Issue 内消息 | `search_messages` tool 跨 stage 搜索，返回匹配消息列表 |
| B3 | Agent 已知 message ID 需要查看上下文 | `get_message_window` tool 返回锚点消息前后的上下文窗口 |
| B4 | Agent 需要搜索历史 Feature 文档 | 通过 `snail-feature-chain` MCP tool 查询，不再调用 skill 脚本 |
| B5 | Agent 需要创建演进候选 | 通过 `snail-evolution` MCP server 的 `create_candidate` tool 创建 |
| B6 | 系统提示词需要注入 task_anchor | 不再注入（task_anchor 已移除） |
| B7 | SOP 验证机制需要读取 change_type | 从 Issue context 读取 `sop.change_type`，替代从 task_anchor 读取 |
| B8 | 已有的 snail-knowledge、snail-issue-context 能力 | 不受影响，继续通过现有 MCP tool 访问 |

## 设计

### 一、snail-message-history（新建 MCP Server）

**定位**：替代 conversation-history skill，提供跨 stage 的消息查询能力。

**能力映射**：

| 旧 mode | MCP Tool | 说明 |
|---|---|---|
| `search` | `search_messages` | 跨 stage 关键词搜索 |
| `recent` | `list_messages` (mode=recent) | 每个 stage 最近用户消息及后续 |
| `page` | `list_messages` (mode=page) | 按时间分页 |
| `by-ids` | `get_message` | 按 ID 获取（复用 MessagePort.getMessage） |
| `window` | `get_message_window` | 窗口查询 |
| `reindex` | 不迁移 | 正常查询不使用，异常时重启服务即可 |

**Tool 设计**：

| Tool | 参数 | 说明 |
|---|---|---|
| `search_messages` | `issue_id`(必填), `query`(必填), `limit`(可选,默认10) | 跨 stage 关键词搜索。实现路径：StagePort.listStages → 对每个 stage 的消息做 LIKE 匹配 |
| `list_messages` | `issue_id`(必填), `mode`(recent/page), `limit`(可选), `before_id`(可选) | 跨 stage 消息列表。recent 模式返回每个 stage 最近用户消息及后续；page 模式按时间顺序分页 |
| `get_message` | `message_id`(必填) | 单条消息获取，复用 MessagePort.getMessage |
| `get_message_window` | `message_id`(必填), `before`(可选,默认2), `after`(可选,默认2) | 窗口查询。获取锚点消息所在 stage，取锚点前 N 条 + 后 N 条 |

**数据访问路径**：

```
MCP handler → StagePort.listStages(issueId) → 获取 stage IDs
            → MessagePort.listMessages(stageId, ...) → 各 stage 消息
            → 聚合/过滤/排序 → 返回结果
```

**性能说明**：`search_messages` 采用 N+1 查询模式（先查 stages，再逐 stage 查消息）。当前阶段为已知 trade-off——单个 Issue 通常 10-20 个 stage，LIKE 查询在消息量级内可接受。后续可优化为单次 JOIN 查询。

**设计决策**：跨 stage 聚合在 MCP handler 层完成，不修改 MessagePort 接口。原因：
- MessagePort 保持 stage 粒度的单一职责
- 跨 stage 聚合是查询时组合，不是领域概念
- 避免在 MessagePort 上引入 issueId 参数导致接口膨胀

**设计演进（review 阶段）**：原始设计中 handler 层通过 `listMessages` 全量加载后在内存中过滤/窗口查询。review 发现全量加载不可持续（stage 消息量大时内存溢出），因此在 MessagePort 上新增两个 stage 粒度的查询方法：

| 新增方法 | 用途 | 保持 stage 粒度 |
|---------|------|----------------|
| `listMessagesWindow(stageId, anchorId, before, after)` | 窗口查询，SQL 取锚点前后 N 条 | ✅ 参数不含 issueId |
| `searchContext(stageId, query, limit)` | 关键词搜索，SQL LIKE + ESCAPE | ✅ 参数不含 issueId |

这两个方法不引入 issueId 参数，不破坏 stage 粒度的单一职责。原始约束的核心意图（不在 MessagePort 上做跨 stage 聚合）仍然保持。

### 二、snail-feature-chain（新建 MCP Server）

**定位**：直接暴露现有 FeatureChainPort 能力。

| Tool | 参数 | 对应 FeatureChainPort 方法 |
|---|---|---|
| `search_feature_chain` | `query`(必填), `limit`(可选,默认10) | `search(query, limit)` |
| `get_feature_doc` | `id`(必填) | `get(id)` |
| `get_feature_chain` | `id`(必填), `direction`(可选,backward/forward/both,默认backward) | `chain(id, direction)` |

**数据访问路径**：

```
MCP handler → FeatureChainPort.search/get/chain → FileFeatureChainRepository → 文件系统 + SQLite FTS5
```

此 MCP server 是纯透传，handler 层无额外逻辑。

### 三、snail-evolution 扩展

在现有 `snail-evolution` MCP server 中新增 `create_candidate` tool：

| Tool | 参数 | 对应 EvolutionPort 方法 |
|---|---|---|
| `create_candidate` | `title`(必填), `content`(必填), `workspace_id`(必填), `tags`(可选), `metadata`(可选) | `create(input)` |

**Side Effects 说明**（写入 tool description）：此 tool 仅创建 `evolution_item` 记录（状态为 Candidate）。治理对话的 Issue/Stage/Conversation 由治理流程创建，不由本 tool 创建。这与旧 skill 脚本的四表联动行为不同——旧脚本绕过 domain 层直接 SQL 创建了 issue + stage + conversation，属于越权行为。

### 四、set-task-anchor 移除 + SOP 验证机制迁移

task_anchor 不仅是 set-task-anchor skill 的输出，更是整个 code-delivery SOP 验证机制的输入。以下 SOP skill 依赖 task_anchor 中的 `change_type` 和 `verification_commands`：

| SOP skill 文件 | 引用方式 | 用途 |
|---|---|---|
| `cd-design/SKILL.md` | "变更类型标签写入 task_anchor" | 设计阶段写入 change_type |
| `cd-development/SKILL.md` | "task_anchor 设置"、"根据 change_type 执行验证命令" | 开发阶段读取 change_type 决定验证命令 |
| `cd-shared/references/evidence-rules.md` | "task_anchor 中的 change_type 决定验证命令" | 验证命令选择规则 |
| `cd-review/references/adversarial-check.md` | "从 task_anchor 读取 change_type" | 审查阶段独立执行验证 |

**迁移方案**：`change_type` 和 `verification_commands` 存入 **Issue context**（通过 `snail-issue-context` MCP tool 的 `set_context`）。

- 存储 key：`sop.change_type`、`sop.verification_commands`
- 理由：change_type 是 issue 级属性（跨 stage 共享）、Issue context 已有 MCP 读写路径、无需新增 domain 字段
- SOP skill 修改：将"从 task_anchor 读取"改为"从 issue context 读取 `sop.change_type`"

**完整移除范围**：
- skill 脚本：`data/file/skills/set-task-anchor/scripts/set-task-anchor.js`
- skill 定义：`data/file/skills/set-task-anchor/SKILL.md`
- SOP skill 中的 task_anchor 引用：改为引用 issue context（6 个文件，见改动范围表）
- 体外字段：如数据库 issue 表存在 `task_anchor` 列，DDL 中移除

## 设计约束摘要

1. **所有数据访问统一经过 MCP tool**：不再有脚本直接操作数据库的路径
2. **不新建 domain**：message 域已有完整实现，跨 stage 聚合在 handler 层组合
3. **MessagePort 保持 stage 粒度单一职责**：新增 `listMessagesWindow` 和 `searchContext` 均为 stage 粒度查询，不引入跨 stage 参数
4. **FeatureChainPort 直接透传**：不增加抽象层
5. **evolution create 与旧脚本行为不同**：仅创建 evolution_item，不再联动创建 issue/stage/conversation
6. **task_anchor 彻底移除**：change_type 和 verification_commands 迁移到 Issue context（`sop.change_type`、`sop.verification_commands`），SOP skill 同步更新
7. **FeatureChainPort.rebuild() 不暴露**：索引由系统启动时自动重建，rebuild 是运维操作，不适合暴露给 Agent

## 分析推理过程记录

### 排查阶段

1. 搜索全仓库 db-bridge 引用 → 发现 4 个 skill 脚本仍引用已删除的 db-bridge.js
2. 搜索直接使用 SQLiteDatabase 的文件 → 确认 V2 domain 层已完整覆盖
3. 对照 MCP server 现有 tool → 确认 knowledge 和 issue-context 已覆盖，其余 4 个未覆盖

### 设计收敛

1. **conversation-history 的 domain 归属**：用户明确指出 conversation 是 V1 概念，当前只有 stage + message → 不新建 domain，围绕现有 MessagePort 设计
2. **set-task-anchor 的处置**：用户明确指示直接移除 task_anchor 字段，以当前 model 为准 → 整体移除，由 issue context 替代
3. **evolution create 的行为差异**：旧脚本四表联动（evolution_item + issue + stage + conversation），但 domain 层 EvolutionPort.create 只创建 evolution_item → 新 MCP tool 遵循 domain 层语义，治理对话由治理流程创建
4. **跨 stage 查询的实现层**：MessagePort 保持 stage 粒度，跨 stage 聚合在 MCP handler 层通过组合 IssuePort.listStages + MessagePort.listMessages 实现

## 关键决策记录

| # | 决策点 | 正方 | 反方 | 最终决策 | 依据 |
|---|--------|------|------|---------|------|
| D1 | conversation-history 是否新建 domain | 当前 stage + message 模型已覆盖需求 | 旧 skill 有 FTS 搜索能力，domain 层缺失 | 不新建 domain，handler 层组合 + LIKE 查询 | 用户明确指令：不要新增 domain，按当前模型设计 |
| D2 | set-task-anchor 是否迁移 | task_anchor 在旧系统中有用 | 当前 Issue model 无此字段，属于 schema 漂移 | 整体移除，由 issue context 替代 | 用户明确指令：直接移除，以当前模型为准 |
| D3 | evolution create 是否保持四表联动 | 旧脚本行为是四表联动 | domain 层 create 只创建 evolution_item | 遵循 domain 层语义，仅创建 evolution_item | 不绕过 domain 层是本次收权的核心目标 |
| D4 | 跨 stage 查询在哪层实现 | 在 MessagePort 上加跨 stage 方法 | 在 MCP handler 层组合 | handler 层组合 | MessagePort 保持 stage 粒度单一职责，避免接口膨胀 |
| D5 | 消息搜索是否引入 FTS5 | FTS5 搜索体验更好 | 当前阶段 LIKE 查询足够，FTS5 增加复杂度 | 先用 LIKE，后续按需扩展 | 消除过度设计，YAGNI 原则 |
| D6 | task_anchor 移除后 SOP 验证机制如何存续 | change_type 是 SOP 核心输入，不能丢 | task_anchor 必须移除 | change_type + verification_commands 迁移到 Issue context（`sop.change_type`、`sop.verification_commands`） | Issue context 已有 MCP 读写路径，跨 stage 共享，无需新增 domain 字段 |
| D7 | FeatureChainPort.rebuild() 是否暴露为 MCP tool | Agent 可能需要手动触发重建 | 索引由系统启动时自动重建，暴露 rebuild 增加误用风险 | 不暴露 | rebuild 是运维操作，不属于 Agent 数据访问能力 |
