# F2026060402 [sop] 检视手册质量闭环强化

<!-- [design-time] 以下章节在需求收敛与设计阶段（代码前）完成并锁定 -->
<!-- 进入实现阶段后不得单方面修改，如需变更须通过问题卡片向用户提出并确认 -->

## 背景

当前检视体系存在"非阻塞问题可跳过"的认知偏差。实际场景中，审查者给出"查到 xxx 问题，但不堵塞，可先合入"的结论，开发者以"不阻塞"为由拒绝在当前 PR 修复非阻塞改进。这导致质量改进被无限期推迟。

根因分析：

1. **审查者手册**："非阻塞改进同样必须提出"只约束了"提出"，没有闭环约束"修复"。复检流程没有定义"开发者跳过非阻塞问题"的拦截机制。
2. **审查者手册**：缺少结论格式约束。审查者可以给出笼统的"可合入"结论，而实际还有未修复的问题。
3. **开发者手册**："逐条处理"给了"不合理则说明理由"的退出通道，但没有约束不得以"不阻塞"为由拒绝合理的质量改进。
4. **术语偏差**："阻塞/非阻塞"天然暗示"非阻塞 = 可跳过"，与手册中"在当前 PR 范围内做到了最好"的精神矛盾。

关联 feature：
- F2026060305（证据驱动的门禁验证）：建立了基于证据的验证体系，本次在此基础上强化检视闭环
- F2026051106（检视提示词优化）：重构了检视工作流为五阶段，本次在阶段三和阶段五增加约束
- F2026050608（代码注释检查闭环）：强化了 why-comment 检查闭环，本次用类似思路强化质量改进闭环

## 目标

消除"非阻塞可跳过"的认知偏差，确保审查者提出的所有问题都在当前 PR 中得到处理，检视结论必须逐条列出问题处置状态。

### P1 — 审查者手册闭环强化

- 质量改进必须在当前 PR 修复，不得推到后续 feature
- 检视结论必须逐条列出每个问题的处置状态
- 复检时必须逐条对照上轮检视意见，拦截跳过的问题

### P2 — 开发者手册约束收紧

- 开发者不得以"不阻塞"或"可后续优化"为由拒绝审查者提出的合理质量改进

### P3 — 术语统一

- 将"非阻塞改进"统一替换为"质量改进"，消除术语本身的心智偏差

## 非目标

- 不改变检视的五阶段工作流程结构
- 不改变 merge 阶段的硬性条件（维护者职责不变）
- 不改变交叉审视的对抗机制
- 不引入新的工具或自动化检查

## 设计

### P1 详设

**改动 1：审查者手册·阶段三——质量改进闭环**

在第 8 条（非阻塞改进必须提出）之后，增加闭环约束：

- 提出的问题必须在当前 PR 中修复——审查者提出的所有问题（无论严重度）都是检视意见，开发者必须在当前 PR 中处理。复检时逐条确认：未修复的问题就是待处理问题，检视不能清零

**改动 2：审查者手册·阶段五——结论格式约束**

在阶段五中增加结论格式要求，检视结论必须逐条列出每个问题的处置状态：

- `[已修复]` — 开发者已在当前 PR 修复
- `[开发者回应]` — 开发者有合理理由不修改，审查者认可
- `[待处理]` — 开发者尚未处理或回应

只有全部问题为"已修复"或"开发者回应（审查者认可）"时，才能给出"可等待用户合入"结论。存在任何"待处理"项时，结论必须是"需要开发者继续处理"。

**改动 3：审查者手册·复检流程——跳过拦截**

复检时发现开发者跳过了之前提出的任何问题（包括质量改进），必须打回。逐条对照上一轮检视意见，确认每条都有对应的修复或经审查者认可的回应。

### P2 详设

**改动 4：开发者手册·阶段二——不得以严重度为由拒绝**

审查者提出的改进意见，只要确实能提升代码质量，不得以"不阻塞"或"可后续优化"为由拒绝在当前 PR 修复。"不合理"仅限于：事实错误、理解偏差、或修复会引入更大风险。

### P3 详设

**改动 5：术语替换**

将"非阻塞改进"统一替换为"质量改进"，涉及文件：
- `config/sop/code-delivery/review#reviewer.handbook.md`（阶段三第 8 条、自检清单）
- `config/sop/code-delivery/shared.handbook.md`（完成标准段落）

### 设计决策

| # | 决策 | 理由 |
|---|---|---|
| D1 | 保留"阻塞/非阻塞"分类用于问题严重度描述，但禁止用于决策"是否修复" | 分类本身有价值（帮助优先级排序），问题在于被误用为跳过依据 |
| D2 | 结论格式用中括号标签而非表格 | PR 评论中表格渲染不稳定，标签格式更可靠 |
| D3 | "开发者回应"需要审查者认可 | 防止开发者单方面关闭问题，确保双方达成共识 |
