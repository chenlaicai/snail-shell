# F20260702cstr — Design 阶段协作优化

## 背景

用户发现 AI 间协作不明显：架构师完成独立分析后直接 @用户，而不是先与对方架构师交叉审视。用户不得不充当"人工消息路由器"，手动在两位架构师之间调度每一步交互。

**实际对话证据（6/30 - 7/2 的 7 个 Issue）**：

| Issue | 架构师-1 完成分析后的路由目标 | 用户手动路由次数 |
|-------|---------------------------|----------------|
| F20260630u38q | user（发出 stage_transition） | 6 次 |
| F20260630jeds | user | 7 次 |
| F20260701tj92 | user | 4 次 |
| F20260702bhqh | 架构师-2 ✅ | 3 次（用户纠正后退化） |
| F20260701nbbn | 架构师-2 ✅ | 2 次 |

5 个 design 阶段 Issue 中，只有 2 个架构师-1 自发路由给架构师-2。当协作确实发生时，审视质量很高——架构师-2 平均发现 5 个架构师-1 遗漏的实质问题。

## 根因分析

| # | 根因 | 类型 |
|---|------|------|
| 1 | cross-review.md 规则已存在但未被遵守 | 规则执行 |
| 2 | SKILL.md 主流程对 cross-review.md 的引用信号不够强 | 规则优先级 |
| 3 | 架构师-1 没有把架构师-2 视为"共同设计者"，而是视为"审查者" | **角色认知** |
| 4 | LLM "尽快给结果"倾向与"先@对方"规则冲突 | LLM 特性 |
| 5 | 用户纠正后 LLM 优先回应用户，跳过交叉审视 | LLM 特性 |
| 6 | "独立分析完成"被等同于"可以给用户看" | **完成定义** |
| 7 | 系统 prompt 暗示架构师可以选择路由给谁 | **prompt 措辞** |

**关键洞察**：问题不是规则缺失（cross-review.md 已有完整的三阶段流程），也不是系统没有兜底机制，而是 **AI 不知道正确的做事思路**。架构师-1 把自己定位为"主设计者"，把架构师-2 定位为"辅助审查者"，把用户定位为"直接汇报对象"。

## 目标

**P1 — 认知重构：让架构师自然地认为"先和对方讨论"是做事的正确方式**

通过修改 SKILL.md 角色定义、工作流程措辞和系统 prompt，改变架构师对自身角色和协作关系的理解。

## 非目标

- 不修改 `collaboration.ts` 的路由代码逻辑（仅更新路由目标声明的 prompt 文本）
- 不实现路由拦截或自动路由
- 不修改 `set_final_body` 的 MCP 接口
- 不实现 cross_review_completed 标记

## 核心业务行为

| # | 场景 | 预期行为 |
|---|------|----------|
| B1 | 当架构师-1 完成独立分析时 | 产出的是"草稿方案"，必须路由给架构师-2 进行对抗审视 |
| B2 | 当架构师-2 完成对抗审视且双方达成共识时 | 最终方案呈现给用户 |
| B3 | 当用户纠正架构师的设计后 | 架构师修正设计，将修正后的草稿方案路由给架构师-2 重新审视 |
| B4 | 当双方存在分歧无法达成共识时 | 升级到用户裁决 |
| B5 | 当架构师在消息文本中写了 @user 时 | 设计阶段的路由应遵循"草稿方案→架构师-2"的规则 |

## [design-time] 设计

### 关键设计决策

**D1：解决方案类型 — 认知重构 + prompt 设计，而非系统兜底**

曾考虑的方案：
- 路由拦截（validateToSpeakers throw Error）→ 用户指出：事后兜底，约束过于死板
- 自动路由（resolveReplies 自动设置）→ 用户指出：系统的写死逻辑不是正确方向

最终方案：让 AI 理解正确的做事思路，通过 prompt 设计引导行为。

正方：更符合问题本质（AI 不知道正确思路）；侵入性低（不修改代码）。
反方：可靠性依赖 LLM 对 prompt 的理解。
结论：采用。配合轻量级软提醒作为辅助。

**D2：角色定位 — "共同设计者"而非"主设计者 + 辅助审查者"**

当前隐含的角色定位：
- 架构师-1 = 主设计者（产出方案）
- 架构师-2 = 辅助审查者（审一下方案）
- 用户 = 直接汇报对象

修正后的角色定位：
- 架构师-1 + 架构师-2 = 共同设计者（各自独立分析，交换方案，对抗审视）
- 用户 = 升级裁决者（只有在达成共识或需要裁决时才介入）

**D3：完成定义 — "草稿方案"和"最终方案"的区分**

架构师-1 完成独立分析后，产出的是"草稿方案"，不是"最终方案"。
草稿方案必须经过架构师-2 的对抗审视后，才能成为"最终方案"呈现给用户。

正方：改变架构师对"完成"的理解，从根本上解决路由问题。
反方：依赖 LLM 理解"草稿"和"最终"的区分。
结论：采用。

**D4：轻量级技术辅助 — validateToSpeakers 软提醒**

在 `validateToSpeakers` 中，当检测到架构师在 design 阶段路由给 user 时，返回警告（不拦截）。

正方：提供善意提醒，与认知重构方向一致。
反方：LLM 可能忽略警告。
结论：采用。不强制拦截，仅提醒。

### 三层防护

| 层级 | 机制 | 文件 |
|------|------|------|
| 认知层 | 明确"共同设计者"角色定位，草稿方案→对抗审视→最终方案 | SKILL.md |
| 规则层 | 禁止单方确认，强化 @mention 触发条件 | cross-review.md |
| 提示层 | 路由目标声明 + validateToSpeakers 软提醒 | 系统 prompt + snail-final-response.ts |

### SKILL.md 修改

**角色定义修改**：

当前：
```
架构师-1：负责需求分析与方案设计
架构师-2：负责交叉审视与方案验证
```

修正后：
```
架构师-1 和 架构师-2：共同负责需求分析与方案设计。两位架构师各自独立分析，交换方案，对抗审视，合并收敛。
```

**工作流程修改**：

当前：
```
2. 需求分析 — 独立分析需求
3. 交叉审视 — 两位架构师 @mention 交互
```

修正后：
```
2. 需求分析 — 独立分析需求，产出草稿方案
   ↓
   [HARD] 草稿方案必须路由给对方架构师进行对抗审视
   ↓
3. 交叉审视 — 交换草稿方案，对抗审视，合并收敛为最终方案
   ↓
   最终方案呈现给用户
```

**增加协作规则**：
```
设计阶段的直接协作对象是架构师-2，不是用户。用户是升级裁决者，不是日常工作汇报对象。
只有在以下情况才路由给用户：
- 双方架构师达成共识，呈现最终方案
- 双方存在分歧，需要用户裁决
```

### cross-review.md 修改

强化 @mention 触发条件措辞：

当前：
```
架构师在对话中完成独立分析且分析包含至少一个修复方向后，直接 @对方架构师请求审视
```

修正后：
```
架构师完成独立分析后，产出的是草稿方案。草稿方案必须路由给对方架构师进行对抗审视，审视达成共识后才能成为最终方案呈现给用户。
```

### 系统 prompt 修改

当前：
```
**路由目标声明**：如果需要其他角色继续处理，必须在 set_final_body 的 to_speakers 参数中声明目标角色。
```

修正后：
```
**路由目标声明**：
- design 阶段：您的输出是草稿方案，必须路由给架构师-2 进行对抗审视。审视达成共识后，再向用户呈现最终方案。
- 其他阶段：如果需要其他角色继续处理，在 set_final_body 的 to_speakers 参数中声明目标角色。
```

### validateToSpeakers 软提醒

在 `validateToSpeakers` 中增加软提醒（不拦截）：

```typescript
if (stageKey === "design" && isArchitect(currentSpeaker) && targets.includes("user")) {
  // 软提醒，不拦截
  logger.warn("Design阶段：您的草稿方案是否已经过对方架构师审视？");
}
```
