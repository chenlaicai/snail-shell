## 设计 [required]

### 根因分析

#### 根因 1：只有禁令，没有替代行为（核心）

所有修复都是**负面约束**（"不得要求迁移"、"不得写兼容性桥接"），但没有给架构师一个**正面替代**：当检测到破坏性变更时，应该做什么？

架构师的对抗性心智模型天然会问"会不会破坏已有行为？"——这个问题本身合理。但系统只说了"别回答兼容性"，没说"应该怎么回答"。于是架构师要么沉默（违反质疑义务），要么把顾虑包装成其他措辞。

#### 根因 2：交叉审视清单触发兼容性思维

cross-review.md 的检查点"是否会引入回归风险或破坏已有行为？"天然激活兼容性思维。架构师被要求从这个角度审视，然后又被禁止在这个角度上表达，认知冲突由此产生。

#### 根因 3：T-01 十诫过于抽象

"兼容性是 bug 放大器"是元认知约束，但 AI agent 无法从这条抽象规则推导出"面对 schema 变更时不应该问迁移策略"。F20260630mxmn 的纠偏确认了这一点——问题在 skill 层，不在 tenet 层。

#### 根因 4：概念混淆缺乏纠正机制

msg #5460 显示架构师将"包体积"与"架构兼容性"混为一谈。系统没有机制识别和纠正这种概念漂移。

#### 根因 5："兼容性"作为业务偏好的反面教材

cd-design L46 将"是否保留向后兼容"列为业务偏好示例。这在决策模式分类中正确，但副作用是让"兼容性"在架构师认知中被标记为"需要讨论的维度"，与 T-01 的"别考虑兼容性"形成认知矛盾。

### 为什么加更多规则不会有效

已有规则覆盖了**具体的违规模式**，但问题的产生机制是：

1. 对抗性审视天然触发"会不会破坏已有行为"的思维
2. "兼容性"被标记为业务偏好 → 架构师认为需要考虑
3. 被禁止表达 → 包装成其他措辞
4. 系统检测到的是措辞，不是思维模式

**策略转变**：不加更多禁令，而是给架构师一个正面替代行为——检测到破坏性变更时，走"不兼容更新"记录 + 建议层流程。

### 修复方案

[D1] **修改 1：cd-design SKILL.md L38 — 替换禁令为破坏性变更处置规则**

将当前的 [HARD] 禁令替换为正面指引，聚焦于**非数据库破坏性变更的出口**（数据库规则已被遵循，保留原话）：

```
- **[HARD] 破坏性变更处置规则**：当审视发现破坏性变更时，禁止讨论"如何保持兼容"或"如何平滑迁移"——这不是设计问题，是系统决策。处置方式：
  - 数据库 schema 变更：只允许 CREATE TABLE IF NOT EXISTS，严禁 ALTER TABLE、迁移脚本（已有规则）
  - 非数据库破坏性变更：记录到 Feature 文档 `## 不兼容更新` 段落，标注变更内容和影响范围
  - 涉及删除已有功能：走建议层流程，向用户说明影响并请求确认
  - 涉及行为修改：写入行为规格条目，确保"当 X 时，应该 Y"覆盖新行为
```

[D2] **修改 2：cd-design SKILL.md L46 — 移除"向后兼容"业务偏好示例**

```
- **业务偏好**：无客观对错、取决于产品定位或用户取向的选择。例：优先一致性还是
  可用性、错误信息面向开发者还是终端用户、日志详细程度。
```

[D3] **修改 3：cross-review.md L113 — 拆分为两个独立检查点**

将"是否会引入回归风险或破坏已有行为？"拆分：

```
- 是否会引入回归风险？（关注非预期的行为退化）
- 如涉及破坏性变更（删除/修改已有 API、行为语义变更），是否已按"破坏性变更处置规则"处理？
```

[D4] **修改 4：cross-review.md — 新增"破坏性变更"定义标准**

```
**属于破坏性变更**：
- 删除已有功能、API、配置项
- 修改已有行为的语义（"当 X 时，应该 Y" 变为 "当 X 时，应该 Z"，且 Y≠Z）
- 修改已有数据模型的字段（新增 NOT NULL 字段、删除字段、修改字段类型）

**不属于破坏性变更**：
- 新增可选字段、新增 API、新增功能
- 不改变语义的 bug 修复（修复后行为符合原始设计意图）
- 错误信息措辞改进（除非下游代码依赖特定字符串匹配）

**边界 case**：默认配置值变更——如果用户显式设置了该配置，不影响；如果用户依赖默认值，是破坏性变更。判断标准：该配置是否有文档化的默认值？用户是否有合理理由依赖该默认值？
```

[D5] **修改 5：cross-review.md — 明确"不兼容更新"段落的记录标准**

```
**"不兼容更新"段落记录标准**：
- 架构师在 design 阶段识别破坏性变更后，记录到 Feature 文档 `## 不兼容更新` 段落
- 记录内容：变更描述、影响范围、是否需要用户确认
- [Incompatible] 标签由开发者在 development 阶段标注，架构师不标注标签
- 两者是上下游关系：架构师识别 → 开发者标注

**审视义务交互**：已记录的破坏性变更仍计入风险点（质疑义务基于"发现了什么"而非"处理了什么"）
```

[D6] **T-01 定位**：T-01 的"兼容性是 bug 放大器"保留为全局元认知约束。修复目标是补全 skill 层的转化——对开发者已到位（cd-development L19），对架构师需要补全（本次修复）。

## 设计约束摘要 [required]

### 硬约束（违反 = bug）

- 破坏性变更不得讨论"如何保持兼容"或"如何平滑迁移"
- 数据库 schema 只允许 CREATE TABLE IF NOT EXISTS（已有规则，保留）
- 非数据库破坏性变更必须记录到 Feature 文档 `## 不兼容更新` 段落
- 回归风险和破坏性变更作为两个独立检查点审视
- "不兼容更新"段落与 [Incompatible] 标签是上下游关系，架构师只负责段落

### 设计取舍（必须保留）

- [D1] 禁令替换为正面处置规则——LLM 对"当 X 时做 Y"的遵循优于"不要做 X"
- [D2] 移除"向后兼容"业务偏好示例——消除与 T-01 的认知矛盾
- [D3] L113 拆分——回归风险不应被决策树"消耗"
- [D4] 破坏性变更定义——明确边界减少概念混淆
- [D5] 段落与标签区分——明确架构师与开发者的职责边界
- [D6] T-01 保留——元约束层不变，补全 skill 层转化

### 语义不变量

- T-01 十诫层不变
- 开发者侧规则不变（cd-development L19、L22）
- 审查者侧规则不变（cd-review adversarial-check.md L100）
