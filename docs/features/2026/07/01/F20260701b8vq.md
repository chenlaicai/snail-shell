# F20260701b8vq — 日志文件去重与职责分离

## 背景

当前日志机制存在三个文件、两条链路，其中 pino stdout target 导致内容重复：

| 文件 | 写入方 | 内容 | 问题 |
|------|--------|------|------|
| `server.log` | `bin/snail-service` 捕获 Node.js 进程 stdout+stderr | 后端 pino JSON + 非 pino 输出 | 每次启动截断；pino 日志和 snail-shell.log 重复 |
| `snail-shell.日期.log` | pino-roll（root logger file target） | 后端 pino JSON | 正常，有轮转 |
| `web.log` | `bin/snail-service` 捕获 Vite 进程 stdout+stderr | Vite 输出 + pino JSON（web logger stdout target） | pino 日志和 web.日期.log 重复 |
| `web.日期.log` | pino-roll（web logger file target） | 前端性能日志 pino JSON | 正常，有轮转 |

根因：`src/infra/logger.ts` 中两个 pino logger 都配置了 `pino/file destination: 1`（stdout target），而 `bin/snail-service` 又把进程 stdout 重定向到 `server.log` / `web.log`。同一条 pino 日志走了三条路径：pino-roll 文件 + stdout → server.log/web.log。

## 设计目标

1. **消除重复**：每条日志只写入一个最终落盘位置
2. **职责清晰**：pino-roll 文件承载结构化日志，server.log/web.log 只承载进程级输出
3. **排查可靠**：排查问题时有明确的日志查阅路径，不需要对比多个文件

## [design-time]

### 核心业务行为

- 当 pino logger 初始化时，应该只配置 pino-roll file target，不配置 stdout target
- 当 `bin/snail-service` 启动进程时，应该将进程 stdout+stderr 捕获到 server.log/web.log（保留现有行为）
- 当排查后端问题时，应该查阅 `logs/snail-shell.YYYY-MM-DD.log`（结构化 JSON，有历史）
- 当排查启动失败时，应该查阅 `server.log`（非 pino 的进程输出）或 tail pino-roll 当日文件
- 当排查前端性能问题时，应该查阅 `logs/web.YYYY-MM-DD.log`

### 改动范围

| 文件 | 改动 |
|------|------|
| `src/infra/logger.ts` | root logger 和 web logger 移除 `pino/file destination: 1` target |
| `README.md` | 更新日志路径说明，明确 pino-roll 文件为主要日志位置 |

### 设计决策：移除 stdout target vs 其他方案

**正方（移除 stdout target）**：
- 从根本上消除重复——pino 日志只走 pino-roll 一条路径
- server.log 恢复其本来用途：只包含非 pino 的进程输出（Vite 启动信息、Node.js warning、未捕获异常的原始输出）
- pino-roll 文件写入是同步的（pino-roll 使用 async file write），`tail -f snail-shell.log` 可实时查看
- 改动最小，只涉及 logger.ts 一处

**反方**：
- 习惯 `tail -f server.log` 看所有日志的用户需要切换到 `tail -f logs/snail-shell.log`
- server.log 变小后，`print_log_tail` 诊断输出可能不够详细

**反驳**：
- `tail -f logs/snail-shell.log` 是更可靠的习惯——看到的是带时间戳的结构化 JSON，不是混杂的 stdout
- `print_log_tail` 用于诊断启动失败，此时需要的是非 pino 的错误信息（进程崩溃栈、端口占用等），pino 日志反而干扰诊断

### 设计决策：server.log 截断行为

当前 `: > "$log_file"` 每次启动截断 server.log。移除 stdout target 后，server.log 只包含非 pino 输出（通常很少），截断行为不变——每次启动看到干净的进程输出，符合预期。不需要额外轮转。

### 不兼容更新

**server.log / web.log 内容语义变化**：文件路径不变，但内容从"全部日志（pino JSON + 进程输出）"变为"仅进程级输出（非 pino）"。排查后端问题的主路径从 `server.log` 切换到 `logs/snail-shell.YYYY-MM-DD.log`。开发者需调整排查习惯。

## 验收标准

- AC-1：root logger transport 中不包含 `pino/file destination: 1` target
- AC-2：web logger transport 中不包含 `pino/file destination: 1` target
- AC-3：`npm run check` 通过
- AC-4：启动服务后，`server.log` 中不包含 pino JSON 格式日志（`{"level":...}` 形式）
- AC-5：启动服务后，`logs/snail-shell.log` 中包含正常的后端 pino 日志
- AC-6：前端性能日志正常写入 `logs/web.YYYY-MM-DD.log`
- AC-7：`README.md` 中日志路径说明更新为 pino-roll 文件为主要日志位置，server.log/web.log 定位为进程级输出
