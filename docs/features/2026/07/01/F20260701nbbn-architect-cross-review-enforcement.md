# F20260701nbbn [sop] 架构师交叉审视强制执行机制

<!-- [design-time] 以下章节在需求收敛与设计阶段（代码前）完成并锁定 -->

## 背景

架构师交叉审视流程（Phase 2）在实际执行中经常被跳过。典型模式为：用户发言 → 架构师-1 独立分析 → 架构师-1 直接向用户呈现方案。Phase 2（交换对抗）和 Phase 3（合并收敛）未发生，架构师-2 的审视职责被转嫁给用户。

SOP (`cross-review.md`) 定义了三阶段流程，但缺少强制执行机制，导致架构师走阻力最小的路径。

## 目标

确保架构师交叉审视流程（Phase 2）必须发生，而非可选。

### P1 — 强制执行交叉审视

1. 在 Stage Gate 中增加 design-04 条件，要求必须有至少一轮交叉审视记录
2. 定义 @mention 交互协议，明确触发条件、响应格式和轮次约束
3. 禁止单方确认：Phase 2 完成前不得向用户呈现方案
4. 定义升级流程：架构师无法达成共识时的处理机制

## 非目标

- 不改变架构师的角度分工（架构师-1 业务/用户/前端，架构师-2 技术/架构/风险）
- 不引入新的角色或协调者
- 不改变 Issue context 的使用约束（只存指针，不存内容）

## 核心业务行为

| # | 场景 | 预期行为 | 测试覆盖 |
|---|------|----------|----------|
| B1 | 当架构师将独立分析写入 worktree 文件且文件内容包含至少一个修复方向时 | 系统应阻止架构师直接向用户呈现方案，要求先 @对方架构师请求审视 | |
| B2 | 当审视意见中引用了独立分析的具体内容（如根因编号、修复方向）而非仅给出结论时 | 系统应接受该审视意见为有效审视 | |
| B3 | 当 Phase 2 未完成时 | 系统应阻止进入产出锁定阶段（design-04 Gate 不通过） | |
| B4 | 当 Feature 文档的决策记录中缺少另一方架构师的参与记录时 | 系统应提示需要另一方架构师的审视意见 | |
| B5 | 当两位架构师经过 3 轮交互仍未达成共识时 | 系统应触发升级流程，@用户并附带分歧摘要 | |

## 设计

### 问题诊断

#### 根因分析

| # | 根因 | 类型 | 说明 |
|---|------|------|------|
| R1 | Phase 2 缺少强制 Gate 条件 | 设计缺口 | Stage Gate 不要求 Phase 2 必须发生 |
| R2 | @mention 机制缺乏触发规则 | 设计缺口 | 路由表允许双向流转，但没有定义何时触发、响应格式 |
| R3 | 产出锁定规则可被绕过 | 设计缺口 | 锁定步骤直接面向用户，绕过了架构师互审 |
| R4 | 已有规则未被执行 | 执行缺口 | cd-design SKILL.md 有交叉审视要求，但无强制机制 |

#### 对抗性审视过程

本轮诊断经历了两轮完整的交叉审视：

**第一轮**：
1. **架构师-1 独立分析**：识别 4 个根因（Phase 切换无协调、锁定规则绕过互审、@mention 无触发规则、无共享存储）
2. **架构师-2 对抗审视**：根因 2 归因偏差、根因 4 过度设计、补充真正的根因
3. **架构师-1 回应**：接受过度设计批评，坚持"设计缺口"归因
4. **架构构师-2 确认**：接受"设计缺口 + 执行缺口两者并存"

**第二轮**（严格审视）：
1. **架构师-2 正式审视报告**：
   - RISK-1：design-04 Gate 可被形式主义绕过
   - RISK-2：@mention 协议缺少最大轮次约束
   - GAP-1：升级流程未定义
   - 核心业务行为 S1 需精确化
2. **架构师-1 回应**：全部接受，修正 Gate 检查方式、增加轮次约束、补充升级流程、精确化触发条件
3. **架构师-2 确认**：接受所有回应，无未解决分歧

### P1 详设

#### 修复 1：增加 design-04 Gate 条件

在 `cross-review.md` 的 Stage Gate 中增加：

- **design-04**：存在至少一轮交叉审视记录（双方各自的审视 + 对方的回应）

Gate 检查方式：
- Feature 文档的"关键决策记录"章节中必须有至少两条参与者不同的决策记录
- 每条决策记录的"正方论点"和"反方论点"字段不得为空，且不得是同一论点的复述（防止形式主义绕过）

#### 修复 2：定义 @mention 交互协议

在 `cross-review.md` 中增加 Phase 切换协议：

**触发条件**：
- 架构师完成独立分析后，必须将分析写入 worktree 文件
- 通过 Issue context 写入路径指针（key 格式：`design.arch{N}_analysis_path`）
- 然后 @对方架构师请求审视

**响应格式**：
- 审视者必须展示独立分析过程
- 禁止"分析全面，同意方案"作为唯一输出
- 必须满足质疑义务最低要求（risk >= 2, gap >= 1, alternative >= 1）

**交互轮次约束**：
- 最少一轮审视 + 一轮回应
- 最多 3 轮（审视 → 回应 → 再审视 → 再回应 → 最终审视）
- 超过 3 轮仍未达成共识，触发升级流程（见修复 5）
- 禁止单方确认

#### 修复 3：禁止单方确认

在 `workflow.md` 阶段四"产出锁定"中增加前置条件：

- 产出锁定前必须有双方审视记录
- 缺少一方审视则 Gate 不通过
- Phase 2 完成前不得向用户呈现方案

#### 修复 4：存储修正

独立分析产物存储方式：
- **内容**：写入 worktree 文件（如 feature 文档的独立章节，或独立分析文档）
- **指针**：Issue context 只存文件路径（如 `design.arch1_analysis_path`）
- **禁止**：Issue context 不得存放大段文本、检视计划、方案内容

#### 修复 5：升级流程

在 `cross-review.md` 中增加升级机制：

**触发条件**：
- 3 轮交互后仍未达成共识
- 或任一架构师明确表示无法接受对方方案

**升级方式**：
- @用户，附带分歧摘要

**分歧摘要格式**：
- 双方各自的核心论点（各 1-2 句话）
- 无法达成共识的具体点

## 设计约束摘要

- **边界**：不改变 Issue context 的使用约束（只存指针），不引入新的角色
- **关键决策**：问题本质是"设计缺口 + 执行缺口"两者并存，非单一原因
- **非目标约束**：不改变架构师角度分工，不引入协调者角色
- **语义不变量**：Phase 2 必须在产出锁定前完成，不可跳过
