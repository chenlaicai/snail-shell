# F20260701h4rm [docs] Feature 文档模板优化：决策留痕与必填 enforcement

<!-- [design-time] 以下章节在需求收敛与设计阶段（代码前）完成并锁定 -->
<!-- 进入实现阶段后不得单方面修改，如需变更须通过问题卡片向用户提出并确认 -->

## 背景

当前 feature 文档模板存在三个结构性问题，导致模板合规性在近期文档中持续退化：

**退化证据**（4 份近期文档对比）：

| 文档 | 决策记录 | 设计约束摘要 | 核心业务行为 |
|------|---------|------------|------------|
| F20260626g7rt (06-26) | ✅ 8列格式，6条 | ✅ 4条 | ✅ B1-B10 表格 |
| F20260630advp (06-30) | ✅ 4列格式，6条 | ✅ 6条 | ✅ B1-B6 表格 |
| F20260701w8ey (07-01) | ⚠️ 5列，非标准命名 | ❌ 缺失 | ⚠️ 散文而非表格 |
| F20260701rq3d (07-01) | ⚠️ 风险与决策混杂 | ❌ 缺失 | ❌ 完全缺失 |

**根因分析**：

1. **决策记录是"事后补记"**：底部决策表与设计章节分离，AI 先写设计、事后补记——于是跳过或草草填写。F20260701rq3d 的设计中描述了三个关键决策，但只存在于正文，未进入决策记录表。
2. **风险和决策混为一谈**：F20260701rq3d 使用"风险与决策记录"把风险（识别准确性）和决策（prompt 规则方案）放同一张表。决策需要正反论点，风险需要缓解策略——混在一起两者都不清晰。
3. **"应该"和"必须"边界模糊**：模板对所有章节使用同等权重的描述语气，没有区分哪些是"不填不得推进"的硬约束、哪些是"建议填写"的软约束。架构师在时间压力下自行判断跳过哪些——而跳过的恰好是下游角色最需要的。

## 目标

1. 将决策记录从"事后补记"改为"过程产物"——设计章节内嵌决策标记
2. 将风险从决策记录中分离，独立为跟踪对象
3. 改造设计约束摘要为分类速查，保留原名
4. 在模板中显式标注 required/optional，配合 Gate 检查阻止退化

## 非目标

1. 不新增交接清单或执行摘要章节（改造现有章节而非新增）
2. 不改变 feature 文档的整体结构和生命周期管理
3. 不引入自动化工具或脚本
4. 不修改已合入的历史 feature 文档
5. 不改变 [design-time] 章节的锁定机制

## 核心业务行为

| # | 场景 | 预期行为 | 测试覆盖 |
|---|------|----------|----------|
| B1 | 当模板中标注 `[required]` 的章节未填写时 | 系统必须阻断 design → development 推进（Gate 自检 fail） | |

## 设计

### 改动 1：设计章节内嵌 `[Dn]` 决策标记

> **[D1]** 选择"正文内嵌标记 + 底部轻量索引"方案。正方：决策在产生的地方被记录，负担最低（正文一句话 + 底部一行索引）。反方：需要架构师在设计过程中主动判断"什么算关键决策"。依据：8 列表格失败的根因是填写负担高 + 判断标准模糊，内嵌标记降低填写负担，显式触发条件解决判断标准问题。

在 `## 设计` 章节中，当描述到关键决策时，使用内联标记：

```markdown
> **[Dn]** {结论}。正方：{理由}。反方：{理由}。依据：{依据}
```

**`[Dn]` 标记的触发条件**（满足以下任一条件即必须标记）：

1. **有正反论点**：存在被否决的替代方案（如"选择 A 而非 B"）
2. **改变行为语义**：该决策改变了系统的外部可观测行为
3. **限制下游选择**：该决策限制了开发者或审查者的后续选择空间

底部 `## 关键决策记录` 表格变为纯索引（`#|决策点|最终决策|状态` 四列），通过 `Dn` 编号自然关联到设计正文中的内联标记。正反论点、决策依据只存在于内联标记中，信息只在一个位置。

**架构师行为规范**（设计过程中的操作规则）：

- 当架构师在设计章节中遇到关键决策时，必须在正文中用 `> **[Dn]**` 标记记录决策摘要（结论 + 一句话依据）
- 当架构师判断"什么算关键决策"时，必须满足触发条件三条件之一
- 当架构师填写"关键决策记录"表格时，必须使用纯索引格式（`#|决策点|最终决策|状态`）
- 当架构师填写"风险与缓解"章节时，必须使用独立表格（`#|风险|严重程度|影响|缓解策略|负责方`），不得与决策记录合并
- 当架构师填写"设计约束摘要"时，必须按"硬约束/设计取舍/语义不变量/非目标"四分类
- 当审查者发现设计决策需要修正时，必须在决策记录的状态列中标记为"审查阶段修正"，并关联范围变更记录

### 改动 2：风险独立为 `## 风险与缓解`

> **[D2]** 将风险从决策记录中分离。正方：风险的生命周期（持续跟踪）和决策（一次确认）不同，混在一起两败俱伤；F20260701rq3d 的混杂表是反面教材。反方：增加一个章节的维护成本。依据：分离后审查者有独立的风险关注入口，不再需要从决策表中筛选风险条目。

新增 `## 风险与缓解` 章节（标记为 `[required]`），格式：

```markdown
## 风险与缓解

| # | 风险 | 严重程度 | 影响 | 缓解策略 | 负责方 |
|---|------|----------|------|----------|--------|
| R1 | {风险描述} | 高/中/低 | {影响范围} | {缓解措施} | {角色名} |
```

### 改动 3：`## 设计约束摘要` 改为分类速查

> **[D3]** 设计约束摘要保留原名，内部组织改为"硬约束/设计取舍/语义不变量/非目标"四分类。正方：比当前的"边界/关键决策/非目标约束/语义不变量"更直觉，开发者 30 秒内知道什么不能做；保留"语义不变量"因为它无法归入其他三类。反方：改变分类方式可能造成短期混乱。依据：当前分类过于抽象（"语义不变量"不易理解），新分类加括号说明直接对应行动指令。

改造后的格式（标记为 `[required]`）：

```markdown
## 设计约束摘要

### 硬约束（违反即 bug）
- {不得越过的范围限制}

### 设计取舍（不得自行推翻）
- {已确认的设计决策及理由}

### 语义不变量（实现中必须保持为真）
- {持续为真的条件}

### 非目标（不得扩展）
- {明确不处理的范围}
```

### 改动 4：决策表格简化为 4 列纯索引 + 状态列

> **[D4]** 决策表格从 8 列简化为 4 列纯索引 + 状态列。正方：移除"参与者"、"日期"和"正反论点"（参与者和日期可从对话追溯，正反论点移至内联 `[Dn]` 标记）；新增状态列支持逆向反馈流（审查修正回流）。反方：简化可能丢失追溯信息。依据：参与者和日期从未被下游角色使用过，而状态列解决了"审查发现设计缺陷如何回流"的问题。

新格式：

```markdown
| # | 决策点 | 最终决策 | 状态 |
|---|--------|----------|------|
| D1 | {决策点} | {选择的方案} | 设计阶段确认 |
```

底部表格是纯索引——正反论点、决策依据只存在于设计章节的 `[Dn]` 内联标记中。

**状态列定义**：
- `设计阶段确认`：架构师在设计阶段做出的初始决策
- `审查阶段修正`：审查者发现设计缺陷后修正的决策（需关联范围变更记录）
- `用户确认`：经用户确认的决策（覆盖前两种状态）

### 机制补充 M1：模板所有章节标注 `[required]` / `[optional]`

> **[D5]** 在模板中显式标注 required/optional。正方：这是阻止退化趋势的根本机制——没有 enforcement，任何格式都会退化。反方：增加模板的视觉噪声。依据：4 份文档的退化趋势证明"应该填写"不够，必须"不填不得推进"。

模板标注方案：

| 章节 | 标注 |
|------|------|
| 背景 | `[required]` |
| 目标 | `[required]` |
| 非目标 | `[required]` |
| 核心业务行为 | `[required]` |
| 设计 | `[required]` |
| 生效路径 | `[required]` |
| 设计约束摘要 | `[required]` |
| 改动范围 | `[required]` |
| 验证 | `[required]` |
| 关联 | `[required]` |
| 关键决策记录 | `[required]` |
| 风险与缓解 | `[required]` |
| 未实现说明 | `[optional]` |
| 范围变更记录 | `[optional]`（有变更时 required） |

### 机制补充 M2：Gate 自检增加模板合规性检查

> **[D6]** 在 design Gate 自检中增加 `design-04: required 章节合规性检查`。正方：Gate 是 enforcement 的最后一道防线，缺失 Gate 检查等于没有 enforcement。反方：增加 Gate 自检项可能拖慢设计阶段。依据：F20260629v7k7 证明 Gate 检查是有效的 enforcement 机制（context 记录 enforcement 同理）。

新增 Gate 自检项：

| ID | 清单项 | 必须 |
|---|--------|------|
| design-04 | 所有 `[required]` 章节已填写且内容非空 | ✅ |

**边界条件**：required 章节未填写时，**阻断** design → development 推进（Gate 自检 fail），不得降级为警告。`required` 的语义就是"不填不得推进"。

## 设计约束摘要

### 硬约束（违反即 bug）
- 不改变 feature 文档的整体结构和生命周期管理
- 不改变 [design-time] 章节的锁定机制
- `required` 章节未填写时必须阻断推进，不得降级为警告

### 设计取舍（不得自行推翻）
- 改造现有章节而非新增章节（不新增交接清单或执行摘要）
- 决策内嵌标记（`[Dn]`）替代底部完整表格，降低填写负担
- 风险与决策分离为独立章节，生命周期不同必须分开跟踪
- 设计约束摘要保留原名，内部改为四分类（硬约束/设计取舍/语义不变量/非目标）

### 语义不变量（实现中必须保持为真）
- Feature 文档模板的 `[design-time]` 章节在进入实现阶段后不得单方面修改
- `[required]` 的语义是"不填不得推进"，与 `[optional]` 有明确的行为差异
- Gate 检查只防完全缺失，填写质量由交叉审视保证（分工边界不可模糊）

### 非目标（不得扩展）
- 不引入自动化工具或脚本
- 不修改已合入的历史 feature 文档
- 不新增交接清单或执行摘要章节
