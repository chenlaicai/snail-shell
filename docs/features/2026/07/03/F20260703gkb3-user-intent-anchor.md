# F20260703gkb3 用户意图锚：全面意图保真机制

## 背景 [required]

当前 code-delivery SOP 在管线各阶段设有逻辑正确性防线（行为条目 S1-S5、交叉审视、证据规则、审查禁逃），但缺少**语义保真度**防线。用户的精确描述（空间位置、时序关系、数量约束、交互细节等修饰语）在管线 handoff 中被系统性丢失。

**真实案例**：用户明确指定"发言中加载标识在气泡的左侧"，最终实现为"在气泡的上一行"。经追溯，架构师-1 记录时丢失了空间修饰语"左侧"，架构师-2 审视时未校验用户原话保真度，审查者仅检查代码逻辑无法还原视觉效果。三个防线全部未能拦截。

**根因**：管线中没有以"用户原始表达"为锚点的保真校验机制。现有 Task Anchor（F2026052105）解决的是"为什么做"的意图保持，不解决"用户怎么说"的表达保真。

## 用户意图锚 [required]

> 以下内容直接引用用户原始表达，架构师不得改写或概括。后续所有阶段以本节为语义保真基准。

**不适用** — 本需求为纯 SOP 流程变更（增加意图锚机制），不涉及用户对视觉/空间/交互效果的表达。用户对话中的描述（如"在气泡的左侧"）是机制设计的背景案例，非本 feature 的实现需求。

## 目标 [required]

### P1 — 核心保真

- 在 Feature 文档中建立"用户意图锚"区域，逐字记录用户原始表达并提取关键修饰语
- 在交叉审视中增加语义保真度检查维度
- 在验收标准中建立对意图锚的追溯关系

### P2 — 视觉/交互验证

- 对涉及视觉/空间/动画的变更，要求开发者提供视觉证据（截图/录屏）
- 审查者以视觉证据比对意图锚描述，不一致 = 审查不通过

## 非目标 [required]

- 不替代现有 Task Anchor 机制（两者互补：Task Anchor 管"为什么"，意图锚管"怎么说"）
- 不改变行为条目 S1-S5 的结构（意图锚是上游素材，行为条目从意图锚派生）
- 不引入自动化 NLP 比对工具（当前阶段以人工校验为主）
- 不要求所有需求都有意图锚（纯技术优化、重构等无用户表达的需求不适用）

## 设计 [required]

### 组件 1：Feature 文档增加"用户意图锚"区域

在 `## 背景` 之后、`## 目标` 之前，增加独立章节：

```markdown
## 用户意图锚 [required]

> 以下内容直接引用用户原始表达，架构师不得改写或概括。后续所有阶段以本节为语义保真基准。

| # | 来源 | 用户原话（逐字引用） | 关键修饰语 | 架构师解读 |
|---|------|---------------------|-----------|-----------|
| UA-1 | msg-{id} | 用户原话 | 空间/时序/数量/条件等修饰词 | 架构师的理解，必须覆盖所有修饰语 |
```

[D1] **意图锚的适用范围判断**：不是所有需求都需要意图锚。判断标准：用户表达中是否包含可被降维的修饰语（空间、时序、数量、条件、视觉属性）。纯逻辑需求（"当 X 时做 Y"）的行为条目 S1-S5 已足够覆盖。设计取舍：将意图锚标记为 `[required]` 章节但允许标注"不适用"，确保每个 feature 都经过适用性评估，而非跳过。**"不适用"的客观判断标准**：如果用户对话中没有任何包含空间/时序/数量/条件/视觉属性修饰语的表达，则可标注"不适用"。标注时必须附带原因说明（如"本需求为纯重构，无用户表达"），且原因说明必须在交叉审视中被验证。

[D2] **逐字引用 vs 概述的边界**：用户原话必须是逐字引用。如果用户跨多条消息表达同一需求，架构师应合并引用并标注消息来源（`来源` 列填写消息 ID）。如果用户用口语化表达（"就那个转圈圈的东西，放左边"），原文照录，不做书面化改写。原因：改写过程本身就是信息丢失的风险点。

[D6] **意图锚的记录时机**：意图锚必须在需求对齐结束后、向用户呈现方案前记录，以用户最终确认的版本为准。如果用户在后续对话中修改需求，必须更新意图锚表并在"架构师解读"列中标注修改历史（"用户曾表达 X，最终确认 Y"），保留决策过程。

[D7] **从意图锚到行为条目的派生规则**：一个 UA 可派生多个 B，一个 B 可追溯多个 UA。派生时必须保留 UA 中的所有修饰语，不得降维。"架构师解读"列中的解读必须与派生出的行为条目"预期行为"列一致。

[D8] **"逐词对比"的判断标准**：保真检查的核心不是字面逐词，而是"修饰语是否完整保留"。判断规则：(1) 空间修饰语（上下左右、内外、同行）必须保留，不得替换为其他空间词；(2) 时序修饰语（先、后、同时、立即）必须保留；(3) 数量修饰语（一个、多个、所有）必须保留；(4) 视觉属性（颜色、大小、形状）必须保留；(5) 口语化描述可书面化，但语义不得改变。

[D9] **意图锚与 Task Anchor 的优先级**：当两者冲突时，以意图锚为准。原因：意图锚是用户原话的逐字记录，Task Anchor 是架构师对目标的理解。Task Anchor 的成功标准必须与意图锚一致，不得矛盾。

### 组件 2：交叉审视增加语义保真度检查

在现有交叉审视机制中，增加一个必检维度。

架构师-2 审视时执行的保真检查清单：
1. 逐条检查"用户意图锚"表，确认"用户原话"是否为逐字引用（通过`来源`列的消息 ID 定位原始对话进行对比）
2. 逐条检查"关键修饰语"是否完整提取（空间、时序、数量、条件、视觉属性五类）
3. 逐条检查"架构师解读"是否覆盖了所有修饰语（按 D8 判断标准：修饰语完整保留，非字面逐词）
4. 检查核心业务行为条目是否体现了意图锚中的所有修饰语，追溯关系（← UA-n）是否正确
5. 标记为"待澄清"的条目是否已获得用户确认
6. 标注"不适用"的条目是否有合理的客观原因，且原因是否经交叉审视验证

[D3] **保真检查的执行深度**：架构师-2 不仅要检查意图锚表是否"填了"，还要按 D8 判断标准（修饰语完整保留）对比用户原话与架构师解读。这比现有审视更重，但"气泡左侧→气泡上一行"这类偏离恰恰是因为没有人做这个对比。权衡：增加审视时间成本 vs 防止需求偏离导致的返工成本。

### 组件 3：验收标准追溯意图锚

`## 核心业务行为` 和 `## 验证` 中的条目，对来源于用户意图锚的行为，在"预期行为"列末尾标注 `← UA-n`。

```markdown
| B1 | 当 AI 正在生成回复时 | 在消息气泡左侧同行显示加载标识 | ← UA-1 |
```

追溯关系的用途：
- 审查者可以快速定位每个行为条目的用户原话来源
- 可以反向验证：每个 UA 是否至少有一个 B 对应
- 当实现偏离时，可以精确定位是哪个用户表达被丢失

[D4] **追溯关系的粒度**：并非所有行为条目都需要追溯到意图锚。只有直接来源于用户明确表达的行为才标注。架构师自行推导的行为（如边界处理、异常路径）不标注，避免虚假追溯。

### 组件 4：视觉/交互类需求的特殊处理

对于涉及以下效果的变更，增加视觉证据要求：
- 空间位置（上下左右、同行、内部/外部）
- 布局（排列方式、对齐、间距）
- 动画（过渡、旋转、闪烁）
- 颜色/样式（主题、高亮、状态色）

流程约束：
- 开发者 PR 描述中必须附带关键状态的截图或录屏
- 截图必须标注与意图锚描述的对应关系
- 审查者比对截图与意图锚描述，不一致 = 审查不通过，标记为 bug

[D5] **视觉证据的范围界定**：不要求所有 PR 都附截图。仅当 Feature 文档的意图锚中包含视觉/空间修饰语时才触发。纯逻辑变更（API、数据处理、状态机）不强制。判断标准：如果行为条目中有空间/视觉/动画类修饰词，则该条目需要视觉证据。

[D10] **视觉证据与证据规则的融合**：视觉证据（截图/录屏）定义为证据规则（F2026060305）的第四种证据类型，与现有三种（验证命令、影响面清单、配置一致性对比）并列。视觉证据的格式要求：(1) 截图必须标注与意图锚描述的对应关系；(2) 录屏需覆盖关键状态转换；(3) 审查者比对截图与意图锚描述，不一致 = 审查不通过，标记为 bug。

## 设计约束摘要 [required]

### 硬约束（违反 = bug）

- 用户原话必须逐字引用，不得改写，来源列必须记录消息 ID
- 关键修饰语必须覆盖空间、时序、数量、条件、视觉属性五类
- 交叉审视的保真检查是必检项（6 项清单），不得跳过
- 视觉/空间类变更必须有截图/录屏证据，作为证据规则第四种类型
- "不适用"标注必须附客观原因，空白 ≠ "不适用"
- 意图锚与 Task Anchor 冲突时，以意图锚为准

### 设计取舍（必须保留）

- [D1] 意图锚标记为 `[required]` 但允许标注"不适用"（需附客观原因），平衡覆盖面与灵活性
- [D2] 用户原话逐字引用不做书面化改写，接受口语化表达的代价
- [D3] 保真检查按 D8 标准（修饰语完整保留）执行，增加审视成本换保真度
- [D4] 追溯关系仅对直接来源于用户表达的行为标注，避免虚假追溯
- [D5] 视觉证据仅对有视觉修饰语的行为条目触发，避免全面截图负担
- [D6] 记录时机为需求对齐结束后，修改时标注历史
- [D7] 派生规则明确一个 UA 可派生多个 B，派生时不得降维
- [D8] "逐词对比"判断标准为"修饰语完整保留"，非字面逐词
- [D9] 意图锚优先于 Task Anchor（用户原话 > 架构师理解）
- [D10] 视觉证据定义为证据规则第四种证据类型

### 语义不变量

- 现有 Task Anchor 机制不受影响，两者互补，冲突时意图锚优先
- 行为条目 S1-S5 结构不变，意图锚是上游素材
- 交叉审视的现有维度（风险、缺口、替代方案）不变，保真度是新增维度
- 证据规则的三种现有证据类型不变，视觉证据是新增第四种

### 非目标

- 不引入自动化 NLP 比对（未来可考虑工具辅助生成意图锚草稿，但当前阶段以人工为主）
- 不要求所有需求都有意图锚（纯技术优化/重构可标注"不适用"）
- 不改变开发者的编码流程（仅增加截图提交）
