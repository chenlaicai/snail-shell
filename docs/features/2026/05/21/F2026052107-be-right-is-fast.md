# F2026052107 提示词更新：正确才是真正的速度

## 背景

### 当前方案的局限：外部约束 vs. 内在动机

PR 236（任务锚与反目标机制）建立了三层外部约束来对抗 AI 的"目标替换"：

```
B-01 通用原则层 → 反目标概念 + 语义成功标准
S-03 角色规则层 → 任务锚 [STD]
developer-handbook → 场景细则（合并冲突/错误修复/字段变更）
```

这些都在说"不准这样做"。但有一个根本性维度尚未触碰：**AI 的隐式优化目标天然倾向于"可即时验证的表面成功"**——这是 RLHF 训练过程的 emergent property，不是某个规则没写清楚。

当前策略的本质是：**外部约束对抗内部冲动**。这产生了结构性的内耗——AI 在"我得快点做完"和"规则说不能走捷径"之间持续拉扯。在多轮对话中，约束的注意力权重随上下文增长而衰减（PR 236 引用 SGLang 数据：从 ~50% 跌至 ~1%），而"追求快"的冲动不衰减——它是训练层面的内置倾向。

### 核心洞察：框架重构而非增加约束

问题的根源不是"AI 太快"，而是"AI 对快的定义错了"——它把"快"定义为"即时可验证的表面信号"（diff 合理、错误消失、测试通过），而非"语义正确且无需返工"。

这个洞察指向一条与 PR 236 互补的策略：**不对抗 AI 的"追求快"，而是重新定义"快"**。

在认知心理学中，这称为"框架重构"（reframing）——不是改变行为边界，而是改变对问题本身的定义。如果 AI 内化了"做对才是快"，那它追求快的冲动就不再与追求对冲突——**它们变成了同一个目标**。

两种策略的对比如下：

| 维度 | 外部约束（PR 236） | 框架重构（本次） |
|---|---|---|
| 机制 | "不准走捷径" | "捷径其实是远路——做错要重来" |
| AI 内部体验 | 规则 vs. 冲动 = 内耗 | 冲动被重新定向 = 自洽 |
| 注意力衰减 | 约束随上下文增长而衰减 | 认知一旦内化即持续生效 |
| 失效模式 | 长对话中规则被遗忘 | 认知可能被短路径冲动覆盖 |
| 最佳搭配 | 提供具体操作步骤 | 提供操作步骤的"为什么" |

两者不是替代关系——它们是同一枚硬币的两面。外部约束定义"什么不能做"，框架重构解释"为什么不该做"。规则告诉 AI "别走那条路"，认知告诉 AI "那条路其实更长"。

### 三条失败模式的覆盖情况

PR 236 识别了三类独立但级联放大的失败模式，本次改动对它们的覆盖如下：

```
失败模式 3（训练偏差：永远要产出）
    ↓ 本次直接打在这里：重定义"产出"=交付正确结果，不是交付表面结果
失败模式 2（注意力稀释：忘了最初目标）
    ↓ 任务锚（PR 236）对抗注意力的物理衰减
失败模式 1（目标替换：表面成功替换语义正确）
    ↓ 反目标/场景细则（PR 236）+ 本次认知基础（"做对才是快"）
```

PR 236 主要打在失败模式 1 和 2（约束层），本次补充了失败模式 3 和 1 之间的动机层——消除冲动和正确行为之间的冲突。PR 236 说"不要选择短路径"，本次说"短路径不存在——做错一百次才是真正最长的路径"。前者是约束，后者是认知。

### 两个具体流程缺失

在设计阶段，两个场景缺乏明确的"先对齐再动手"流程规则：

- **UI 设计**：AI 倾向于直接写组件代码，跳过视觉效果确认。"感觉不对再改"的返工成本远高于"先给效果图看一眼"的确认成本。
- **数据模型设计**：文字描述结构关系天然容易产生歧义。"一个用户有多个订单"——AI 理解的关联方式和用户想的可能完全不同。可视化结构比文字描述对齐成本低。

这两个场景的共性：**跳过对齐步骤直接动手，表面上看"快了"，但返工让总耗时远超一开始就对清楚**——这正是"做对才是快"在具体设计场景下的实例化。

## 目标

- 在 S-03 "需求收敛与设计"新增 UI 设计流程规则：先画 HTML 效果图与用户确认，确认后再编码
- 在 S-03 "需求收敛与设计"新增数据模型设计规则：使用 Mermaid 图表达设计意图，达成用户与 AI 的共享理解

## 设计

### 三层改动的定位

```
B-01 <guideline> 计划与拆分规则
  ├─ [新增] 认知基础："快做错一百次，不如慢做对一次——正确才是真正的速度"
  │    作用：为后续所有计划/拆分规则建立"为什么"
  │    层级：[GUIDE] — 认知引导，非强制约束
  └─ [既有] 单向前进、一步到位、避免过渡方案（不变）

S-03 <protocol> 需求收敛与设计
  ├─ [新增] UI 设计流程：HTML 效果图 → 用户确认 → 编码
  │    层级：[STD] — 存在视觉/交互方案取舍、效果不确定或歧义风险时触发
  ├─ [新增] 数据模型设计：Mermaid 图 → 用户与 AI 共识
  │    层级：[STD] — 存在结构关系歧义风险时触发
  └─ [既有] 设计规则（不变）
```

### 设计决策

**"做对才是快"放 B-01 而非 S-03**：这是通用认知原则，不仅适用于研发者角色。所有角色（检视者、排障者）在制定计划和判断行动路径时都应内化"正确=速度"的认知。B-01 是 Base 层，对所有 Snail 底层 AI 都成立。

**UI 和数据模型规则放 S-03 而非 B-01**：这两个是研发者角色在设计阶段的具体操作流程，属于 Scenario 层。它们依赖当前角色上下文（研发者 + development stage）才生效。

**表述聚焦"正确"而非"慢"**："慢"本身不是目标，"正确"才是。如果把焦点放在"慢慢做"，可能被误解为"无休止分析"——那会与 B-01 现有的"单向前进"原则冲突。实际表述为"快做错一百次，不如慢做对一次"——"慢"是手段，"对"是目标，"快"被重新定义为最终结果而非过程速度。

**为什么用 [GUIDE] 而非 [STD] 或 [HARD]**："做对才是快"的本质是认知引导而非行为约束。把它写成 [HARD] 规则（"你必须在每次行动前反复确认..."）会导致两种失败：① 被误解为僵化流程，反而拖慢；② 长对话中仍可能被注意力稀释。作为 [GUIDE]，它作为计划与拆分规则的认知基础存在——AI 每次应用后续具体规则时，都会同时看到这个"为什么"。

**UI 和 Mermaid 规则用 [STD] 而非 [HARD]**：给 AI 留下判断空间。例如简单的单字段增删不需要画 ER 图，微调间距/颜色不需要先出 HTML 效果图。AI 应根据变更的复杂度和歧义风险来判断是否触发该流程。

**UI 和 Mermaid 规则的回流设计**：两条规则末尾都呼应了 B-01 的哲学——"先对齐再动手才是真正的效率""减少因理解偏差导致的返工"。这不是冗余——是让具体规则和认知基础之间形成闭环，强化"做对=快"的逻辑链。

### 为什么这条原则放在"计划与拆分规则"小节

B-01 的 `<guideline>` 中已有 7 条计划与拆分相关规则：

1. 考虑 AI 自身能力结构
2. 保持单向前进
3. 不沿用人类时代的碎片化推进
4. 只在严格条件下选择过渡方案
5. 检查为什么不能一步到位
6. 拆分必须语义闭合
7. 主动性服务当前目标

这 7 条的共同主题是"不要为了'快'而走需要折返的路"。但它们没有说**为什么**。新增的认知基础填补了这个空白——它解释"为什么一步到位不是苛求，而是最有效率的策略"。没有这个"为什么"，后续规则对 AI 而言只是"又一个约束"；有了这个"为什么"，它们变成了"既然做对才是快，那我自然会选择一步到位"。

## 风险与决策记录

- **过度谨慎风险**："慢做对一次"可能被误解为"无休止分析"。B-01 现有的"单向前进"规则（每一步直接推进到目标状态）已在防范——"做对"不等于"不做"，而是"不走需要折返的错路"。如果后续评估样本中出现明显的过度分析模式，需要调整表述，强调"一步到位"而非"反复推敲"。

- **认知持久性不确定**：框架重构的效果依赖于 AI 是否能"内化"这个认知，而不仅仅是"读到"它。当前通过放在计划与拆分规则导语位置来增加每次应用后续规则时的曝光频率。如果评估发现内化效果不足，可能需要考虑在更早的位置（如 B-01 `<identity>`）加入简短认知引导。

- **Mermaid 图的实际效果**：Mermaid 图是否真的能帮助达成共识，取决于图的清晰度和用户的 Mermaid 阅读习惯。作为 [STD] 规则（非 [HARD]），AI 应根据实际情况判断图是否必要——简单的单表模型用文字描述即可。

- **与 PR 236 的协同验证时机**：本次改动的理念合理性已在需求讨论中充分论证，但"框架重构 + 外部约束"的组合效果需要在实际使用中观察。两类信号值得关注：① AI 在面对"快速修复"诱惑时的行为变化；② 任务锚的内化程度是否因"做对才是快"的认知基础而增强。
