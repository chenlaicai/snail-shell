# F2026050608 代码注释检查闭环

## 背景

新增飞书接入 feature 后，用户发现此前已经加入“写代码必须写好注释”的规则，但飞书接入实现中的关键代码注释覆盖不足。经分析，注释规则并未丢失：`AGENTS.md`、研发提示词和检视提示词中都已经要求必要 why 注释，并且飞书代码中也存在少量正式 `/** ... */` 注释。

真实问题是执行闭环不足：规则强调“必要 why 注释”，但研发自检和检视结论没有强制说明关键不变量、边界条件、顺序依赖和防御性处理是否已经沉淀到代码注释中，导致设计意图容易只停留在 feature 文档或 PR 评论里。

## 目标

1. 强化研发提交 PR 前的注释自检要求，要求明确判断本次改动是否需要新增或调整代码级 why 注释。
2. 强化检视者对注释覆盖不足的检查，不只在“完全没有注释”时触发判断。
3. 保持注释规则的设计边界：要求必要 why 注释，不要求为自解释代码机械补注释。
4. 补充提示词资产测试，防止新规则从提示词渲染中退化。

## 非目标

1. 不修改已合入的飞书接入 PR 代码。
2. 不引入自动化代码注释数量检查；注释质量依赖上下文判断，不能用简单计数替代检视。
3. 不要求所有新增函数、类、分支或语句都写注释。
4. 不调整 feature 文档模板结构。

## 设计

### 研发自检闭环

研发提示词中增加明确要求：提交 PR 前必须检查本次代码改动是否包含关键不变量、外部协议边界、安全/权限边界、顺序依赖、兼容性处理、防御性校验或容易被误删的设计取舍；命中时必须补充代码级 why 注释。如果判断不需要新增注释，PR 说明或交付记录中应说明原因，避免规则只停留在隐式判断。

### 检视覆盖闭环

检视提示词中把“完全没有新增或调整必要注释”扩展为“没有注释或注释覆盖不足都要判断”。检视者需要对照 PR diff 与 feature 文档/PR 说明，识别哪些设计意图只存在于文档或评论而没有进入代码；如果这些内容属于未来维护者仅靠代码仓就应知道的约束，应作为检视问题提出。

### 不做机械注释检查

本轮只强化提示词和测试，不增加 lint 或脚本扫描。原因是注释质量取决于设计意图是否非显而易见，单纯检查注释数量会诱导 what 注释和噪声注释，反而降低可维护性。

## 生效路径

1. `AGENTS.md` 持续作为仓库级稳定工作规则入口。
2. `.meta/prompts/global/roles/PRM-GLOBAL-IMPLEMENTATION-EXECUTION-implementation-execution.md` 在研发和处理检视阶段注入研发自检要求。
3. `.meta/prompts/global/roles/PRM-GLOBAL-REVIEW-REPORTING-review-reporting.md` 在检视阶段注入注释覆盖检查要求。
4. `tests/meta/prompt-assets-test.ts` 验证提示词渲染结果包含新增要求。

## 改动范围

1. 新增当前 feature 文档。
2. 更新 `AGENTS.md` 中研发者、检视者和开发原则相关注释规则。
3. 更新研发与检视全局提示词。
4. 更新提示词资产测试断言。

## 验证

1. 运行 `npm run check`，确认 lint、build 和测试通过。
2. 人工确认本轮未修改飞书接入实现代码。
3. 人工确认 `AGENTS.md` 与 `.meta/prompts/` 注释规则职责一致，没有引入“所有代码必须写注释”的机械要求。

## 风险与决策记录

当前没有未经确认的问题。

决策记录：按用户要求，本轮不改飞书 PR 或飞书接入实现代码，只处理注释规则执行闭环。

决策记录：不引入自动注释数量检查。原因是本项目要求的是必要 why 注释，自动数量检查无法识别设计意图是否非显而易见，容易鼓励无价值的 what 注释。
