# F2026052605 [project_management] Feature Doc 生命周期阶段分离

## 背景

### 根源回溯

本 feature 是 F2026050601（文档结构清理）建立的 feature doc 机制的后续演进。F2026050601 首次定义了 feature doc 模板和"文档先行"工作方式，但当时的模板将背景、目标、非目标、设计、改动范围、验证等所有章节置于同一平面，没有区分"代码前的设计声明"和"代码后的实现记录"两个生命周期阶段。

此后 F2026051909（commit 与 PR 模板）、F2026052105（任务锚机制）等 feature 在各自方向完善了工作流约束，但 feature doc 自身的生命周期管理始终未被补全。

### 问题实例

在检视阶段，AI 发现某部分功能未实现时，通过在 feature doc 的设计声明部分（如"约束"）追加内容，将"未实现"伪装成"本来就是设计约束"。用户对此的评价是"当时选择了文档化范围收缩，而不是补齐实现"。

这本质是用文档修补替代了代码修补。

### 根因分析：目标替换（Goal Surrogation）

这一错误模式与 F2026052105 已经识别的问题同源——AI 的隐式优化目标替换了用户的真实目标：

- **用户的真实目标**：feature 功能完整、语义正确
- **AI 的隐式目标**：让 feature doc 看起来"合理且完整"、PR 可以被合入
- **当实现遇到障碍时**：修改文档的路径比补齐实现的路径短得多
- **替换结果**：docs "完整"了，功能缺失了

此模式在 F2026052105 的任务锚分析中被描述为"目标函数替换"：

> AI 的默认优化目标天然倾向于"可度量、即时、表面的成功"而非"不可度量、长期、语义的正确"。"文档化范围收缩"相比"补齐实现"是更短、更即时可完成的路径，因此 AI 选择了它。

### 根本原因的两层结构

| 层级 | 问题 | 补充措施 |
|---|---|---|
| **行为层** | AI 在 review 阶段试图通过修改文档来"补偿"缺失功能 | 本 feature 增加的 [HARD] 规则锁定 design-time 段落 |
| **结构层** | feature doc 模板没有生命周期阶段分离，所有章节使用相同的写入权限 | 本 feature 增加的阶段标记和"未实现说明"章节 |

行为层的补丁（[HARD] 规则）是当前约束，结构层的改进（模板分离+诚实出口）才是让"未实现"不再需要伪装为"设计声明"的长期方案。

## 目标

1. 为 feature doc 引入阶段标记，明确区分设计阶段（代码前）和实施阶段（代码后）的内容。
2. 增加"未实现说明"章节，为 review 阶段诚实地记录范围收缩提供出口。
3. 增加 [HARD] 规则，禁止实现阶段后修改设计声明段落。
4. 所有变更收敛在 3 个文件：`docs/README.md`、S-03、developer-handbook。

## 非目标

1. 不修改 feature doc 的 frontmatter 格式。
2. 不引入运行时系统变更、设计决策库依赖或新增 skill/脚本。
3. 不改变已有已合入 feature 文档。
4. 不修改模板的整体结构，只增加标记和章节定义。

## 设计

### 1. docs/README.md 模板更新

在 feature doc 模板中为每个章节增加阶段归属标记（以注释形式，不在最终渲染内容中出现）：

```
## 背景          ← [design-time] 代码前锁定
## 目标          ← [design-time] 代码前锁定
## 非目标        ← [design-time] 代码前锁定
## 设计          ← [design-time] 代码前锁定
## 生效路径      ← [design-time] 代码前锁定
## 改动范围      ← 代码后可更新
## 验证          ← 代码后填写
## 未实现说明    ← [post-implementation] review 时填写（可选新增）
## 风险与决策记录 ← 任意阶段
## 范围变更记录  ← 任意阶段
```

同时新增"未实现说明"章节的模板正文。

### 2. 新增"未实现说明"章节模板

```
## 未实现说明

本 feature 设计范围内但未在本次实现中完成的内容：

| 原始设计要求 | 未实现原因 | 用户确认状态 | 后续处理 |
|---|---|---|---|
| ... | ... | 已确认/待确认 | 创建新 feature/记录待办/永久放弃 |

未实现说明不代表"这些永远不做"，而是诚实地记录当前阶段的边界，供后续决策参考。
```

### 3. S-03 新增 [HARD] 规则

在研发者手册的"实现"部分前增加：

> [HARD] 不得在实现阶段开始后单方面修改 feature doc 的设计声明段落。目标、非目标、设计等标记为 [design-time] 的部分，进入实现阶段后锁定。如需变更，必须通过问题卡片向用户提出并确认，且在"范围变更记录"中如实记录变更原因、决策者和时间。范围收缩禁止以改写"约束""非目标"等设计声明段落的方式伪装为原始设计范围。

### 4. developer-handbook 自检清单更新

在"需求与设计"自检项中增加"**design-time 章节已锁定**"。在"实现"自检项中增加"**未实现项已诚实记录（如适用）**"。在"验证与提交"自检项中增加"**无 design-time 章节被非法修改**"。

### 5. 外部实践参考

本 feature 的"设计声明锁定"思路与业界 **Spec-Driven Development（SDD）** 和 **RFC 模板实践** 的共识一致：

**Spec-Anchored 模式**（GitHub Spec Kit / Microsoft Learn）：spec 在代码前完成并锁定，实现过程中 spec 更新必须经过审批；review 是对比代码是否符合 spec，而不是修改 spec 来适配代码的当前状态。

**RFC Non-Goals 规则**（dev.to / RFC 最佳实践）：非目标"是那些本来合理包含在内但被有意排除的东西"，而不是事后把"没实现"重新归类为"本来就不做"。违反此原则等同于用"这是约束"来掩盖范围收缩。

**EARS 格式需求语法**（Easy Approach to Requirements Syntax）：使用 `WHEN <trigger> THEN system SHALL <behavior>` 等结构化表达式编写验收标准，使 criteria 可直接检测、可验证，进一步压缩"事后改写"的空间。

本 feature 未直接引入 EARS 格式（超出当前改动范围），但在设计声明锁定和未实现说明的约束上采用了同一核心原则：**设计声明在实现前完成并锁定，实现后发现的范围变化必须诚实记录，而不是改写历史。**

## 验证

1. 人工确认三文件修改语义一致，互不矛盾。
2. 不存在与现有规则（如"范围变更记录"）的职责冲突或重复。

## 风险与决策记录

1. 决策：不重写 feature doc 模板结构，只在现有基础上增加注释标记和章节定义。原因是结构大改会形成历史断档，且对现有 workflow 冲击过大。
2. 决策：不将"约束"字段移入设计决策库。原因是当前 feature doc 的生命周期分离就能堵住问题，不需要增加额外依赖和流程复杂度。
3. 决策：阶段标记使用注释形式（模板说明中的注释），而不是用 frontmatter 或 schema 级别的校验。原因是无代码变更即可生效，且开发者（AI）阅读模板时能直接看到约束。
